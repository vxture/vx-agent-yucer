### 2a/2b/2d 已交付内容

- `authz/`：19 权限 / 7 角色的**类型化镜像**，`catalog.test.ts` 逐条解析

### 一轮六视角审计（2026-08-16）

对全仓做了一次六视角审计（产品完整性 / 门控正确性 / 数据完整性 / 智能体两平面 /
测试缺口 / 界面质量），36 条原始发现，经**独立质疑者对抗验证**后确认 4 条 critical，
4 条被驳回（这正是验证阶段的价值——半数没扛住敌意复读）。四条已全部关闭：

| 发现 | 处置 |
|------|------|
| D6 管道完全只读，无人能推进/定价/关闭商机 | PR #22 |
| 无角色管理界面，工作区只能有一个可用的人 | PR #23 |
| 放弃 SSE 流只 `releaseLock()` 不取消，上游继续生成并计费 | PR #24 |
| `platform/s2s.ts` 零测试，ADR-004 的计费主体不变量无人守 | PR #25 |

PR #24 顺带发现超时其实什么都没管住：`timeoutMs` 在响应 resolve 时清除，而那是
**响应头到达**的时刻，两个客户端的 body 读取都是无界的。PR #25 在写测试的过程中发现
`cacheKey()` 用 `"|"` 拼接**不是单射的**（`tenant "a|b"+ws "c"` 与 `tenant "a"+ws "b|c"`
同键），一个工作区铸出的凭证会被交给另一个——测试第一次跑就红。

PR #26 处理审计尾部中**不涉及商业判断**的部分：账户详情页直接持有 store 句柄（隐藏
导航链接不是访问控制，直接输 URL 照样返回客户档案与联系人名单）；`execute()` 在门之前
读行，使未授权者能通过 `not_found` 与 `permission_denied` 的差异**枚举有效提案 id**。

### 对同一轮自身产出的复审（PR #31）

上述十个 PR 是在一次连续作业里写的，只有作者本人看过。于是把同一套机器（五视角 +
独立质疑者）对准 `e65a7ea..HEAD` 这个范围本身：27 条原始发现，**4 条确认、4 条驳回，
四条确认的全部是这一轮新引入的**。

| 缺陷 | 性质 |
|------|------|
| `planStageChange` 不移动 `forecast_category` | 赢单后仍留在 `commit` 桶，`rollUp()` 把**已赢收入算成未到手承诺**，`closedAmount` 为空——同一笔钱报两次。且该行处于 `planCategoryChange` 双向拒绝的状态，后续任何编辑都修不回来 |
| 预测类别写在编辑门之下 | 类别属 `pipeline.forecast`（pro + 专有权限，规格文档明写），却被折进 `pipeline.opportunity.update`（免费档）。反向荒谬：规格指定的 `sales_ops` 反而调不到该函数 |
| 已关闭商机保存必失败 | 上一条的后果，表单每次提交全部字段，把过期的桶带回去 |
| 拒绝的流丢失错误信封 | **修 #24 泄漏时引入**：`abort()` 放在读 body 之前，`GRANT_DENIED`/`QUOTA_EXCEEDED`/`RATE_LIMITED` 全塌缩成裸 `"403"` |

**这一轮的方法论结论，值得记住：**

- **审计擅长发现「没接上的东西」，不擅长发现「接错了的东西」。** 四条 critical 都是
  「后端完整但界面没接」，而 #31 的四条全是「接了但接错」——后者要靠动手复算、以及
  让测试去撞才会暴露。
- **一个测试的价值取决于它断言的是什么，不是它有多少行。** 往返测试断言了收关后的
  状态、赢率、`closed_at`、金额，唯独漏了类别，于是一路绿着放行了最严重的一条。
- **修复本身会制造缺陷。** #24 修泄漏时弄坏了诊断能力，而 #24 自带的测试因为假 body
  没接到 `init.signal` 上而抓不到。新测试留下之前先把修复回滚验证它确实变红——
  **一个不会为它守护的 bug 变红的测试，不是测试**。

### 界面层的两条纪律

**没有任何页面在本地重算商业结论。** 按钮的可见性一律来自服务端动作会重跑的同一个
`can()` 门。信号页曾经用 `["pro","business","enterprise"].includes(tier)` 算过一次，
上线前被抓掉——那是产品在本地推导商业结论，套餐一改就漂移。

**全部非 ASCII 文本集中在两个纯数据文件**：`(app)/lib/messages.ts`（界面文案）与
`domains/shared/demo-fixtures.ts`（演示数据的展示文本）。两者都不含逻辑，`app/` 下
其余源文件全部 ASCII，可机器穷举（TD-002）。

## 批次 3.5 - 证据面与两条平台面（PR #36-#46）

批次 3 之后追加的一轮，起因是 owner 的重新定位：**把原来散在各销售人员脑子里的信息

| #46 | 决策链接入交互参与人；逾期承诺扫描作业 |

**一期带杀死判据**：六周窗口，按 `/admin/adoption` 的覆盖率读数决定二期（主张与判断层）
建不建。判据的两个决定值得记住：

- **测覆盖率，不测数量。** 一个人往一条商机上倒二十条笔记，「每周交互数」会很好看，
  而另外十九条商机全黑——由此得出的「习惯形成了」在唯一要紧的意义上是假的。
- **刻意不按人拆分，并写在界面上。** 一旦能当绩效看，大家就会为它记录，它就不再测量
  它要测的东西。

窗口未满一律返回「观察期未满」而非失败：**一个能提前失败的判据，一定会被提前引用。**

#### 6b-1b 已交付（2026-08-26）

规则（`lib/pricing.ts` 追加三个 plan 函数）、端口写方法、内存实现、
**`prisma-store.ts`——本域的第一个适配器**、三条写服务、5 条新测试。

**权限分离是这一项的核心，也是唯一被反证过的断言。**
`catalog.write` 维护卖什么，`catalog.price` 决定不再往下让的那条线。
测试用手工构造的持有者把两者**分别**给出去，断言各自**做不到对方的事**——
把 `catalog.pricebook.upsert` 的权限改回 `catalog.write`,这条测试立刻变红。
一个编目录的人顺手就能移动底价的产品，是一个每笔折扣都自我批准的产品。

**价格是追加的，不是就地改的。** `effective_at` 属于唯一键，新时点的新价格是新行——
这正是「价目**书**」区别于「价目」的地方：被取代的那一行仍可读，它解释了今天这个
数字是怎么来的。`incr/0010` 给 list/floor 的 UPDATE 授权是为了改刚写错的那一行，
不是为了改写历史，端口刻意不暴露它。

**三条规则各自挡住一件事**：产品必须有**单位**（没有单位的「10 × 1000」是十个坐席、
十天还是十个站点，那是三笔不同的生意）；方案必须**装着东西**（空方案是个名字）；
底价**不得高于标价**（那会让每一笔都需要签字，等于没有底价）——
但底价**等于**标价是允许的，「此产品不打折」是一个立场，不是笔误。

**适配器的两处事务不是保守**：方案的 items 是**整体替换**,delete 与 insert 之间失败
会留下一个空方案，而空方案正是规则层拒绝任何人创建的东西。

#### 6b-3 已交付（2026-08-26）

`replaceOpportunityLines` 落在 **pipeline** 而不是 catalog：行项住在
`yucer_pipeline`,按 ADR-001 归 D6——定一笔交易的价属于
`pipeline.opportunity.update`,目录只是它读的维度。

**ADR-014 §2 就是这个函数的全部**：行项存在时行项是权威，
`opportunity.amount` 等于它们之和。这条约束写在服务层而不是 DDL——
它跨行（一个 header 对多条 line）,CHECK 表达不了，触发器会把业务规则藏进数据库。
于是服务在**写行项的同一次调用里**重算 header，而且这是**唯一**允许改 amount 的路径。

**`needsApproval` 由服务算，永不接受调用方传入。** 客户端能设的标志就是客户端能清的
标志，而这一个决定一笔折扣要不要送到人面前。逐行按「该产品该币种当时生效的那一条」
定价——拿一次查询给整批定价，会让一条过期底价去裁定它从未适用过的产品。

**实测**：把一行数量 16 → 8，运行合计在提交前就显示 1,900,000；保存后
详情页与管道列表页的 header 双双变成 ¥1,900,000。
再把一行单价压到 1，服务端标出「低于底价，需要签字」;恢复后标记消失。

**六条测试守着这条规则**，其中最要紧的一条断言的是**存储里的 header**而不是返回值——
一个报告了自己没写进去的总额的函数，会在它自己的输出上通过测试，
而把两个数字留在那里各自漂移。反证过：让服务写 `total + 1`,这条立刻变红。

#### 6b-4 已交付（2026-08-28）

6b-3 交付时留下了一个自己造出来的死结：定价规则会把低于底价的行项标成待批，
战况板会计数，徽标会显示，**而权限目录里没有任何一条权限能把它降下来**。
`pricing.discount_approval` 只是 ADR-015 的一个能力标签，说的是智能体可以*提议*，
不是有人可以*做出*。底价创造了一个没人能满足的签字要求。

**新权限 `pipeline.discount`（incr/0012），与 `pipeline.write` 分离。** 报出低于
底价的人不能是给它签字的人。授予范围与 `catalog.price` 相同——定底价和为底价开例
外是同一份权力的两半，而 sales_ops 本来就能移动底价。功能键仍是 19。

**签字按价格记，不挂在行项上。** 行项是整体替换写入的，挂在行项上的签字会被同一
商机上任何另一行的编辑销毁。键取
`(opportunity_id, product_id, unit_price, currency)`,于是三个性质是白送的：改别的
行签字仍在，重新报得更低就匹配不上（对，没人签过新数字）,改回签过的价格又匹配上
（也对）。追加表，无 UPDATE / DELETE 授权。

**实测**：sales_rep 把单价压到 700（底价 800）,行项列「折扣」显示「待批」且**没有
批准按钮**；同一页以 sales_leader 打开，按钮出现，填理由签字后该行变「已批准」,
管道列表的待批徽标从 1 归零。改到 600 后徽标重新出现，改回 700 又消失。

**九条测试**，其中两条做过反证：把 `approvalFor` 的价格比较去掉，「改低即失效」立刻
变红；把 action 的权限改成 `pipeline.write`,「销售不能给自己签字」立刻变红。

**顺带修好一个守卫的盲区。** `column-locks.test.ts` 原来只从「先全授权再 REVOKE
UPDATE」推导追加表。本增量的表用的是更紧的写法——建表时就只授 SELECT / INSERT——
于是对那条推导完全不可见。推导已拓宽为认两种写法，并配了各自的非空断言。
（一度以为它顺手抓到了 `yucer_field.commitment` 的缺失授权，查证是我漏看了它后面的
列级 `GRANT UPDATE`,那里没有缺陷。）

### 数据库通道（PR #34/#35）

`db-contract` job：`postgres:18` service 容器，按 `db-init.yml` 的**同一顺序**跑真
DDL，然后跑 `*.db.test.ts`（15 个）。**未加入必需检查集合**——那会改动分支保护
ruleset，是 owner 决定。

之所以必须先建通道再修适配器：唯一索引、CHECK、REVOKE 和 NULL 比较都是**数据库的
性质**，内存适配器建模不了。有几个缺陷就是这样在 788 个绿灯下活下来的：

- `uidx_sales_target_scope` / `uidx_forecast_snapshot_scope_at` 建在可空列上，而
  Postgres 的 UNIQUE **把 NULL 视为互不相同**——所以这两个约束**对工作区级行完全
  失效**，而那正是其他所有数字的基准。`incr/0003` 用 `NULLS NOT DISTINCT` 重建。
- `count()` 分配编号的三处注释都声称"放在事务里所以安全"。事务给的是**原子性不是
  串行化**：READ COMMITTED 下两个并发事务读到同一个 count。改用
  `pg_advisory_xact_lock`，按分配种类和作用域双重分键。
- `saveWinLossReview` 的 upsert `where` 未按工作区限定；`recordSignal` 的裸 `catch`
  把外键/CHECK 失败一律报成"已存在"。

**通道在它自己第一次运行里就抓到了三个我写的缺陷**：CHECK 测试的第 2、3 条断言因
Postgres 事务中止语义而实际无效（约束删掉照样绿）、硬编码容器口令、安装未禁用生命周期
脚本。这三件都只有对着真数据库和真 CI 跑过才会现形。

关于审计的一处措辞更正：它称 `deletedAt` 过滤意味着"全仓服务层断言证明的是另一个
实现"。**这说过头了**——没有任何产品路径能设置 `deleted_at`（所有 port 都没有删除
方法），两个适配器返回的是同一批活行。真正成立的是**排序**分歧（PR #30）。

TD-002 的现状是**收敛而非解决**：全部非 ASCII 文本集中在两个纯数据文件——
`portals/app/app/(app)/lib/messages.ts`（界面文案）与
`portals/app/app/domains/shared/demo-fixtures.ts`（演示数据展示文本），其余源文件
全部可机器校验。**收敛的口径是「可穷举且只含数据」，不是「只有一个文件」**：新增中文
文本只能进入这两个文件，装配逻辑（如 `demo-seed.ts`）必须保持 ASCII。

标准修订后二选一收口——平台仓为终端用户文案开显式口子，或引入正式 i18n 方案把文案
移出源码树。**在裁定之前收敛状态维持不变，不要「顺手修掉」**：把文案改成 `\uXXXX`
转义确实能满足字面规则，但会得到一份人类无法维护的文案和一份无法评审的演示数据。

### 一版被丢弃的 karda 接入（2026-08-15）

本仓曾写过 `platform/karda/{types,redact,client}.ts` 三个文件，含一个「主张可外发、
证据不可外发」的边界模块。**已整体丢弃**，不是风格问题——一次独立对抗审查（四视角 +
独立质疑者，62 个 agent、28 条确认发现）在那个 137 行的边界文件里查出**四条各自独立
的客户名称越界路径**：最强的一道检查 `knownNames` 通过端口结构上不可达；`derivedFrom`
原样外发且其唯一校验器是死代码、还按 `acc_` 前缀写而本仓主键全是 `gen_random_uuid()`；
facet 的**键**从不检查；正则是照测试夹具而非真实中文文案调的。外加该模块**从未编译
通过**（全仓唯一一处 tsc 错误，硬失败 `build`）。

**方法论上的结论，比这些 bug 本身重要：**

> **可以把「线格式的猜测」隔离在一个适配器里；不可以把「不属于自己的词汇表」隔离起来。**

那版代码自造了 `KNOWLEDGE_KINDS` / `KNOWLEDGE_SCOPES` / `KnowledgeClaim` —— 一个本仓
并不拥有的领域的词汇表 —— 再把一条**不可逆**的披露边界挂上去。猜错时端口错、边界规则错、
所有调用点全错，传输层隔离救不回来。arda 一期之所以能现在就写，正是因为它的端口返回
**yucer 自有的 `NewSignal`**，唯一的猜测被关在 `http-source.ts` 一个文件里。

悄悄挑 `rows[0].href` 然后与启动器分歧。反证：退回按键查找 → 红；战况板自选 → 红。

**实测**：`/domain/position` 上模块条回来了（`阵地经营域 | 客户管理 | 商机管理 |
报价管理 开发中 | 赢丢复盘`），战况板尾部读作五个域块，`战略武备域 → /domain/armory`、
`兵力部署域 → /planning`（单路由域指向那一页）。

### 7q 菜单按域拆开 —— 已交付（2026-08-30）

owner 两次纠正之后才对：「五个业务域 = 五个相对独立的功能板块，有单独的菜单+必要
首页」「你的菜单还是一锅粥」「保持现在菜单的 card 模式，需要按照业务域拆分为 5 个」。

**我前两次都改错了地方。** 7o 做域首页、7p 改战况板尾部的分组——都不是菜单本身。
菜单就是左栏那一列卡片，而它是一锅粥：判断卡（等你定、我的资源、友军·决策链、
产品线·在办）加五个域块，**全量堆在一起，不管你在哪个域、在做什么**。那是一个
没有域的产品的菜单。

**改法：菜单 = 你所在域的卡片。**

- **在域内**：只显示这个域自己的卡（判断卡 + 模块卡）加跨域常驻卡。
- **不在域内**（首页）：菜单就是五个域的**地图**——那是你挑一个板块进去的地方。
  进去之后地图消失：它的全部职责就是把你送进去，留着等于把你已经做过的选择在
  产品的每一页再摆一遍。

**归属从 href 读出，不手工指派。** 一张卡链接到它数字的来源页，那一页本来就只在
一个域里——所以 href 就是答案，卡换页即自动换菜单。手工指派会让两者漂移，而一张
归在它并不链入的域下的卡，是一个点下去就离开本板块的菜单项。

**踩到一个真错误并记下判据**：`menuFor` 起初写在 `board.ts` 里，而 `nav-board.tsx`
是客户端组件——把整个服务端模块拖进了浏览器包，构建死在 `Can't resolve 'fs'`。
规矩不是「文件要小」，是**客户端组件只能 import 浏览器跑得动的模块**；类型可以随便
引（类型会被擦除），运行时函数不行。已拆出纯模块 `board-menu.ts`。

**实测三处**：`/pipeline` 收窄为阵地经营域的四张卡；`/` 是五域地图；`/catalog` 只剩
常驻卡——战略武备域目前确实没有判断卡，那是真实状态不是缺陷，但值得记：**域拆开之后，
哪个域的菜单是空的立刻看得见**，这在一锅粥里是看不出来的。

反证：菜单停止过滤 → 5 条守卫红 4 条。

## 业务流程与剩余任务计划（2026-08-30）

### 流程摊平


### 本轮执行 —— 第 1 批已交付（2026-08-30）

**报价面 `/quote`**。机制一直都在：`opportunity_line` 带 quantity/unit_price/
amount/`needs_approval`，`price_book_entry` 带底价，`line_discount_approval` 带签字，
而 `listOpportunityLines` **早就把行项与审批 join 好了**（正是为了没有调用方能只看到

DesignateAccount），缺的是**名册**——「我们的重点客户是谁」放在一起看。
**只读，刻意的**：分级要在能看到证据的地方做（健康度、决策链、在办商机都在详情页），
在列表上给分级控件等于邀请人对着表格给客户排座次，而那正是 ADR-013 要避免的。

**16/19 个模块已是页面**，余 3 个需裁定（见第 2 批）。

### 第 2 批 · 线索分派 —— 已交付（2026-08-30）

owner 裁定：**「首先是区域，其二是负载」**。

**先量出链条断在哪**：`territory.owner_sub` 自 baseline 就在——「谁覆盖这块地」一直
答得出；**「这块地是哪」从来没有**。demo 把这个洞摆得很明白：区域叫
EAST/NORTH/SOUTH，客户带的是 华东/华北/华南/华中/西南/西北，**中间没有任何列、键或
规则连接**。区域优先的分派在这一环补上之前根本无法存在。

`0017` 给 territory 加 `regions`（JSONB 列表），**与 market_segment.criteria 同形状**
——那是已被真实数据验证过的模式，另造一套「这个覆盖哪些客户」的词汇会让产品对同一个
问题有两个答案，正是 ADR-023 写的那个错误。**空 = 不覆盖任何**，不是覆盖全部：
一个没配完的区域不该成为全工作区每条线索的答案。

**规则的顺序就是规则本身**。区域决定谁**有资格**接，负载决定这几个人里**该谁**接。
反过来，闲着的销售会拿到他从没打过的地盘——那比排队慢更糟。关键反证：rep_1 手头
99 条、rep_2 空闲，华东线索**仍然给 rep_1**。

**无法分派是一种结论，不是错误**：没匹配客户、客户无区域、无区域覆盖、覆盖区域无
负责人——四种都保留在列表里且说明原因。把它们藏掉会让区域地图看起来是完整的，
而线索悄悄没人接。

**预览 + 逐行应用**，不是「一键全分」。分派是在人之间搬工作，最需要人看一眼的恰恰是
规则答错的那种情形；而线索归谁，是谁会被问起它——那是几十个独立决定，不是一个批量
操作换了件衣服。

**实测**：长江物流（华中）→ East China → 指派成功 → 刷新后显示「已在规则位置」且
按钮消失；生鲜连锁未匹配客户，如实显示无区域、不给按钮。

**顺带发现并加固**：规则原本直接读 `t.regions`，而 0017 之前的历史行没有这一列——
`undefined.includes()` 会让路由器在遇到真实生产数据的那一刻停摆。改为
`(t.regions ?? [])`，未知的地盘读作「不覆盖」而非「覆盖全部」，并补了对应测试。

### 第 2 批 · 续约规则 —— 规则层已交付（2026-08-30）

owner 裁定：**「续约商机从项目派生，但是需要为订阅类的项目开始」**。

`0018` 给 project 加 `engagement_type`（one_off | subscription）。**为什么是一列而不是
从既有字段推**：`ends_at` 两种都有——一次性实施交付即结束，订阅制到期即结束——
从日期、金额或产品组合去猜一笔生意的商业形态，是从影子推实物；猜错的代价是要么追讨
客户从未承诺的续约，要么漏掉真正会流失的。**默认 one_off**：所有既有项目都早于这一列，
默认订阅制等于给历史上每一次交付都凭空造出一个续约义务。

规则要点：**已过期的最紧急**（把过去过滤掉正好藏起漏掉的那些）；**暂停中的项目仍在
走期限**（工作停了钟没停，这正是最容易漏的时候）；**草案带上一期的金额，不发明涨价**
（上期值多少是事实，下期值多少是谈判）；**已续约的不再提第二次**。9 条测试。

派生动作本身**不自动写**——ADR-003 那条线在这里格外重要：提案是对客户的一次商业接触。
UI 与服务层在下一批。

### 第 2 批 · 续约服务层与页面 —— 已交付（2026-08-30）

上一批把续约的规则写完了，然后停在那里，工作计划自己记了一句「UI 与服务层在下一
批」。这一批是那句话的兑现，但先量出来的是**规则里有一条分支根本到不了**。

**`already_renewed` 是死代码**。`assessRenewal` 有这条分支、有测试、有注释，而测试
是靠手工传进去的一个布尔量满足的——真实调用方无从得知。原因是模型里少一条边：
`project.opportunity_id` 记的是「这个交付来自那笔生意」（D6→D7 的去程），**没有任何
列记「这笔生意是那个交付的续约」**（回程）。没有它，产品会在期限窗口内每打开一次页面
就重新提议同一个续约，无论已经有人开过几个。

`0019` 补这条边：`opportunity.source_project_id`。

**为什么放在商机上而不是项目上**。两种放法都能回答「续过了吗」，所以由**谁来写**
破局：`source_project_id` 由 D6 在写自己那一行时写入，符合「一个对象一个归属域」；
反过来 `project.renewal_opportunity_id` 要 D6 伸手去写 D7 的表，为省一列破掉归属规则，
而且把一个项目永远钉死为只能续一次——对一份还会继续走下去的订阅是错的。

**它不给 UPDATE 授权**，这是设计不是遗漏。「这笔生意从哪来」就是归因，而归因键在
创建时冻结（98 的第 2 条）。INSERT 是表级的，所以它能被写一次、永不可改。因此 98
无需改动，可写列镜像也不动——**增量只有在加「可写」列时才需要重述 GRANT**。

**续约不是 self_sourced**。`resolveAttribution` 多了一条 `renewal` 分支。self_sourced
说的是「销售自己挖到的」；把续约算进去，等于让新业务领走存量书带来的收入的功劳——
正是归因冻结要防的那种功劳重分配，只不过挪到了创建时刻，没人看得见。`campaignId`
留 null：继承首期的 campaign 会让一场活动为客户此后每一次续约持续记功。

**两个动词，各守各的门，都不写**。`listRenewals`（D7）说什么快到期，`renewalDraft`
（D7）说某一笔会以什么条件开出；建商机走 `createOpportunity`（D6，
`pipeline.opportunity.create`）。D7 无权读 D6，所以「哪些项目已经有续约」由页面从
D6 取来传进去——和 /routing 把客户区域喂给路由器是同一个形状。

**健康度只为幸存者推导**。推一次要读一遍里程碑和一遍分期，而工作区里项目远多于到期
续约；而「是否到期」不依赖健康度（只有 due 的 risk 依赖），所以便宜的一遍过全部，贵的
一遍只过筛下来的。

**页面上量出来两个缺陷，都是点出来的，不是测出来的**：

1. **到期列跟着结论走**。`daysToEnd` 从 due 结论上取，于是 PRJ-0006（已有续约、但
   还有 4 天到期）显示成「未填到期日」——页面对数据说了假话。到期日是项目的事实，
   与规则的结论无关。`daysUntilEnd` 因此提到规则层导出，**只留一份定义**，
   `assessRenewal` 也调它。
2. **「已创建」标记落在别的行上**。`useSaveAction` 一个组件一份状态，是给「一个面板
   一个保存按钮」设计的；表格里每行一个 `SaveRow`，于是全表共用同一对
   `saved`/`err`——点第 2 行成功，标记画在第 1 行；**第 3 行被拒，拒绝理由会印在其余
   每一行旁边**。新增 `SaveCell`（每行自持状态），/routing 一并改掉：它是同一个构造，
   只是那里行不会消失所以看不出来。

**实测**：智能仓储实施（已过期 29 天）与 POS 上线一期（还有 21 天）带按钮；点 POS
那行 → 该行变「已有续约商机在跑」按钮消失，**上一行保持干净**；调度平台年度订阅如实
显示「还有 4 天 / 已有续约商机在跑」；门店运营订阅服务显示缺到期日的理由。

1244 tests pass，43 表 lockstep，19 个增量全部授权到位。

**余下需裁定的只剩预测规则**（第 2 批第 5 项）：自动建议 vs 强制；覆盖人工选择时留不
留痕。

### 第 2 批 · 预测规则 —— 已交付（2026-08-31）

owner 裁定：**「只建议，逐单应用」**，且**分歧不存列、按需推导**。第 2 批清单五项至此清空。

**先摆出一个冲突，因为它决定这个模块能不能存在**。`forecast.ts` 从第 1 批起就写着
预测档位**与阶段刻意解耦**——「一个在 negotiate 却不肯承诺的销售会填『乐观』，而这个
分歧正是预测评审的全部内容」。所以「按阶段自动定档」会推翻规则层已写下的决定。
**建议**不会：它给那个判断提供了一个可供判断的对象，把只能靠一单一单翻看板才看得见的
分歧摆到一页上。这是裁定为「建议」而非「强制」之后才成立的模块。

**四条规则，除分档外全部是下调**。时间流逝不是进展：在 negotiate 坐了两个月的生意
比昨天刚到的更不可能落地，绝不会更可能。一条能把自己往上说的规则，最终会从不活动里
预测出信心来。

| 输入 | 作用 |
|------|------|
| 赢率（本人填的或阶段默认） | 定基础档：≥80 承诺，≥50 乐观，其余管道 |
| 没写预计成交日 | 封顶到管道——**承诺就是在说它落在哪个周期**，没写周期就没有可承诺的东西 |
| 预计成交日已过而生意还开着 | 封顶到管道。这是预测永远停在「承诺」的最常见方式：日期滑了，档位没滑，数字继续上报 |

### 导航系统性整改 · 导航就是board（2026-08-31）

owner：**「你还是没有处理彻底」**，并给了四条规格：今日裁决在每个域置顶；其下是域内各模块，

## 采纳真的把事情做了（`feat/accepting-does-the-thing`）

裁定：**「采纳当然要真实发生业务动作，不能是假的」**，以及**「执行走采纳者的权限

**这一批之前，整套裁决是表演。** 点「采纳」把提案行改成 `accepted`，商机**一动不动**；

**走域服务，绝不走 store。** `advanceStage` 带着阶段机、`opportunity_stage_event` 的

**用采纳者自己的权限，一行代码都不用知道那是哪个权限**——`ctx` 原样传下去，

所以能到达执行器的集合是**开放的**，只有白名单能给它封边界。不在名单上的一律按高风险
处理并拒绝执行，而不是猜。

## 采纳了但做不了，不叫失败（`feat/accepted-is-not-failed`）

上一批把「采纳」接上了真实执行，这一批处理它的直接后果：**队列里有三条提案，采纳
之后会被标成「失败」**——两条起草触达、一条信号升级为线索。

**`failed` 是终态，用错了词就等于毁掉一个刚做出的判断。** `failed` 应该是「试过、
被拒绝」；而一个产品根本没有 handler 的动作类型，**从来没有试过**。真实的状态是：
人同意了，机器不会做，需要人去做。于是这类提案停在 `accepted`，界面上标「需人工执行」，
不再送进执行器。`draft_outreach` 没有 handler 是**有意的**——发出去的消息收不回来。

**在点之前说，不是点完再说。** 行上有标记，确认框里有一句「这 N 条里有 M 条产品不会
自动执行」。`batchRisk` 多返回一个 `manualCount`，所以对话框说的话由数据算出来，不是
手写的。

**顺手修掉三个「同一件事两个答案」**：

1. `batchRisk` 里写着字面量 `< 60`，而自治规则读的是 `CONFIDENCE_FLOOR`。同一个数，
   两处定义——挪动门槛会改变「什么能无人执行」而不改变「对话框警告什么」。
2. 授权设置页的「高风险问我」文案自己数了一遍能自动执行的动作，**还写着「信号升级
   为线索」**——它 2026-09-01 就从清单里拿掉了。设置页和上面两寸的队列互相矛盾。
   现在这句名单由 `EXECUTABLE_ACTIONS` 现算现填，说不错。
3. 确认框把枚举原样打出来：中文界面上写着「动作类型：draft_outreach；作用对象：
   account」，而正下方的表格写的是「起草触达 / 客户」。表格早就修过一次，对话框漏了。
   这是 TD-010 反复出现的形状。

## 三条豁免名单条目的清算（`chore/retire-three-unwired`）

`KNOWN_UNWIRED` 的规矩是「下次复查时还没有调用方就删掉」。这一批把三条到期的走完，
**三条的结论各不相同——不逐条看是分不出来的**。

**`isTerminalStatus` 删了，连同 `TERMINAL_ACTION_STATUSES`。** 它的豁免理由写着
「常量本身有调用方，这个包装函数没有价值」——**前半句也是错的，两个都没有任何调用方**。
这个文件里每条规则都从**正面**判断状态（`=== "proposed"`、`!== "proposed"`、
`=== "accepted"`），因为每条规则只知道自己能从哪一个状态出发；没有一条需要「什么都不会
再发生的状态集合」。代码从来不问的概念，不值得钉一个定义。

**`capabilityLabel` 接上了，不是删掉。** 客户详情页在手搓一个更弱的版本——直接索引
label map，**跳过了 `isCapability`**——于是这个函数 docstring 里那条性质（未标注的历史
要保持可见地未标注，而不是被猜进某个能力）在唯一需要它的地方**没有被应用**。
「没有调用方」是症状，病因是**有一个调用方，它把这个函数重写了一遍**。

顺手补了一条守卫：label map 与 `CAPABILITIES` 必须**一一对应**（中英文两份都查）。
今天它们正好完全一致——**这正是现在断言它的理由，而不是等它们不一致之后**。两个方向
的失败形态不同：有能力没标签，会静悄悄地退化成「未标注」，看起来像数据缺失而不是字典
缺失；有标签没能力更糟，它会在能力退休之后继续为已经不被承认的历史命名。

**`daysSinceLastContact` 走的是「统一」那一支。** 它原来收一个**日期数组**——这就是它
几个月找不到调用方的原因：store 给出的 `lastContactAt` 是单个日期（Prisma 适配器里是
一个 MAX，归约根本不过网），所以每个读者手上都只有一个 `Date | null`。**为一个不存在的
调用方设计的形状，会一直闲着，同时它本该服务的那件事被到处内联重写**——判断规则里一次，
客户证据面板里一次。改成调用方真正持有的形状之后，两处内联都换成了它。

**`null` 不是 `0`，测试现在明写这一条**：「从没联系过」和「今天刚联系」是相反的事实，
一个把两者都返回 0 的函数，会让静默客户规则要么对一个从没打过电话的客户误报，要么对
它闭嘴。

## 预测准确率：那张只追加的表终于收账（`feat/forecast-accuracy`）

`forecast_snapshot` 从批次 1 起就被 revoke 掉 UPDATE，**整套不可变设计只为了一个读法**：
期末实际对期初快照。产品一直在付这个代价，而**没有任何界面问过这个问题**——而且
预测轨迹那一节的说明里，这句话从批次 1 就印在屏幕上：「快照只追加、不可修改——预测
准确率是期末实际对期初快照，少一个点就算不出来。」**一句关于不存在的数字的话。**

**先纠正我自己上一轮的判断。** 我把这条挂起，理由是「算到 owner 头上会激励低报」，
说它需要裁定。查了之后发现**根本不需要**：`submitForecastSnapshot` 把
`scopeType: "workspace"` 写死了，产品里没有第二处写快照，所以 owner 口径的快照
**根本不存在**，裁不裁都算不出来。我把阻塞点放大了。真正该裁的时点是**在这类数据
存在之前**，不是现在。

**期初快照是最早的那一条，这里自己排序**，不信任 store 的返回顺序。「oldest first」
是某一个适配器的文档属性；一旦它松动，这个数会以**没人看得出来的方式**错——一条在
季度快结束时才补的快照会让准确率永远接近满分，一个好看且毫无意义的数字。测试特意
按**倒序**种数据。

**实际值现算，不从最后一条快照读。** 快照是某人在那一天说的话，实际是这些商机现在
说的话。从末次快照读会让答案取决于「有没有人记得在期末点一下按钮」——于是
**「没人点」会悄悄变成「预测很准」**。

**实际值走 `planSnapshot`，不在这里另写一次 rollUp**，这样比值的两边由同一个定义
算出：同样的「先口径后周期」过滤，同样的「丢单不计入」规则。本地再写一个 rollUp 就是
实际值的第二个定义，两个过滤器任何一处一改就会漂。

**三种「没有数」是三种答案，都不是 0%**：
- 没有期初快照 → 「无期初快照，准确率算不出」。印 0% 等于把「没预测」报成「预测得差」。
- 期初承诺为零 → 「期初未承诺，无从对照」。没有分母。
- 读取失败 → 徽章根本不渲染。因为查询出错而显示 0% 比不显示更糟。

**周期没结束时它不叫准确率。** 同一个比值，季度中是「已兑现期初承诺的 N%」。叫它
准确率等于在第二周告诉一个团队它的预测准确率是 8%。

**又一次踩中「档位和权限是两个轴」。** 我第一版测试断言 `sales_rep` 读准确率会被
`permission_denied` 拒——**没有**。`pipeline.forecast.view` 要的是 feature
`pipeline.forecast` 加 permission `pipeline.read`，而每个销售角色都有 pipeline.read。
真正的门是**档位**（pro 以上）。这个安排是对的（卖的是「预测能力」，买了之后组内看
团队承诺不算特权），但**旁边 `forecastHistory` 的注释把这件事说反了**，写着「不能
预测的 rep 也不能审计预测」——已一并更正。

**浏览器里验了四个状态中的三个**（第四个只有单测覆盖，因为 demo 里没有哪个已结束
周期带着非零期初承诺）：
- 本期 → 「已兑现期初承诺的 84%」。**这个数本身就是判别性检查**：若误用末次快照的
  承诺（420 万）而非期初，270/420 会显示 64%。显示 84%，说明用的是期初。
- 2026Q2（已结束、无快照）→ 「无期初快照，准确率算不出」，不是 0%。
- 给 Q2 存一次空快照 → 「期初未承诺，无从对照」。

`KNOWN_UNWIRED` 现在剩 5 条，全部是「钉住一个别处会吵起来的定义」那一类。

## 准确率不是达成率（`fix/accuracy-is-not-attainment`）

裁定：**「territory / owner 口径的快照，应该容许」**。这一批是它的前置条件，不是它本身。

**上一批我把一个缺陷发到了界面上。** `accuracy()` 返回的是裸比值：承诺 1000、成交 3000
返回 3，于是页面上会写「**准确率 300%**」。那不是准确率——一份错了 200% 的预测不可能
是 300% 准。**而且这正是让低报有利可图的形状**：承诺 100、成交 1000，得分 1000%。

在工作区口径下这只是个怪现象。**一旦允许按 owner 存快照，它就变成一个「少承诺就更好看」
的个人数字**——而被打分的人，恰好也是给每个商机填预测类别、并按下快照按钮的人。**同一个
人批改自己的作业，两次。** 所以口径这件事不能先做。

**拆成两个数，两个名字：**

| | 含义 | 超额时 |
|---|---|---|
| 已兑现（`commitAttainment`） | 期末实际 / 期初承诺 | 大于 100%，本该如此 |
| 准确率（`forecastAccuracy`） | `1 - \|实际-承诺\|/承诺`，下限 0 | 也算错，且是大错 |

对称是**设计**，不是副作用：低报一半和超额一半都得 50%。**一个团队成交是承诺的三倍，
得到「已兑现 300%」和「准确率 0%」**——两句话都是真的：这个季度打得漂亮，这份预测什么
都没说。任何一个数单独拿出来都只讲了一半。

**下限取 0，不让它变负。** 实际超过承诺两倍之后公式转负，而「准确率 -140%」不是一句
帮得上任何人的话；错过头之后，每一档错法传达的是同一条信息。

**准确率只在周期结束后出现，已兑现一直在。** 季度中每份预测都「不准」，只因为季度还
没过完；那时候唯一诚实的说法是「已兑现期初承诺的 N%」。两个徽章并排显示，就是为了让
300% / 0% 这种组合能被完整读到。

**服务动词改名 `forecastScorecard`**——它现在返回两个数，叫 accuracy 就又只说了一半。

浏览器确认：本期仍是「已兑现期初承诺的 84%」，准确率徽章按预期不出现。**已结束周期
且期初承诺非零的两徽章形态在 demo 里无法触达**（没有哪个已结束周期带着非零期初承诺），
只有单测覆盖——这本身是 demo 的一个缺口，值得单独补。

1361 tests pass。

## 按区域、按人的预测口径（`feat/forecast-scopes`）

**领域层从批次 1 就支持三种口径**——`inScope`、`validateScope`、`countNewLogos`，

## 让 demo 有一个已经结束的季度（`feat/demo-settled-quarter`）

补上上一批自己点名的缺口：**产品的旗舰数字在 demo 里根本看不到**。准确率是期末实际
对期初快照，需要一个**已经结束**的周期；而这份 fixture 里每一笔成交都落在当前季度。
一个评审者能看到只追加的轨迹，却永远看不到这张表被保留下来的那个理由。

**两个数字必须不一样，否则等于没教。** 一个少完成的季度会把同一个数字报两遍
（已兑现 60%、准确率 60%）。所以上季度设成**打赢了、但预测得不准**：期初承诺 260 万，
实际成交 320 万 → **已兑现 123% / 准确率 77%**。这一对差值就是整个道理——季度可以既
被超额完成又被预测得很糟。

**日期怎么来的，试错了一遍才对。** demo 有一条守卫：**所有日期必须从 `DEMO_NOW` 推导**，
不许写死。我第一版写了 `new Date("2026-05-20")`，被它按住了——而且守卫是对的。三种做法
只有一种成立：

1. 写死季度和日期——守卫拒绝，而且钉死的季度配一个活的时钟，相对日期会错得跟它过期
   的程度一样多；
2. 从 `DEMO_NOW` 推「上一季度」——到十月，「上一季度」变成 2026Q3，而 `PERIOD` 仍然
   说自己是 2026Q3，**同一个季度会挂着两套快照**；
3. **从 `PERIOD` 推**——当前周期不管说自己是什么，已结束的那个就是它前面一个，填充它
   的商机在运行时按那个 range 定位。没有字面量，两个标签也不可能互相矛盾。

**成交要挑没有 Q3 成交的客户。** `countNewLogos` 记的是每个客户**有史以来第一次**成交；
给 acc_demo_1/2/5 补一笔 Q2 成交，会把它们的首胜挪出 Q3，**悄悄改掉当前季度的新客数**
——一次改 fixture 就动了一个没人在看的数字。

**最后一个快照要跟实盘对得上**，和 Q3 序列遵循同一条规矩：一个结束的季度就该是承诺
归零、成交填满（0 / 0 / 0 / 320 万）。

**浏览器确认**：`?period=2026Q2` 两个徽章并排——「已兑现期初承诺的 123%」「准确率 77%」，
三个点 04-08 / 05-18 / 06-28。当前季度不受影响：仍是 84%、没有准确率徽章、窗口里仍是
6 条商机（三笔 Q2 成交不会串进来）。

## 租户 / 工作区 / 席位 / 人员更替（2026-09-01 裁定）

owner 的裁定，分三条：**平台管「谁能用、有多少席位」；产品管「激活/停用、历史保留或
转交、以及产品自己的角色」；邀请给按钮，跳到平台执行。**

### 先确认：这个模型已经是现状，而且不是本仓定的

- **租户在工作区之上**，来自 OIDC token 的 `active_org`；两个智能体平面按
  tenant × workspace 计量。
- **工作区是订阅主体**，是**平台契约钉死的**：C2 授权信封的字面结构是
  `{ workspace_id, product, status, tier, limits, quota_pools }`，**里面没有 org_id**。
  `vx_provision.app_instance` 用平台自己的话标注：`workspace_id` 是
  *authoritative isolation key*，`tenant_id` 是 *rollup only*。
- **成员归属工作区**，而且是**首次登录惰性建行**（`seeMember`）——产品从不邀请任何人。

### 分析：产品侧不该验席位

三条理由，一条比一条硬：

1. **那个数不是独立事实。** `listWorkspaceMembers().length` 是「平台已经放行过的人数」。
   拿它比 `member.max` 再拒绝，是对平台已经回答过的问题给出第二个答案——而且答得更晚：
   产品只能在人**已经进门之后**才拒绝。
2. **`withinCap()` 是 fail-closed 的。** 今天所有工作区的 entitlement 都不带
   `member.max`，接上去等于把所有人锁死。
3. **`app/entitlement/` 是继承的 C2 契约面，在刚性区。** `withinCap` / `limitOf`
   没有调用方**不是产品死代码**，是模板给别的 metric 留的通用工具。不该为了「接线」动它，
   也不该把它列进未接线名单。

产品侧知道而平台不知道的只有一件事：**谁实际用过、持有哪些角色**。所以正确产出是
**对账视图**，不是门。

### 做的是人员生命周期，因为那里有个真的洞

三个测出来的事实：`member.status` 建行时永远写 `'active'`、**没有任何代码改过它**
（DDL 允许 `'inactive'`、列锁也授权了 UPDATE——schema 预留了停用，代码从没实现）；
**没有移除成员的动词**，只有一次一个的 `revokeRole`；名册**从不按 status 过滤**；
平台入站事件只有 `tenant.provisioned/deprovisioned`，**没有任何人员事件**。

**最尖锐的后果不是名单不好看**：平台之后若因为别的原因再次给同一个 sub 授权（换岗回来、
同名复用），他一登录，**旧角色原封不动地回来了**——首次登录的 owner bootstrap 刻意只跑
一次，不会介入。等于一次没人重新批准过的权限恢复。

所以 `deactivateMember` **收回全部角色**而不是记住它们，`reactivateMember` **什么都不
恢复**。回来是一次要重新做的决定。

**而这一行绝对不能删。** 所有归属列（`decided_by_sub`、`approved_by_sub`、
`actor_sub`）都把 sub 存成裸文本，删掉**不破任何外键**——它只是拿走了唯一一份
`usr_<uuid>` → 姓名的映射，让审计轨迹里的每一个签名变成没人认识的字符串。

**邀请是链接不是表单**，而且目的地**刻意不进 deeplink 契约**：`entitlement/deeplink.ts`
是继承的 C2 转化面，只有 `/subscribe` 一个出口、三个 intent，没有 invite。往里加等于在
产品仓自造平台标准。所以它是一个独立的环境变量，未配置时**不渲染按钮**——一个点了没反应
的按钮比没有按钮更糟。

### 两件本批没做完的，都已定范围

**转交（`owner_sub` 换人）没做**，但 schema 已经把答案写好了：可转交的是
`account` / `opportunity` / `lead` / `campaign` / `strategy_plan` / `territory`
（`owner_sub` 有 UPDATE 授权）；**不可转交**的是 `sales_target.owner_sub`（口径元组的
一部分，冻结）和 `forecast_snapshot.owner_sub`（只追加，压根没有 UPDATE）。这个划分本身
就是正确语义：**转交移动在办的盘，绝不动历史和指标**。转交跨三个域，每个域要有自己的
`reassignOwner` 动词，是下一批。

**产品角色（大区总监 / 总经理 / 销售经理）没加**，因为量出来一件必须先说的事：
`listPipeline` 过了门之后**返回整个工作区的商机**，`filter` 是界面传的、不是强制的。
**这个产品只有「你能做什么」一个轴，没有「你能看到哪些行」**，而大区总监的区别性特征
恰恰是数据范围。owner 裁定：**先加角色，数据范围下一批**——我会在角色目录文档里明写
这一点，不让它假装范围已经分开了。

## 转交：离职的人，他的盘去哪（`feat/owner-handover`）

第 2 步。停用管住了「他还能不能进来」，转交管住「他手上的活谁接」。

### 移什么、不移什么，`98_column_locks.sql` 早就写好了

不是我定的划分，是列锁定的——而且它就是语义本身：

| 移 | 不移 |
|---|---|
| `account` / `opportunity` / `lead`（`owner_sub` 有 UPDATE 授权） | `sales_target.owner_sub`——**口径元组的一部分，冻结** |
| | `forecast_snapshot.owner_sub`——**只追加，压根没有 UPDATE** |

**转交移动在办的盘，绝不动历史，也绝不动目标。** 给一个人定的目标就是给**那个人**的，
转手等于改写一个已经上报过的数字；他名下的快照是他当天说过的话。

同一条推理还排除了两样**授权允许、但语义不该动**的：

- **已成交/已丢单的商机**。赢单的 owner 是**谁打赢的**，那是一个已经结束的季度的功劳。
  `listPipeline` 不传 `includeClosed` 正好只给在办的。
- **已转化的线索**。`assignLead` 自己就拒绝，而且理由更好：**商机上已经有负责人了**，
  移动线索会让两者对「这是谁的单」各说各话。

**战役 / 计划 / 区域没有批量转交**，这是范围而非原则：它们的 owner 是管理者、每样就几条、
在各自页面上编辑。批量扫过去等于把一件该慎重做的事悄悄做了。

### 走域服务，一行一行

每次写入跑自己的门和自己的规则——和 copilot 执行器调 `advanceStage` 而不是自己写列
是同一个理由。比一条 bulk UPDATE 啰嗦，而**这正是要点**：一个跳过规则的转交，会是全产品
唯一一个这么干的写入方。

补了一个缺的动词：`reassignAccount`。store 从基线起就能写 `owner_sub`，**从来没有服务动词
暴露它**——所以客户的负责人只能在创建时定、之后再也改不了，「有人离职」在这个域里是个
没有答案的问题。

**接收人必须是在岗成员**，这个检查只能在编排层做：`local_authz` 在所有域之下，没有任何
域能回答「这个人还在不在」。把盘转给一个也已离职的人，比不转更糟——工作从对一个人不可见
变成对两个人都不可见。

从不给销售代表」——**不变量是后半句**，持有者名单会随目录增长，而两个新角色的存在理由

## 数据范围 A 批：模型与规则，刻意不上界面（`feat/data-scope-model`）

owner 裁定三条：范围是角色之后的下一批；**决定权给工作区管理员，不一定是总经理**；
**列表和按 id 取单条都收窄**。第三条把这件事从「组织分工」变成了「保密」。

### 一句话架构：范围是第二把隔离钥匙

`workspace_id` 不是在 service 里判的业务规则——它是**每个 store 调用都带的参数**，所以
没有任何动词能忘记它。范围是同一类陈述（这一行是给谁的），所以它走同一条路。

放在 service 层逐个动词判，意味着每个列表、每个按 id 取、以及将来每个新动词都要记得，
而**漏一个就是静默的保密漏洞**——这是本产品能发的最糟的一种缺陷，因为**人会相信这个设置**。

### 三条设计判断，每条都有它拒绝的替代方案

**范围挂在成员上，不是角色上。** 从角色推导（「大区总监看本区」）会把决定权放进
**产品级、封闭**的角色目录里；挂在成员上才够得着管理员，按工作区、按人。这正是裁定
「不一定是总经理」的直接后果——`admin.manage` 由 `sales_leader` **和 `sales_ops`** 持有。

**多对多，因为 `territory.owner_sub` 表达不了。** 那一列说的是「谁**负责**这个区」，
一区一人；而一个总监**管好几个区**。复用它会把「能看见这个区」和「对这个区负责」变成
同一件事——而管理员可能就是想让一个运营分析师看三个他一个都不负责的区。

**默认 `workspace`，而且这和 `agent_autonomy` 方向相反，值得写下来。** 自治默认最保守，
因为那是**给机器一份没人给过的权力**。范围相反——它是**从今天看得见的人手里拿走可见性**：
每个现存工作区会在上线那天早上悄悄少掉一堆行，而没有人要求过这个限制。**管理员主动收窄；
迁移不能替他收窄。**

### `own` 不等于「只看 owner_sub 是我的」

一个只看自己盘的销售，**他的商机挂在别人名下的客户上**。如果 `own` 严格按
`account.owner_sub = 我`，**他自己商机的详情页就打不开那个客户**——范围会对着它本该描述
的那个人执行保密。

所以 `own` = 我拥有的 + **我的活所挂的客户**。这也是「我的盘」的诚实读法。这个可达集
**每请求解析一次**，因为答案跨域（客户 / 商机 / 线索），而**没有任何 store 可以伸进另一个
store 的表**去算它。

### 层级是现成的，环不是

`territory.parent_id` 从基线就在——**分了父区就看得见子区**，否则层级是装饰，而且新增一个
子区的那天配置就错了。展开时按 `seen` 判重再下降：`parent_id` 是个裸自引用，**没有任何
约束阻止成环**，而一次数据订正造出的环会**挂住请求**而不是渲染错页面——挂住比渲染错更糟，
因为没有东西会报告它。

### 这一批没有任何界面，这是刻意的

**一个会漏的保密功能比没有这个功能更糟，因为它被相信。** 屏幕上写着「只看自己」而人还
看得见全部，就是撒谎。所以 A 批只落模型和规则；**管理员界面和强制一起在 B 批出现**，
屏幕和事实同时到场。

### B 批的范围（已量）

store 端口带上范围 → 列表与按 id 一起收窄（**19 处按 id 取记录的调用点由构造覆盖**，
不靠逐处记得）+ 行为守卫 + 管理员界面。

**一个已知的洞要在 B 批裁**：`lead` **没有 `territory_id`**，只能经
`account_id → account.region → territory.regions` 落区；**没有客户的线索落不到任何区域**。
区域档下它是「谁都看不见」还是「不受限」，是个产品裁定。

## 数据范围 B1 批：强制机制与守卫，仍不上界面（`feat/data-scope-enforcement`）

owner 两条指示：**未归属的线索按「可见」处理**；以及**参考传统 CRM 的逻辑，不要新创**。
第二条纠正了我设计里的一处发明——下面每一条都对应一个成熟产品里早就有的东西。

### 可见性 = 四条路径的并集，全部是既有模式

| 路径 | 传统 CRM 里的名字 | 为什么第一性原理设计会漏掉 |
|---|---|---|
| **归属** | owner-based sharing | 不会漏 |
| **父对象** | implicit sharing（客户控制其子记录） | 我原来的可达集是**反的**（从商机推客户）；传统是客户带子记录，两个方向都需要 |
| **层级** | role hierarchy | 本产品角色是**扁平的产品级目录**，所以由 `territory.parent_id` 顶上——覆盖父区即覆盖子区 |
| **队列** | lead queue | **owner 裁定**：没主人的记录对所有人可见 |

**是并集，不是交集。** 任何一条路够得着这一行就放行；要求两条会让日常工作消失——一个在
别人区域里拥有商机的销售会**看不见自己的单**。

**队列规则对所有对象生效，不只线索。** 论证与对象无关：**一行没有主人的记录不是别人的
私事**，藏起来意味着这份活永远没人认领。

### 强制点：包装器，因为编译器会替我们问

**范围是第二把隔离钥匙**，而 `workspace_id` 从来不是靠 service 记得去检查的——它是每个
store 调用的参数。所以范围走同一条路：**在发放 store 的地方包一层**。

关键在于**为什么是 `implements` 而不是 `...store` 展开**：包装类声明实现端口，所以
**端口后来新增的方法不写在这里就编译不过**——而写它的那一刻，作者被迫当场决定这个方法
返回的行要不要收窄。用展开语法的版本会**静默地把新方法透传出去且不收窄**，那是这个想法
行不通的那个版本。

**写这个文件时编译器当场抓了六个**：三个我猜错的方法名，三个我漏掉的。

**透传是判断，不是偷懒**，每一条都写明理由：写入路径（写之前必先读，而读已收窄）、
不带主人的行（阶段流水属于商机、快照属于工作区）、以及 `listUnreviewedClosed`——
**复盘欠账是工作区的义务**，把同事没复盘的丢单藏起来会让这张单子变错而不是变私密。

**按 id 取答 `null` 而不是拒绝**：每个调用方本来就把 null 变成 `not_found`，而这正是
对的答案——区分「不存在」和「不是你的」会**把范围变成一个存在性预言机**，这和跨工作区
读取给出同样答案是同一条推理。

**默认档零开销**：`workspace` 时包装器**根本不套**，返回的就是原对象（测试断言的是
**同一个对象**，不是等价）。

### 变异验证了两半

- 把一个已收窄的读改成透传 → 行为测试变红。
- 从包装器里删掉一个端口方法 → **编译不过**（2 个 tsc 错误）。

### 这一批仍然没有界面，而且**还没有接线**

机制建好、测好、变异验证过，但**还没有任何调用点使用它**——大约 30 处
`store: getXStore()` 需要换成带范围的版本，那是一次机械但必须仔细的清扫，配一条
「不许直接取未收窄 store」的守卫。

**在一个很长的会话末尾草率地接一个保密功能，是最不该做的事**——半接通的保密比不做更糟。
所以它留给下一批，和管理员界面一起。在那之前：默认档是 `workspace`，包装器不套，
**行为与今天完全一致，屏幕上也没有任何东西声称不是这样**。

## 数据范围 B2 批：接线、守卫、界面，三样一起（`feat/data-scope-wiring`）

承诺的做法：**屏幕和事实同时到场**。B1 建了机制不接线，因为半接通的保密比不做更糟；
这一批把三样一起落。

### 接线：范围放在 session 上，不是逐处记得

**64 处**调用点分布在 25 个文件里，手工扫一遍必漏。所以三个带主人的 store **挂在
session 上、已经收窄**：页面能拿到的就是收窄过的那个。

`getPipelineStore()` 仍然存在——**范围解析器自己按定义就需要未收窄的**（拿收窄过的去算
范围，等于让答案依赖它自己，不动点是「什么都看不见」），域内部调用方也在用。规则更窄：
**在 `(app)` 目录下，你能拿到的 store 就是 session 上的那三个。**

**`scoped-acquisition.test.ts` 守着这条**，因为**编译器抓不到**——两者返回同一个类型。
豁免两个文件，各写明理由，并且有一条断言**豁免项必须仍然名副其实**（避免名单腐烂）。
变异验证：把一个页面改回 `getPipelineStore()`，测试点名该文件。

**两个辅助模块顺带暴露了同一个坑**：`board.ts` 和 `domain/[key]/facts.ts` **没有 session**，
它们伸手去拿 store 会**静默拿到未收窄的**——而 board 是最糟的位置：它是第一屏，而且它做
汇总。现在两者的 context 都要求传入 `stores`。

### 解析放在 `(app)/lib`，因为分层就是这么定的

`own` 要问「我的活挂在哪些客户上」，跨客户/商机/线索三个域。**`authz` 在域之下、不能读
任何一个域**，所以这一步只能在这一侧做——而 session 本来就在这里读 entitlement 和 demo 种子。

**每请求一次，不是每查询一次**：把可达性 join 进每次读取，等于把跨域 join 塞进 store，
而那是分区规则唯一明令禁止的事。**未收窄档零成本**——`workspace` 在任何读取之前就返回。

### 界面：管理员定，而且「所有人都不受限」是屏幕上的事实

成员页新增「可见范围」列。**没有管理权限时仍然显示**（只读）——「大家都看得见全部」应该
是看得见的事实，不是被假设的默认，和授权面板的「尚未设置」同一个做法。

**不需要新权限**：`admin.member.scope` 映射到已有的 `admin.manage`，而它由 `sales_leader`
**和 `sales_ops`** 持有——这正是「主管理员，不一定是总经理」。谁能授予角色，谁就已经在
替同事做这一类决定了。

**客户端只发字符串和 id 列表，从不发 scope 对象**：客户端能拼的形状就是它能拼错的形状，
而这个形状决定可见性。服务端解析并校验两次。

### 浏览器里从头到尾验了

| **仅本人** | **0 条** | **全部 ¥0** |

## 区域档漏掉了父路径（`fix/territory-scope-parent-path`）

owner 问：「未归区」是不是公海的意思、应该所有人可见。**公海那部分早就对了**——
`owner_sub IS NULL` 在任何档位都可见，这正是传统 CRM 的公海/待领取。

但这一问让我去查了旁边那件事，**查出一个我自己发出去的真缺陷**（#137）：

```
owned lead     → false
owned account  → false      ← 一条都看不见
owned deal     → true
unowned (公海) → true
```

**区域档下，成员只看得见「本区商机」和「公海」。客户和线索一条都没有。**

原因很具体：`account` 和 `lead` **根本不带 territory 列**——线索要落到区域，只能经
`account_id → account.region → territory.regions`，也就是 incr/0017 为分派建的那套映射。
而我的规则只检查「这一行自己的区域」。所以一个切到本区的大区总监会看到有商机、
**零客户、零线索**——那不是收窄，是坏掉的屏幕。

**这个洞在 #138 的浏览器验收里没被抓到**，因为我只看了管道页（商机带 territory_id，
工作正常）。**没有人去看客户列表**。

### 修法就是传统 CRM 的那条：客户是父对象

区域档现在也带 `accountIds`——本区覆盖的那些客户。可见性变成两条独立路径，任一成立即可：

- 这一行**自己的**区域（商机有）
- 它**客户的**区域（客户和线索只有这条）

区域到 region 的匹配**复用 `coveringTerritories`**，即分派用的同一条规则。在这里另写一遍，
等于让产品对「哪个区域覆盖这个客户」有两个答案，而**分派会把线索派给一个看不见它的人**。

### 一条边界，和公海分开

**有主人、但落不进任何区域的行，仍然不可见。** 那不是公海——**有人拿着它**，只是它的客户
没填 region。因为数据不全就把它给所有人看，是**披着便利外衣的泄露**。测试把这条边界钉住了。

## 未分区与 owner 兜底（`feat/territory-fallback-and-unplaced`）

owner 裁定：**「默认一个未分区，或跟着 fallback 销售所有人区域」**。两半都做了，
而**顺序是关键**——兜底先解决掉能解决的，剩下的才叫未分区。

### 三条规则，按这个次序

1. **归到自己区域的**：这一行自己的区域，或它客户所在的区域。
2. **已经归到别处的 → 不可见。** 这一条必须挡在下面两条前面，否则它们就不是兜底了。
3. **兜底 + 未分区**（只对「哪儿都没归」的行生效）：
   - 属主是本区负责人 → 归本区（`territory.owner_sub`，一区一人）
   - 剩下的 → **未分区，所有区域成员可见**

**第 2 条是我第一版写错的地方，而且是量出来的，不是想出来的。** 我把 owner 兜底放在了
「已归属别处」判断之前，实际含义变成了**「本区负责人的整本盘，无论归在哪个区，都对本区
可见」**。demo 里当场从 3 个客户涨到 6 个——**而这不是那条注释说的意思**。修正后回到 3。

### 这是一次刻意的放宽，说清楚

**未分区的行是有主人的。** 让它对所有区域成员可见，等于**一个填漏了 region 的客户，
把它名下的活扩散到了属主的线之外**。裁定接受这个代价，理由是另一头更糟：那些活**谁都
看不见**——连它所在区域的经理都看不见，因为它没有区域。

**它不是公海。** 公海是**没有主人**的行，任何档位可见、任何人可领。未分区是**有人拿着、
但没人归档**的行。把两者混同，等于把别人名下的活丢进一个大家以为可以领的池子。

### demo 里演示不了，如实说

查了 demo 的覆盖情况：**七个客户的 region 全部被某个区域覆盖**
（East China 覆盖 华东/华中，North 覆盖 华北/西北，South 覆盖 华南/西南）。所以
`unplacedAccountIds` **是空的**，未分区规则没有任何数据可作用——修正后的数字（3 客户 /
7 商机）与加这条规则之前**完全一致**。

**规则实现了，但 demo 演示不了它。** 这和早些时候「demo 没有已结束的季度」是同一类缺口，
下一批补一个未归区的客户进去，让这个案例能被看见。

### 顺带一条测量结论，值得记

未分区放宽的**实际影响完全取决于区域覆盖是否完整**。这个 demo 覆盖是满的，所以放宽为零；
一个区域只覆盖了一半 region 的工作区，会发现区域档几乎不收窄。**这是数据质量依赖，不是
规则缺陷**——但配置的人应该知道。

## demo 补上未归区案例（`feat/demo-unplaced-account`）

上一批自己点名的缺口:**未分区规则在代码里是真的,在屏幕上根本看不见**——demo 七个客户的
region 全部被某个区域覆盖,`unplacedAccountIds` 恒为空。规则再对,没人能看见它做了什么,

**「时刻需要想着智能化、大模型怎么接入怎么用,这才是我们产品的核心竞争力」**。

第二条**纠正了我写到一半的东西**。我原本把「行业推不出来」当成终点——报出来、留空、
不猜。那是保守,不是设计:**推不出来正是模型该上场的地方**。

### 关键发现:脊梁早就建好了,缺的只有一块

`runCopilotTurn` 已经是 gate → session → 模型+工具 → 提案;`PROPOSE_ACTION_TOOL` 让模型
提出 `{action_type, subject_id, payload, rationale, confidence}`,而 **`action_type` 是
自由文本**。所以模型**今天就能**提出「把这家客户的行业填成制造」。

缺的只有一样:**执行器不认识这个动作类型**。今天采纳它会被诚实地标成
`not_executable_type`——这正是 #123 建 `EXECUTABLE_ACTIONS` 时留下的扩展点。

补上 `fill_account_field` 一个 handler,整条链就通了:**模型建议 → 进同一个待裁决队列 →
人点采纳 → 用采纳者自己的权限写入**。**一键赋值 = 那个已经存在的采纳按钮。**

**所以 ADR-003 不需要第二套机制。** 一个直接写入的「智能填充」会是助手改数据的第二条
路径,而且是唯一一条没有签字的。

### 两种缺口,两个回答者,分开是有代价原因的

| | 谁答 | 为什么不能反过来 |
|---|---|---|
| **数据已经知道** | 一次 join | 拿这个去问模型是**缺陷不是功能**:付钱、等待,换来一个数据库已经知道的答案,而且确定性更低 |
| **模型才知道** | 一次 turn | schema 推不出一家公司是做什么的。这是关于世界的事实,也正是产品赚钱的地方 |

规则做免费那半、**点名**另一半(`forModel`),两者分开计数——所以页面可以不花一次 turn
就把数据知道的都摆出来,而**问模型是一次有计数的显式行为**,不是因为有人打开了记录就发生。

**有两样刻意不问模型**:「东北该由哪个区域覆盖」是关于这家公司**怎么组织销售**的决定,
问了只会得到一个自信的、模型不可能拥有的答案;细分市场由管理员写下的 criteria 决定,
让模型去猜等于覆盖掉公司自己拥有的规则。

### 写入这一侧的三道闸

`payload` 是**模型写的 JSON**,所以每一部分都检查而不是信任:subject 必须真的是客户;
字段必须在四个之内(模型写 `tier` 会够到一个有自己规则和自己页面的商业定级);**空值拒绝
而不是写成空白**——「帮我填」把字段清空是这个请求的反面,而模型对答不上来的行业返回空串
是完全预期的事。

列锁本来也会拦住范围外的列,但**数据库上的拒绝是一个 500,不是一个答案**。

### 守卫抓了四次,每次都对

`reachable-codes`(两个新 code 要句子)、`wired`(规则没有调用方——**我因此把界面一起做了
而不是加豁免**)、`single-import`、以及 CJK containment 又一次抓住组件里的顿号。

**其中一次是我犯的老错**:句子用 plain replace 插进了第一个匹配的字典(MEMBER_ERROR)而不是
PROPOSAL_ERROR。这次改成按块定位。

### demo 演示到哪一步

给 `acc_demo_8` 留空了行业——**这就是「首次填写」那个案例**:有人只敲了个公司名。页面上
现在同时出现「行业:数据里推不出来,交给助手」和未分区警告。

**「数据能推出来」那半在 demo 里演示不了**,原因很具体:**三个演示区域每个都覆盖两个
region**(华东/华中、华北/西北、华南/西南),所以「按商机所在区域推出客户区域」这条永远
落不到唯一解——规则**刻意拒绝在两个候选之间挑**,那是把抛硬币写进客户档案。要演示它需要
一个单 region 的区域,是下一个 demo 缺口。

## 让助手真的去查（`feat/ask-assistant-to-complete`）

这条链最后缺的一段。模型**早就能**提出补齐建议,队列**早就能**装它,自 #142 起采纳**早就能**
写入 —— 缺的是**没有任何东西去问**。这一批就是那个按钮。

### 问题在服务端拼,不由客户端发,这一条同时是两件事

**信任边界**:客户端能发的 prompt,就是任何人都能拿这个工作区的计费额度去问模型的任何
问题 —— Atlas 按请求计费。

**质量控制**:问题里点名了公司、点名了缺哪几个字段、**点名了 `action_type` 该写什么**
（`action_type` 是自由文本,模型不说就会自己发明一个,而发明出来的类型会被执行器以
`not_executable_type` 拒绝 —— 读起来像助手失败,其实是措辞问题）。

**而且显式允许弃权**:「不认识这家公司就说不知道,那个字段不要提案」。一个模型在没被拦住
时会给出一个看起来很像那么回事的行业,而**错的行业会悄悄决定细分市场,细分市场决定团队
follow 的作战剧本**。「我不知道」必须是被许可的答案,否则它不会被给出。

**没有缺口就不花这次 turn** —— 一个无论有没有问题都要花钱的按钮,是人会学着躲开的按钮。

**这次 turn 一律 `autopilotActive: false`,不管工作区什么档位**:这是唯一一次模型被问的是
它可能压根不知道的事实,而那正是无人看管的写入最糟的时候。

### 浏览器点下去,抓到一个真的缺陷

第一次点击显示的是 **`atlas_ATLAS_NOT_CONFIGURED`** —— 一个裸 code,正是 TD-010。

**而 `reachable-codes` 守卫对它是结构性失明的**:`atlas_${e.code}` 是**运行时拼出来的**,
来自平台自己的错误词表,这个仓库读自己的代码根本枚举不出这个集合。

修法不是给新界面加一份翻译 —— `copilot-chat.tsx` **早就有一份**,再写一份就会漂,而下一次
Atlas 改名时,第二个界面的读者又会看到裸 code。所以**抽成一份共享映射**,两处共用,
并且用**前缀兜底**:我们无法为不属于自己的 code 逐条承诺句子,**但可以承诺永远不裸打印
一个**。

修完之后同一个按钮显示:**「模型平面尚未接入（需要运营侧完成注册与授权）」** —— 一句
点名了真实补救动作的话。

### 顺带更正一条已经过期的注释

`ask-action.ts` 写着「autopilot 是一个还不存在的工作区设置」—— incr/0020 之后它存在了。
现在仍然传 false,但**理由变了**:`autopilotActive` 塑造的是**提示词告诉模型它有什么权限**,
而真正决定一条提案会不会自己跑的四道 yes 在 `execute()` 里、在采纳时、对着存下来的档位判。
告诉模型「你可以执行」不会让它真的可以,**只会让它对着读答案的人错误描述自己的权力**。

## 补上 X-3 的审计记录表（TD-018，`fix/audit-event-x3`）

自陈文档里改判过一次：「X-3 与 C3 用量信封冲突」是范围划错，真正的差距是本仓
**从未建过**通则要求的那张审计记录表。这一批补的就是那张表，接进两个 X-3 点名
的面：管理面写操作（`authz/admin.ts` 的五个动词）与消费面调用（一次 copilot
turn，含流式与非流式两条路径）。

### 一张表服务两个面，不隶属任一个

审计事件不属于 `local_authz`，也不属于 `local_agent` ——放进任一个都会让另一个
面的写看起来是它的依赖。新开一个 schema，`local_audit`，和 `local_authz` /
`local_usage` 平级。追加写，不可编辑：一张能改的审计表不是审计表。

### outcome 必须区分被拒和成功，不是只记落地的写

`authz/admin.ts` 原来的每个动词都是「gate 检查 → 早退或继续 → 写」。X-3 要求
的是「谁试过、被拒了」也要留痕，所以五个动词的每一条早退路径都补了一次
`audit(...)`，outcome 分三档：`denied`（gate 没过）、`error`（gate 过了但域
校验失败，如 `last_admin` / `not_found`）、`success`。三条区分不是装饰——
一张只记成功的表答不出「谁试过被拒」，而那是审计存在的一半理由。

### costAmount 需要 Atlas 的 token 用量，而这个数字此前被原地丢弃

`turn.ts` 的每次 `atlasClient.chat()` 都带 `usage.totalTokens`，但 `TurnResult`
从没往上传过——`turn-service.ts` 拿到答案就把它扔了。补一个 `totalTokens`
累加器，覆盖主循环的每一轮**和**截断分支那次额外调用（写了两个测试专门证明
截断分支的那次调用被算了进去，不是漏计）。流式路径同理，从 `done` 帧的
`usage` 里取，取不到就报「没有花费」而不是编一个零。

### `actorConsole` 不是新身份模型，是既有字段的改名

通则讲得很直接：这个字段是铸造 OBO 换票的工作台 RP。本仓没有 OBO 中继路径，
每一笔写都是自产的，所以统一填一个进程常量 `"yucer"`；`NULL` 留给不属于任何
控制台的后台通道，本仓目前没有这类写落在这张表里。

### 流式路径原本会被漏掉

非流式 turn（`turn-service.ts`）走完之后才发现还有 `streaming-turn.ts` 这条
独立的消费面路径——它直接调 `atlasClient.chatStream()`，不经过 `runTurn`，
如果只接前者，流式对话的每一次 Atlas 调用都不会留痕。两条路径都接了。

DDL：`incr/0023_audit_event.sql`，新 schema + 表 + 索引，同文件内完成
`GRANT SELECT, INSERT`（`check-incr-grants.mjs` 卡的就是这一条）。Prisma 镜像、
`column-locks.ts` 的 `APPEND_ONLY_TABLES` 同步更新。

## 批量补齐（`feat/batch-completeness`）

PR #142 之后留下的两个后续之一：把「这份客户资料还缺什么」的规则跑遍全部客户，
能一键赋值的批量提案；不能推的仍按公司走单条「让助手去查」。这一批做的是前半。

### 只做数据能推出来的那半，理由和单条页一样

`workspaceCompleteness()` 直接复用 `accountGaps()` / `fillable()`，只是换成扫全部
客户。**不跑 `forModel` 的那半**——批量再加一次模型调用，就是把「问助手」变成
「每个客户都问一次」，一次点击花掉全工作区规模的 Atlas 用量，正是 `completeness.ts`
自己点名要避免的那种浪费，只是被批量放大了。模型半仍然是逐客户、显式点击的
「让助手去查」，这次没有碰它。

### 一次三个域查询，不是 N 次

`accountCompleteness()`（单客户版）每次调用都重新拉一遍 territories 和
segments——对一条记录是对的，但如果批量版对每个客户都这么做，3 次查询会变成
N+2 次。`workspaceCompleteness()` 改成一次性拉全部客户、全部商机、全部区域、
全部细分市场，按 accountId 分组后在内存里跑规则。

### 写入路径和单条页完全一样，只是循环了

没有新建「批量写」的存储层方法。`applyBatchFill()` 逐条调用
`fillAccountField()`——同一个权限检查、同一个字段白名单，只是循环 N 次。批量
选中五十行不会变成一条 SQL 语句；它变成五十次各自受权限检查的写。选择只是给
读者的界面便利，不是绕过检查的捷径。

### 守卫抓到一个真的漏洞：批量失败原因差点裸打印

组件第一版只把 `applied`/`failed` 的**计数**显示出来，从不渲染每条失败的
**原因**——`reachable-codes.test.ts` 当场标红：`applyBatchFill` 绑定的组件
链条里没有任何一处渲染错误字典，是 TD-010 那类缺陷的入口。补了
`BATCH_COMPLETE_ERROR` 字典和渲染点，取第一条失败原因显示，和
`proposal-queue.tsx` 批量拒绝时的做法一致。

### demo 数据现状：这条页面目前是空的，而这是对的

三个演示区域仍然各覆盖两个 region，region 推导永远拿不到唯一解；
segmentCode/ownerSub 在种子里从未留空；行业留空的东北重工集团（acc_demo_8）
是唯一一个缺口，但行业是 `forModel`，本来就不进这张表。所以 `/account/complete`
在当前 demo 数据下渲染的是空状态——用浏览器验证过这条路径本身正确（标题、
说明、空状态文案全对，控制台没有与本功能相关的报错），能看见非空表格需要先
补单 region 的演示区域，那是之前提过、还没做的另一个后续。

1494 tests pass（新增 8 条），六项守卫全绿，生产构建通过，浏览器验证空状态路径。

## field-prisma-store.ts 从 46.88% 补到有真实覆盖（`test/field-prisma-store-coverage`）

上一轮"构建测试并检查覆盖率"报告里，`field-prisma-store.ts` 只有 46.88% 行覆盖，

### 数字低的真实原因：DDL 测了，TRANSLATION 层从没测过

`field-evidence.db.test.ts` 已经很扎实地测了 `yucer_field` 三张表的 CHECK、
GRANT、REVOKE——但那份文件从头到尾用的是裸 SQL，从没有 import 过

interaction 和它的 participants 是不是真的绑在一个单元里）、
`lastContactByContact` 那个在 JS 里做 MAX 聚合的两次查询、`listInteractions`/
`listCommitments` 的过滤与排序、`applyClosure` 的局部 patch——只在内存镜像
（`InMemoryFieldStore`）上跑过。两个镜像互相一致，说明不了哪个是对的，这正是
`column-locks.test.ts` 和 `adapters-prisma.db.test.ts` 已经吸取过的教训，这次
是同一课在没被推广到的一个文件上重演。

### 真的起了一个本地 Postgres 跑这些测试，不是只信 type-check

之前几批的"验证"到 `pnpm run type-check` 通过就停了，这次不是——`brew install
postgresql@18`，起服务，按 `ci.yml` 的 `db-contract` job 同样的顺序（00 →
97 → 98 → incr/*）把全部 DDL 灌进一个全新库，然后带着真实 `DATABASE_URL` 跑
这 11 条新测试和全部 63 条 `*.db.test.ts`。

**这一步真的抓到了两个缺陷——都在我自己写的测试夹具里，不在被测代码里**：

1. 断言"只剩 `dueSoon` 是 open"时忘了 `listCommitments` 的 `status` 过滤是
   **按工作区**，不是按客户——同工作区另一个客户底下那条待还的承诺理所当然
   也会出现。断言写窄了，不是代码错了。
2. 补第一条时顺手把"另一个客户"的承诺到期日设在了过去，让它意外也满足
   `overdueAt` 的条件，把上一条 `overdueOnly` 断言也带错了。

两条都只有让真实的 Postgres 真的跑一遍查询才会暴露——纯靠读代码或信任
in-memory 镜像不会发现，因为 in-memory 版本的过滤逻辑抄的也是同一份错误

### 编写测试过程中暴露的两个真实生产缺陷（都在 `planning/prisma-store.ts`）

真实数据库能抓到内存镜像抓不到的缺陷，原因是两个镜像做了同一个（这次恰好
是错的）假设，互相印证不出对错——这一课 `field-prisma-store.ts` 那批已经吸取
过，这次在另一个文件上又中了一次：

1. **`createTarget()` 从未把 `status` 写进 `data` 对象**，新建的 target
   无论请求什么状态都落在数据库默认值 `draft`。目前唯一的真实调用方
   `planTargetCreation()` 恰好总是传 `draft`，所以是潜伏的，还没炸。已修：
   补上 `status: target.status`。
2. **`upsertTerritory()` 完全没有写 `regions`**（更严重）——`update` 对象
   字面量里根本没有这个键。根因更深一层：`prisma/schema.prisma` 的
   `Territory` model 自 incr/0017 把 `regions` 加进 DDL 以来就从未跟着改，
   Prisma 客户端里这个字段压根不存在，写请求根本无法到达这一列。这意味着
   **在任何真实的 Prisma 后端部署里，通过管理/服务流程配置的辖区区域从未
   真正写入过**，本仓早前建的按区域路由线索、按区域推导数据可见范围两个
   功能因此静默失效。已修：`prisma-store.ts` 补写入 `regions: input.regions`
   + `schema.prisma` 补 `regions Json @default("[]") @db.JsonB` 字段 +
   重新 `prisma generate`。

`check-data-architecture.mjs` 为什么没拦住第 2 条：它自己的文档字符串写明
只做表级 DDL/Prisma 锁步检查，不做列级——这是已知且记录在案的能力边界，不是
它的 bug。列锁 mirror（`column-locks.ts`）恰好早就正确写了
`"yucer_gtm.territory"` 需要 `regions`，只是应用代码和 Prisma schema 两处都
没跟上，说明这是三条各自独立、互不覆盖的检查线：DDL 与 Prisma schema 的表级
核对、列锁 mirror 与 DDL 真值的核对、以及（这次缺失的）DDL 与 Prisma schema
的列级核对。详见 `60-operations/00-index.md` TD-019。

`pnpm test`（无 `DATABASE_URL`）：1601 个 test() 声明，1444 pass、157 skipped
（157 恰好等于全部 `*.db.test.ts` 的自跳过计数，非本批引入的失败）。带真实
`DATABASE_URL` 单独跑全部 `*.db.test.ts`：157 条全部 pass，其中本批新增 94 条。
`tsc --noEmit` 通过，六项守卫全绿，生产构建通过。

### 第三个同类生产缺陷：`agent_action.capability` 从未被写入

与 TD-019 的两个是同一个病，第三次出现，而且这次**修不回来**：

- `NewProposal.capability` 字段存在，注释写着「ADR-015. Set at creation; the
  column has no UPDATE grant」；
- 内存镜像 `store.ts:301` **写了** `capability: p.capability ?? null`；
- `toAction()` **读**这个字段；
- 两个 UI（`theatre-plan.tsx`、`pipeline/[id]/page.tsx`）按它给提案分组；
- 而 `PrismaCopilotStore.createProposals()` 的 `data` 字面量里**根本没有这个键**。

incr/0008 明确不授予 `UPDATE`（「capability joins payload / rationale /
confidence in the frozen set」），所以插入时丢掉的值**此后永远补不上**——这一行
在数据库里就是永久无标签。目前唯一的真实调用方（逾期承诺扫描 `proposalFor()`）
不传 capability，所以是潜伏的、还没炸；但任何一个开始传的生产者，都会在测试里
（内存镜像）正常、在生产中（Prisma）静默失效。已修。

**两个镜像互相矛盾时，先问哪个符合契约**，而不是让它们互相印证——这正是内存镜像
与 Prisma 适配器两边都做同一个（错的）假设时抓不到的那类缺陷的反面：这次两边
假设不同，差异本身就是线索。

### scoped-stores：形状不同，风险最高

`scoped-stores.ts` 是数据可见范围的边界，文件自己的注释写着「a forgotten one is
a SILENT confidentiality hole... because the setting is believed」。它原本已有
一条**结构性**测试，断言 wrapper 的源码**提到**了每个端口方法——但 26 个
pass-through 箭头函数从未被**调用**过。

两者的差距是一整类真实缺陷：**一个转发到错误内层方法的 pass-through**（例如
`listContacts` 实际调用 `listRelations`）签名兼容、编译通过、名字也确实出现在
源码里，原有的结构性测试完全看不见。

新增的测试用一个 Proxy 记录内层被调用的方法名，对每个端口的**每一个**方法断言
「wrapper.X 只调用了 inner.X、参数逐字转发、pass-through 原样返回内层结果」——
方法列表从端口源码解析而来，不在测试里硬编码，所以以后新增的方法自动被问到。

**按本仓「让守卫真的失败一次」的规矩验证过**：把 `listContacts` 故意改成转发
`listRelations`，新测试以
`AccountStore.listContacts called listRelations on the inner store` 精确失败，
而原有的结构性测试全程绿着（`listContacts` 这个名字确实还在源码里）。改回后
11 条全绿。
