- `authz/`：19 权限 / 7 角色的**类型化镜像**，`catalog.test.ts` 逐条解析

### 一轮六视角审计（2026-08-16）

对全仓做了一次六视角审计（产品完整性 / 门控正确性 / 数据完整性 / 智能体两平面 /
测试缺口 / 界面质量），36 条原始发现，经**独立质疑者对抗验证**后确认 4 条 critical，
4 条被驳回（这正是验证阶段的价值——半数没扛住敌意复读）。四条已全部关闭：

| 发现 | 处置 |
|------|------|
| D6 管道完全只读，无人能推进/定价/关闭商机 | PR #22 |
| 无角色管理界面，工作区只能有一个可用的人 | PR #23 |
| 放弃 SSE 流只 `releaseLock()` 不取消，上游继续生成并计费 | PR #24 |
| `platform/s2s.ts` 零测试，ADR-004 的计费主体不变量无人守 | PR #25 |

PR #24 顺带发现超时其实什么都没管住：`timeoutMs` 在响应 resolve 时清除，而那是
**响应头到达**的时刻，两个客户端的 body 读取都是无界的。PR #25 在写测试的过程中发现
`cacheKey()` 用 `"|"` 拼接**不是单射的**（`tenant "a|b"+ws "c"` 与 `tenant "a"+ws "b|c"`
同键），一个工作区铸出的凭证会被交给另一个——测试第一次跑就红。

PR #26 处理审计尾部中**不涉及商业判断**的部分：账户详情页直接持有 store 句柄（隐藏
导航链接不是访问控制，直接输 URL 照样返回客户档案与联系人名单）；`execute()` 在门之前
读行，使未授权者能通过 `not_found` 与 `permission_denied` 的差异**枚举有效提案 id**。

### 对同一轮自身产出的复审（PR #31）

上述十个 PR 是在一次连续作业里写的，只有作者本人看过。于是把同一套机器（五视角 +
独立质疑者）对准 `e65a7ea..HEAD` 这个范围本身：27 条原始发现，**4 条确认、4 条驳回，
四条确认的全部是这一轮新引入的**。

| 缺陷 | 性质 |
|------|------|
| `planStageChange` 不移动 `forecast_category` | 赢单后仍留在 `commit` 桶，`rollUp()` 把**已赢收入算成未到手承诺**，`closedAmount` 为空——同一笔钱报两次。且该行处于 `planCategoryChange` 双向拒绝的状态，后续任何编辑都修不回来 |
| 预测类别写在编辑门之下 | 类别属 `pipeline.forecast`（pro + 专有权限，规格文档明写），却被折进 `pipeline.opportunity.update`（免费档）。反向荒谬：规格指定的 `sales_ops` 反而调不到该函数 |
| 已关闭商机保存必失败 | 上一条的后果，表单每次提交全部字段，把过期的桶带回去 |
| 拒绝的流丢失错误信封 | **修 #24 泄漏时引入**：`abort()` 放在读 body 之前，`GRANT_DENIED`/`QUOTA_EXCEEDED`/`RATE_LIMITED` 全塌缩成裸 `"403"` |

**这一轮的方法论结论，值得记住：**

- **审计擅长发现「没接上的东西」，不擅长发现「接错了的东西」。** 四条 critical 都是
  「后端完整但界面没接」，而 #31 的四条全是「接了但接错」——后者要靠动手复算、以及
  让测试去撞才会暴露。
- **一个测试的价值取决于它断言的是什么，不是它有多少行。** 往返测试断言了收关后的
  状态、赢率、`closed_at`、金额，唯独漏了类别，于是一路绿着放行了最严重的一条。
- **修复本身会制造缺陷。** #24 修泄漏时弄坏了诊断能力，而 #24 自带的测试因为假 body
  没接到 `init.signal` 上而抓不到。新测试留下之前先把修复回滚验证它确实变红——
  **一个不会为它守护的 bug 变红的测试，不是测试**。

### 界面层的两条纪律

**没有任何页面在本地重算商业结论。** 按钮的可见性一律来自服务端动作会重跑的同一个
`can()` 门。信号页曾经用 `["pro","business","enterprise"].includes(tier)` 算过一次，
上线前被抓掉——那是产品在本地推导商业结论，套餐一改就漂移。

**全部非 ASCII 文本集中在两个纯数据文件**：`(app)/lib/messages.ts`（界面文案）与
`domains/shared/demo-fixtures.ts`（演示数据的展示文本）。两者都不含逻辑，`app/` 下
其余源文件全部 ASCII，可机器穷举（TD-002）。

## 批次 3.5 - 证据面与两条平台面（PR #36-#46）

批次 3 之后追加的一轮，起因是 owner 的重新定位：**把原来散在各销售人员脑子里的信息

| #46 | 决策链接入交互参与人；逾期承诺扫描作业 |

**一期带杀死判据**：六周窗口，按 `/admin/adoption` 的覆盖率读数决定二期（主张与判断层）
建不建。判据的两个决定值得记住：

- **测覆盖率，不测数量。** 一个人往一条商机上倒二十条笔记，「每周交互数」会很好看，
  而另外十九条商机全黑——由此得出的「习惯形成了」在唯一要紧的意义上是假的。
- **刻意不按人拆分，并写在界面上。** 一旦能当绩效看，大家就会为它记录，它就不再测量
  它要测的东西。

窗口未满一律返回「观察期未满」而非失败：**一个能提前失败的判据，一定会被提前引用。**

#### 6a-1 已交付（2026-08-26）

`pipeline/forecast-action.ts` + `components/submit-forecast.tsx`，控件落在**轨迹区**

按钮放在总额旁边会暗示它保存那个数字，放在序列上说的才是它做的事——给序列加一个点。

作用域只做 `workspace`：另外两个（territory / owner）需要选择器，而选择器不存在——
提供一个只能产出一个值的下拉，是一个对自己撒谎的控件。

**实测验收**：轨迹末点从种子数据的 08-01 变成当天；连点两次，点数 14 → 15，
两行同日——**追加而非改写**，与 `forecast_snapshot` 的 UPDATE 已 REVOKE 一致。

#### 6b-1b 已交付（2026-08-26）

规则（`lib/pricing.ts` 追加三个 plan 函数）、端口写方法、内存实现、
**`prisma-store.ts`——本域的第一个适配器**、三条写服务、5 条新测试。

**权限分离是这一项的核心，也是唯一被反证过的断言。**
`catalog.write` 维护卖什么，`catalog.price` 决定不再往下让的那条线。

一个编目录的人顺手就能移动底价的产品，是一个每笔折扣都自我批准的产品。

**价格是追加的，不是就地改的。** `effective_at` 属于唯一键，新时点的新价格是新行——
这正是「价目**书**」区别于「价目」的地方：被取代的那一行仍可读，它解释了今天这个
数字是怎么来的。`incr/0010` 给 list/floor 的 UPDATE 授权是为了改刚写错的那一行，
不是为了改写历史，端口刻意不暴露它。

**三条规则各自挡住一件事**：产品必须有**单位**（没有单位的「10 × 1000」是十个坐席、

底价**不得高于标价**（那会让每一笔都需要签字，等于没有底价）——
但底价**等于**标价是允许的，「此产品不打折」是一个立场，不是笔误。

会留下一个空方案，而空方案正是规则层拒绝任何人创建的东西。

#### 6b-3 已交付（2026-08-26）

`replaceOpportunityLines` 落在 **pipeline** 而不是 catalog：行项住在
`yucer_pipeline`,按 ADR-001 归 D6——定一笔交易的价属于
`pipeline.opportunity.update`,目录只是它读的维度。

**ADR-014 §2 就是这个函数的全部**：行项存在时行项是权威，
`opportunity.amount` 等于它们之和。这条约束写在服务层而不是 DDL——
它跨行（一个 header 对多条 line）,CHECK 表达不了，触发器会把业务规则藏进数据库。
于是服务在**写行项的同一次调用里**重算 header，而且这是**唯一**允许改 amount 的路径。

**`needsApproval` 由服务算，永不接受调用方传入。** 客户端能设的标志就是客户端能清的
标志，而这一个决定一笔折扣要不要送到人面前。逐行按「该产品该币种当时生效的那一条」
定价——拿一次查询给整批定价，会让一条过期底价去裁定它从未适用过的产品。

**实测**：把一行数量 16 → 8，运行合计在提交前就显示 1,900,000；保存后
详情页与管道列表页的 header 双双变成 ¥1,900,000。
再把一行单价压到 1，服务端标出「低于底价，需要签字」;恢复后标记消失。

**六条测试守着这条规则**，其中最要紧的一条断言的是**存储里的 header**而不是返回值——
一个报告了自己没写进去的总额的函数，会在它自己的输出上通过测试，
而把两个数字留在那里各自漂移。反证过：让服务写 `total + 1`,这条立刻变红。

#### 6b-4 已交付（2026-08-28）

6b-3 交付时留下了一个自己造出来的死结：定价规则会把低于底价的行项标成待批，
战况板会计数，徽标会显示，**而权限目录里没有任何一条权限能把它降下来**。
`pricing.discount_approval` 只是 ADR-015 的一个能力标签，说的是智能体可以*提议*，
不是有人可以*做出*。底价创造了一个没人能满足的签字要求。

**新权限 `pipeline.discount`（incr/0012），与 `pipeline.write` 分离。** 报出低于
底价的人不能是给它签字的人。授予范围与 `catalog.price` 相同——定底价和为底价开例
外是同一份权力的两半，而 sales_ops 本来就能移动底价。功能键仍是 19。

**签字按价格记，不挂在行项上。** 行项是整体替换写入的，挂在行项上的签字会被同一
商机上任何另一行的编辑销毁。键取
`(opportunity_id, product_id, unit_price, currency)`,于是三个性质是白送的：改别的
行签字仍在，重新报得更低就匹配不上（对，没人签过新数字）,改回签过的价格又匹配上
（也对）。追加表，无 UPDATE / DELETE 授权。

**实测**：sales_rep 把单价压到 700（底价 800）,行项列「折扣」显示「待批」且**没有
批准按钮**；同一页以 sales_leader 打开，按钮出现，填理由签字后该行变「已批准」,
管道列表的待批徽标从 1 归零。改到 600 后徽标重新出现，改回 700 又消失。

**九条测试**，其中两条做过反证：把 `approvalFor` 的价格比较去掉，「改低即失效」立刻
变红；把 action 的权限改成 `pipeline.write`,「销售不能给自己签字」立刻变红。

**顺带修好一个守卫的盲区。** `column-locks.test.ts` 原来只从「先全授权再 REVOKE
UPDATE」推导追加表。本增量的表用的是更紧的写法——建表时就只授 SELECT / INSERT——
于是对那条推导完全不可见。推导已拓宽为认两种写法，并配了各自的非空断言。
（一度以为它顺手抓到了 `yucer_field.commitment` 的缺失授权，查证是我漏看了它后面的
列级 `GRANT UPDATE`,那里没有缺陷。）

### 数据库通道（PR #34/#35）

`db-contract` job：`postgres:18` service 容器，按 `db-init.yml` 的**同一顺序**跑真
DDL，然后跑 `*.db.test.ts`（15 个）。**未加入必需检查集合**——那会改动分支保护
ruleset，是 owner 决定。

之所以必须先建通道再修适配器：唯一索引、CHECK、REVOKE 和 NULL 比较都是**数据库的
性质**，内存适配器建模不了。有几个缺陷就是这样在 788 个绿灯下活下来的：

- `uidx_sales_target_scope` / `uidx_forecast_snapshot_scope_at` 建在可空列上，而
  Postgres 的 UNIQUE **把 NULL 视为互不相同**——所以这两个约束**对工作区级行完全
  失效**，而那正是其他所有数字的基准。`incr/0003` 用 `NULLS NOT DISTINCT` 重建。
- `count()` 分配编号的三处注释都声称"放在事务里所以安全"。事务给的是**原子性不是
  串行化**：READ COMMITTED 下两个并发事务读到同一个 count。改用
  `pg_advisory_xact_lock`，按分配种类和作用域双重分键。
- `saveWinLossReview` 的 upsert `where` 未按工作区限定；`recordSignal` 的裸 `catch`
  把外键/CHECK 失败一律报成"已存在"。

**通道在它自己第一次运行里就抓到了三个我写的缺陷**：CHECK 测试的第 2、3 条断言因
Postgres 事务中止语义而实际无效（约束删掉照样绿）、硬编码容器口令、安装未禁用生命周期
脚本。这三件都只有对着真数据库和真 CI 跑过才会现形。

关于审计的一处措辞更正：它称 `deletedAt` 过滤意味着"全仓服务层断言证明的是另一个
实现"。**这说过头了**——没有任何产品路径能设置 `deleted_at`（所有 port 都没有删除
方法），两个适配器返回的是同一批活行。真正成立的是**排序**分歧（PR #30）。

TD-002 的现状是**收敛而非解决**：全部非 ASCII 文本集中在两个纯数据文件——
`portals/app/app/(app)/lib/messages.ts`（界面文案）与
`portals/app/app/domains/shared/demo-fixtures.ts`（演示数据展示文本），其余源文件
全部可机器校验。**收敛的口径是「可穷举且只含数据」，不是「只有一个文件」**：新增中文
文本只能进入这两个文件，装配逻辑（如 `demo-seed.ts`）必须保持 ASCII。

标准修订后二选一收口——平台仓为终端用户文案开显式口子，或引入正式 i18n 方案把文案
移出源码树。**在裁定之前收敛状态维持不变，不要「顺手修掉」**：把文案改成 `\uXXXX`
转义确实能满足字面规则，但会得到一份人类无法维护的文案和一份无法评审的演示数据。

### 一版被丢弃的 karda 接入（2026-08-15）

本仓曾写过 `platform/karda/{types,redact,client}.ts` 三个文件，含一个「主张可外发、
证据不可外发」的边界模块。**已整体丢弃**，不是风格问题——一次独立对抗审查（四视角 +
独立质疑者，62 个 agent、28 条确认发现）在那个 137 行的边界文件里查出**四条各自独立
的客户名称越界路径**：最强的一道检查 `knownNames` 通过端口结构上不可达；`derivedFrom`
原样外发且其唯一校验器是死代码、还按 `acc_` 前缀写而本仓主键全是 `gen_random_uuid()`；
facet 的**键**从不检查；正则是照测试夹具而非真实中文文案调的。外加该模块**从未编译
通过**（全仓唯一一处 tsc 错误，硬失败 `build`）。

**方法论上的结论，比这些 bug 本身重要：**

> **可以把「线格式的猜测」隔离在一个适配器里；不可以把「不属于自己的词汇表」隔离起来。**

那版代码自造了 `KNOWLEDGE_KINDS` / `KNOWLEDGE_SCOPES` / `KnowledgeClaim` —— 一个本仓
并不拥有的领域的词汇表 —— 再把一条**不可逆**的披露边界挂上去。猜错时端口错、边界规则错、
所有调用点全错，传输层隔离救不回来。arda 一期之所以能现在就写，正是因为它的端口返回
**yucer 自有的 `NewSignal`**，唯一的猜测被关在 `http-source.ts` 一个文件里。

悄悄挑 `rows[0].href` 然后与启动器分歧。反证：退回按键查找 → 红；战况板自选 → 红。

**实测**：`/domain/position` 上模块条回来了（`阵地经营域 | 客户管理 | 商机管理 |
报价管理 开发中 | 赢丢复盘`），战况板尾部读作五个域块，`战略武备域 → /domain/armory`、
`兵力部署域 → /planning`（单路由域指向那一页）。

### 7q 菜单按域拆开 —— 已交付（2026-08-30）

owner 两次纠正之后才对：「五个业务域 = 五个相对独立的功能板块，有单独的菜单+必要
首页」「你的菜单还是一锅粥」「保持现在菜单的 card 模式，需要按照业务域拆分为 5 个」。

**我前两次都改错了地方。** 7o 做域首页、7p 改战况板尾部的分组——都不是菜单本身。
菜单就是左栏那一列卡片，而它是一锅粥：判断卡（等你定、我的资源、友军·决策链、
产品线·在办）加五个域块，**全量堆在一起，不管你在哪个域、在做什么**。那是一个
没有域的产品的菜单。

**改法：菜单 = 你所在域的卡片。**

- **在域内**：只显示这个域自己的卡（判断卡 + 模块卡）加跨域常驻卡。
- **不在域内**（首页）：菜单就是五个域的**地图**——那是你挑一个板块进去的地方。
  进去之后地图消失：它的全部职责就是把你送进去，留着等于把你已经做过的选择在
  产品的每一页再摆一遍。

**归属从 href 读出，不手工指派。** 一张卡链接到它数字的来源页，那一页本来就只在
一个域里——所以 href 就是答案，卡换页即自动换菜单。手工指派会让两者漂移，而一张
归在它并不链入的域下的卡，是一个点下去就离开本板块的菜单项。

**踩到一个真错误并记下判据**：`menuFor` 起初写在 `board.ts` 里，而 `nav-board.tsx`
是客户端组件——把整个服务端模块拖进了浏览器包，构建死在 `Can't resolve 'fs'`。
规矩不是「文件要小」，是**客户端组件只能 import 浏览器跑得动的模块**；类型可以随便
引（类型会被擦除），运行时函数不行。已拆出纯模块 `board-menu.ts`。

**实测三处**：`/pipeline` 收窄为阵地经营域的四张卡；`/` 是五域地图；`/catalog` 只剩
常驻卡——战略武备域目前确实没有判断卡，那是真实状态不是缺陷，但值得记：**域拆开之后，
哪个域的菜单是空的立刻看得见**，这在一锅粥里是看不出来的。

反证：菜单停止过滤 → 5 条守卫红 4 条。

## 业务流程与剩余任务计划（2026-08-30）

### 流程摊平


### 本轮执行 —— 第 1 批已交付（2026-08-30）

**报价面 `/quote`**。机制一直都在：`opportunity_line` 带 quantity/unit_price/
amount/`needs_approval`，`price_book_entry` 带底价，`line_discount_approval` 带签字，
而 `listOpportunityLines` **早就把行项与审批 join 好了**（正是为了没有调用方能只看到

DesignateAccount），缺的是**名册**——「我们的重点客户是谁」放在一起看。
**只读，刻意的**：分级要在能看到证据的地方做（健康度、决策链、在办商机都在详情页），
在列表上给分级控件等于邀请人对着表格给客户排座次，而那正是 ADR-013 要避免的。

**16/19 个模块已是页面**，余 3 个需裁定（见第 2 批）。

### 第 2 批 · 线索分派 —— 已交付（2026-08-30）

owner 裁定：**「首先是区域，其二是负载」**。

**先量出链条断在哪**：`territory.owner_sub` 自 baseline 就在——「谁覆盖这块地」一直
答得出；**「这块地是哪」从来没有**。demo 把这个洞摆得很明白：区域叫
EAST/NORTH/SOUTH，客户带的是 华东/华北/华南/华中/西南/西北，**中间没有任何列、键或
规则连接**。区域优先的分派在这一环补上之前根本无法存在。

`0017` 给 territory 加 `regions`（JSONB 列表），**与 market_segment.criteria 同形状**
——那是已被真实数据验证过的模式，另造一套「这个覆盖哪些客户」的词汇会让产品对同一个
问题有两个答案，正是 ADR-023 写的那个错误。**空 = 不覆盖任何**，不是覆盖全部：
一个没配完的区域不该成为全工作区每条线索的答案。

**规则的顺序就是规则本身**。区域决定谁**有资格**接，负载决定这几个人里**该谁**接。
反过来，闲着的销售会拿到他从没打过的地盘——那比排队慢更糟。关键反证：rep_1 手头
99 条、rep_2 空闲，华东线索**仍然给 rep_1**。

**无法分派是一种结论，不是错误**：没匹配客户、客户无区域、无区域覆盖、覆盖区域无
负责人——四种都保留在列表里且说明原因。把它们藏掉会让区域地图看起来是完整的，
而线索悄悄没人接。

**预览 + 逐行应用**，不是「一键全分」。分派是在人之间搬工作，最需要人看一眼的恰恰是
规则答错的那种情形；而线索归谁，是谁会被问起它——那是几十个独立决定，不是一个批量
操作换了件衣服。

**实测**：长江物流（华中）→ East China → 指派成功 → 刷新后显示「已在规则位置」且
按钮消失；生鲜连锁未匹配客户，如实显示无区域、不给按钮。

**顺带发现并加固**：规则原本直接读 `t.regions`，而 0017 之前的历史行没有这一列——
`undefined.includes()` 会让路由器在遇到真实生产数据的那一刻停摆。改为
`(t.regions ?? [])`，未知的地盘读作「不覆盖」而非「覆盖全部」，并补了对应测试。

### 第 2 批 · 续约规则 —— 规则层已交付（2026-08-30）

owner 裁定：**「续约商机从项目派生，但是需要为订阅类的项目开始」**。

`0018` 给 project 加 `engagement_type`（one_off | subscription）。**为什么是一列而不是
从既有字段推**：`ends_at` 两种都有——一次性实施交付即结束，订阅制到期即结束——
从日期、金额或产品组合去猜一笔生意的商业形态，是从影子推实物；猜错的代价是要么追讨
客户从未承诺的续约，要么漏掉真正会流失的。**默认 one_off**：所有既有项目都早于这一列，
默认订阅制等于给历史上每一次交付都凭空造出一个续约义务。

规则要点：**已过期的最紧急**（把过去过滤掉正好藏起漏掉的那些）；**暂停中的项目仍在
走期限**（工作停了钟没停，这正是最容易漏的时候）；**草案带上一期的金额，不发明涨价**
（上期值多少是事实，下期值多少是谈判）；**已续约的不再提第二次**。9 条测试。

派生动作本身**不自动写**——ADR-003 那条线在这里格外重要：提案是对客户的一次商业接触。
UI 与服务层在下一批。

### 第 2 批 · 续约服务层与页面 —— 已交付（2026-08-30）

上一批把续约的规则写完了，然后停在那里，工作计划自己记了一句「UI 与服务层在下一
批」。这一批是那句话的兑现，但先量出来的是**规则里有一条分支根本到不了**。

**`already_renewed` 是死代码**。`assessRenewal` 有这条分支、有测试、有注释，而测试
是靠手工传进去的一个布尔量满足的——真实调用方无从得知。原因是模型里少一条边：
`project.opportunity_id` 记的是「这个交付来自那笔生意」（D6→D7 的去程），**没有任何
列记「这笔生意是那个交付的续约」**（回程）。没有它，产品会在期限窗口内每打开一次页面
就重新提议同一个续约，无论已经有人开过几个。

`0019` 补这条边：`opportunity.source_project_id`。

**为什么放在商机上而不是项目上**。两种放法都能回答「续过了吗」，所以由**谁来写**
破局：`source_project_id` 由 D6 在写自己那一行时写入，符合「一个对象一个归属域」；
反过来 `project.renewal_opportunity_id` 要 D6 伸手去写 D7 的表，为省一列破掉归属规则，
而且把一个项目永远钉死为只能续一次——对一份还会继续走下去的订阅是错的。

**它不给 UPDATE 授权**，这是设计不是遗漏。「这笔生意从哪来」就是归因，而归因键在
创建时冻结（98 的第 2 条）。INSERT 是表级的，所以它能被写一次、永不可改。因此 98
无需改动，可写列镜像也不动——**增量只有在加「可写」列时才需要重述 GRANT**。

**续约不是 self_sourced**。`resolveAttribution` 多了一条 `renewal` 分支。self_sourced
说的是「销售自己挖到的」；把续约算进去，等于让新业务领走存量书带来的收入的功劳——
正是归因冻结要防的那种功劳重分配，只不过挪到了创建时刻，没人看得见。`campaignId`
留 null：继承首期的 campaign 会让一场活动为客户此后每一次续约持续记功。

**两个动词，各守各的门，都不写**。`listRenewals`（D7）说什么快到期，`renewalDraft`
（D7）说某一笔会以什么条件开出；建商机走 `createOpportunity`（D6，
`pipeline.opportunity.create`）。D7 无权读 D6，所以「哪些项目已经有续约」由页面从
D6 取来传进去——和 /routing 把客户区域喂给路由器是同一个形状。

**健康度只为幸存者推导**。推一次要读一遍里程碑和一遍分期，而工作区里项目远多于到期
续约；而「是否到期」不依赖健康度（只有 due 的 risk 依赖），所以便宜的一遍过全部，贵的
一遍只过筛下来的。

**页面上量出来两个缺陷，都是点出来的，不是测出来的**：

1. **到期列跟着结论走**。`daysToEnd` 从 due 结论上取，于是 PRJ-0006（已有续约、但
   还有 4 天到期）显示成「未填到期日」——页面对数据说了假话。到期日是项目的事实，
   与规则的结论无关。`daysUntilEnd` 因此提到规则层导出，**只留一份定义**，
   `assessRenewal` 也调它。
2. **「已创建」标记落在别的行上**。`useSaveAction` 一个组件一份状态，是给「一个面板
   一个保存按钮」设计的；表格里每行一个 `SaveRow`，于是全表共用同一对
   `saved`/`err`——点第 2 行成功，标记画在第 1 行；**第 3 行被拒，拒绝理由会印在其余
   每一行旁边**。新增 `SaveCell`（每行自持状态），/routing 一并改掉：它是同一个构造，
   只是那里行不会消失所以看不出来。

**实测**：智能仓储实施（已过期 29 天）与 POS 上线一期（还有 21 天）带按钮；点 POS
那行 → 该行变「已有续约商机在跑」按钮消失，**上一行保持干净**；调度平台年度订阅如实
显示「还有 4 天 / 已有续约商机在跑」；门店运营订阅服务显示缺到期日的理由。

1244 tests pass，43 表 lockstep，19 个增量全部授权到位。

**余下需裁定的只剩预测规则**（第 2 批第 5 项）：自动建议 vs 强制；覆盖人工选择时留不
留痕。

### 第 2 批 · 预测规则 —— 已交付（2026-08-31）

owner 裁定：**「只建议，逐单应用」**，且**分歧不存列、按需推导**。第 2 批清单五项至此清空。

**先摆出一个冲突，因为它决定这个模块能不能存在**。`forecast.ts` 从第 1 批起就写着
预测档位**与阶段刻意解耦**——「一个在 negotiate 却不肯承诺的销售会填『乐观』，而这个
分歧正是预测评审的全部内容」。所以「按阶段自动定档」会推翻规则层已写下的决定。
**建议**不会：它给那个判断提供了一个可供判断的对象，把只能靠一单一单翻看板才看得见的
分歧摆到一页上。这是裁定为「建议」而非「强制」之后才成立的模块。

**四条规则，除分档外全部是下调**。时间流逝不是进展：在 negotiate 坐了两个月的生意
比昨天刚到的更不可能落地，绝不会更可能。一条能把自己往上说的规则，最终会从不活动里
预测出信心来。

| 输入 | 作用 |
|------|------|
| 赢率（本人填的或阶段默认） | 定基础档：≥80 承诺，≥50 乐观，其余管道 |
| 没写预计成交日 | 封顶到管道——**承诺就是在说它落在哪个周期**，没写周期就没有可承诺的东西 |
| 预计成交日已过而生意还开着 | 封顶到管道。这是预测永远停在「承诺」的最常见方式：日期滑了，档位没滑，数字继续上报 |

### 导航系统性整改 · 导航就是board（2026-08-31）

owner：**「你还是没有处理彻底」**，并给了四条规格：今日裁决在每个域置顶；其下是域内各模块，

## 采纳真的把事情做了（`feat/accepting-does-the-thing`）

裁定：**「采纳当然要真实发生业务动作，不能是假的」**，以及**「执行走采纳者的权限

**这一批之前，整套裁决是表演。** 点「采纳」把提案行改成 `accepted`，商机**一动不动**；

**走域服务，绝不走 store。** `advanceStage` 带着阶段机、`opportunity_stage_event` 的

**用采纳者自己的权限，一行代码都不用知道那是哪个权限**——`ctx` 原样传下去，

所以能到达执行器的集合是**开放的**，只有白名单能给它封边界。不在名单上的一律按高风险
处理并拒绝执行，而不是猜。

## 采纳了但做不了，不叫失败（`feat/accepted-is-not-failed`）

上一批把「采纳」接上了真实执行，这一批处理它的直接后果：**队列里有三条提案，采纳
之后会被标成「失败」**——两条起草触达、一条信号升级为线索。

**`failed` 是终态，用错了词就等于毁掉一个刚做出的判断。** `failed` 应该是「试过、
被拒绝」；而一个产品根本没有 handler 的动作类型，**从来没有试过**。真实的状态是：
人同意了，机器不会做，需要人去做。于是这类提案停在 `accepted`，界面上标「需人工执行」，
不再送进执行器。`draft_outreach` 没有 handler 是**有意的**——发出去的消息收不回来。

**在点之前说，不是点完再说。** 行上有标记，确认框里有一句「这 N 条里有 M 条产品不会
自动执行」。`batchRisk` 多返回一个 `manualCount`，所以对话框说的话由数据算出来，不是
手写的。

**顺手修掉三个「同一件事两个答案」**：

1. `batchRisk` 里写着字面量 `< 60`，而自治规则读的是 `CONFIDENCE_FLOOR`。同一个数，
   两处定义——挪动门槛会改变「什么能无人执行」而不改变「对话框警告什么」。
2. 授权设置页的「高风险问我」文案自己数了一遍能自动执行的动作，**还写着「信号升级
   为线索」**——它 2026-09-01 就从清单里拿掉了。设置页和上面两寸的队列互相矛盾。
   现在这句名单由 `EXECUTABLE_ACTIONS` 现算现填，说不错。
3. 确认框把枚举原样打出来：中文界面上写着「动作类型：draft_outreach；作用对象：
   account」，而正下方的表格写的是「起草触达 / 客户」。表格早就修过一次，对话框漏了。
   这是 TD-010 反复出现的形状。

## 三条豁免名单条目的清算（`chore/retire-three-unwired`）

`KNOWN_UNWIRED` 的规矩是「下次复查时还没有调用方就删掉」。这一批把三条到期的走完，
**三条的结论各不相同——不逐条看是分不出来的**。

**`isTerminalStatus` 删了，连同 `TERMINAL_ACTION_STATUSES`。** 它的豁免理由写着
「常量本身有调用方，这个包装函数没有价值」——**前半句也是错的，两个都没有任何调用方**。
这个文件里每条规则都从**正面**判断状态（`=== "proposed"`、`!== "proposed"`、
`=== "accepted"`），因为每条规则只知道自己能从哪一个状态出发；没有一条需要「什么都不会
再发生的状态集合」。代码从来不问的概念，不值得钉一个定义。

**`capabilityLabel` 接上了，不是删掉。** 客户详情页在手搓一个更弱的版本——直接索引
label map，**跳过了 `isCapability`**——于是这个函数 docstring 里那条性质（未标注的历史
要保持可见地未标注，而不是被猜进某个能力）在唯一需要它的地方**没有被应用**。
「没有调用方」是症状，病因是**有一个调用方，它把这个函数重写了一遍**。

顺手补了一条守卫：label map 与 `CAPABILITIES` 必须**一一对应**（中英文两份都查）。
今天它们正好完全一致——**这正是现在断言它的理由，而不是等它们不一致之后**。两个方向
的失败形态不同：有能力没标签，会静悄悄地退化成「未标注」，看起来像数据缺失而不是字典
缺失；有标签没能力更糟，它会在能力退休之后继续为已经不被承认的历史命名。

**`daysSinceLastContact` 走的是「统一」那一支。** 它原来收一个**日期数组**——这就是它
几个月找不到调用方的原因：store 给出的 `lastContactAt` 是单个日期（Prisma 适配器里是
一个 MAX，归约根本不过网），所以每个读者手上都只有一个 `Date | null`。**为一个不存在的
调用方设计的形状，会一直闲着，同时它本该服务的那件事被到处内联重写**——判断规则里一次，
客户证据面板里一次。改成调用方真正持有的形状之后，两处内联都换成了它。

**`null` 不是 `0`，测试现在明写这一条**：「从没联系过」和「今天刚联系」是相反的事实，
一个把两者都返回 0 的函数，会让静默客户规则要么对一个从没打过电话的客户误报，要么对
它闭嘴。

## 预测准确率：那张只追加的表终于收账（`feat/forecast-accuracy`）

`forecast_snapshot` 从批次 1 起就被 revoke 掉 UPDATE，**整套不可变设计只为了一个读法**：
期末实际对期初快照。产品一直在付这个代价，而**没有任何界面问过这个问题**——而且
预测轨迹那一节的说明里，这句话从批次 1 就印在屏幕上：「快照只追加、不可修改——预测
准确率是期末实际对期初快照，少一个点就算不出来。」**一句关于不存在的数字的话。**

**先纠正我自己上一轮的判断。** 我把这条挂起，理由是「算到 owner 头上会激励低报」，
说它需要裁定。查了之后发现**根本不需要**：`submitForecastSnapshot` 把
`scopeType: "workspace"` 写死了，产品里没有第二处写快照，所以 owner 口径的快照
**根本不存在**，裁不裁都算不出来。我把阻塞点放大了。真正该裁的时点是**在这类数据
存在之前**，不是现在。

**期初快照是最早的那一条，这里自己排序**，不信任 store 的返回顺序。「oldest first」
是某一个适配器的文档属性；一旦它松动，这个数会以**没人看得出来的方式**错——一条在
季度快结束时才补的快照会让准确率永远接近满分，一个好看且毫无意义的数字。测试特意
按**倒序**种数据。

**实际值现算，不从最后一条快照读。** 快照是某人在那一天说的话，实际是这些商机现在
说的话。从末次快照读会让答案取决于「有没有人记得在期末点一下按钮」——于是
**「没人点」会悄悄变成「预测很准」**。

**实际值走 `planSnapshot`，不在这里另写一次 rollUp**，这样比值的两边由同一个定义
算出：同样的「先口径后周期」过滤，同样的「丢单不计入」规则。本地再写一个 rollUp 就是
实际值的第二个定义，两个过滤器任何一处一改就会漂。

**三种「没有数」是三种答案，都不是 0%**：
- 没有期初快照 → 「无期初快照，准确率算不出」。印 0% 等于把「没预测」报成「预测得差」。
- 期初承诺为零 → 「期初未承诺，无从对照」。没有分母。
- 读取失败 → 徽章根本不渲染。因为查询出错而显示 0% 比不显示更糟。

**周期没结束时它不叫准确率。** 同一个比值，季度中是「已兑现期初承诺的 N%」。叫它
准确率等于在第二周告诉一个团队它的预测准确率是 8%。

**又一次踩中「档位和权限是两个轴」。** 我第一版测试断言 `sales_rep` 读准确率会被
`permission_denied` 拒——**没有**。`pipeline.forecast.view` 要的是 feature
`pipeline.forecast` 加 permission `pipeline.read`，而每个销售角色都有 pipeline.read。
真正的门是**档位**（pro 以上）。这个安排是对的（卖的是「预测能力」，买了之后组内看
团队承诺不算特权），但**旁边 `forecastHistory` 的注释把这件事说反了**，写着「不能
预测的 rep 也不能审计预测」——已一并更正。

**浏览器里验了四个状态中的三个**（第四个只有单测覆盖，因为 demo 里没有哪个已结束
周期带着非零期初承诺）：
- 本期 → 「已兑现期初承诺的 84%」。**这个数本身就是判别性检查**：若误用末次快照的
  承诺（420 万）而非期初，270/420 会显示 64%。显示 84%，说明用的是期初。
- 2026Q2（已结束、无快照）→ 「无期初快照，准确率算不出」，不是 0%。
- 给 Q2 存一次空快照 → 「期初未承诺，无从对照」。

`KNOWN_UNWIRED` 现在剩 5 条，全部是「钉住一个别处会吵起来的定义」那一类。

1357 tests pass。
