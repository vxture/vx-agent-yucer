## 一、组织方式

保留 XY-00–XY-05 总体编号，将涉及数据边界的大批次拆为 A/B 子批次，共九个可执行子批次。

不把子批次直接对应应用版本。默认完成一组可用成果后统一预览，owner 确认当前结果再安排发布。

先校验平台实际供给，避免 UI 完成后才发现关键依赖缺失；接着完成任务连续性与隔离底座，

以下是依赖和交付顺序，不表示安排多个代理并行执行。

- 完成 ISO、KNOW、MEM、ACL、CAP、EXEC 反例，含两个用户、同租户两个空间及撤权中断场景。
- 完成 RULE、FORM、RECEIPT 反例：对话／Skill 要求绕过表单、直接 SQL、切换空间、复用旧授权、
  假报成功和撤权缓存均不能越界；实际服务拒绝和业务回执有证据。
- 测量首个反馈、完整耗时、检索和模型用量，给出实际结果、适用范围及可接受门槛；不凭空承诺性能。
- 汇总能力迁移矩阵、平台缺口、未接通动作与残留 Issue，关联证据、PR、镜像与发布记录。
- 形成 owner 本地／测试环境预览清单；确认后统一安排发布，数据库在应用前升级，
  每次生产审批仍由 owner 本人在 GitHub 点击。

验收证据以明确样本、调用 ID、可核对业务记录及失败结果为准。夹具、真实平台调用、
测试空间写入和生产只读检查分别报告，不把其中一种冒充全部通过。

## 四、预览与发布节奏

| 组 | owner 能检查的完整成果 | 发布原则 |
|---|---|---|
| A | 入口、完整工作区、页面协作、同任务恢复 | 先预览；没有记忆时明确显示能力阶段，不作为“完整小聿”发布 |
| B | 本人长期记忆、记忆管理、独立业务知识及隔离 | 先预览；发布与否取决于 owner 对当前可用成果的确认 |
| C | 今日判断、真实研究与跨板块执行闭环 | 与相关反馈统一预览，完成必要保护再安排发布 |
| 总验收 | 全链路、角色范围、失败恢复和平台实调 | 给出可运行范围及残留，确认后提交生产审批 |

默认先预览并汇总反馈，不以 Issue／PR 合并自动创建版本。owner 未要求分阶段上线时，
可以合并实现而不部署，最终统一发布；不能让已有生产页面依赖尚未部署的数据库增量。

## 五、批次汇报与结项

每次汇报沿用：带上述标记的完整批次跟踪清单、本批验收子项、实际验证、残留与依赖、下一批。
状态区分待开始、实施中、待预览、待发布、已上线和阻塞；阻塞必须标出外部条件及可继续部分。
Issue 至少记录边界、验收、PR、样本和运行证据；生产核验后再关闭对应产品 Issue，
仅设计批次可在文档合并且检查通过后结项。#732 仅在五条铁律和约定可用范围实测完成后结项。

## 六、数据与发布准备

01A、02A、02B、04B 预期涉及新增持久化或数据约束，具体增量编号在实现时按 main 最新账本分配，
本计划不预占 DDL 编号。其余批次是否需要 DDL 以最终设计与证据为准，不为布局修改添加迁移。
任何新增写列同步列锁和 Prisma；角色／权限若需扩展，同步种子、镜像与目录，商业功能键不扩张。
默认销售、管理者和受限角色的可用范围必须在批次验收中覆盖。

数据采用可兼容的增量演进，不批量重写原消息或现行业务数据；旧路由与已存提案保持可达。
若采用分阶段开放，状态由服务器控制，不能用前端隐藏代替权限；未完成的后台自动执行不得开放。
发布材料注明应用回退范围、新旧版本兼容性和数据库不回退的事实，并提供关闭新增入口／任务调度的恢复办法。
涉及生产变更仍按现有 db-init、应用部署与 owner 审批流程执行，不新增平行部署机制。
