# 九个能力分区（D1-D9）

yucer 被切成九个能力分区。切分依据是**业务对象的所有权**：一个业务对象只能
由一个域拥有（可写），其他域只能引用（只读）。这条规则决定了域之间的交接契约，也
决定了 DB schema 的划分。

D9（产品目录）是 2026-08-26 由 ADR-017 追加的第九个分区，晚于本文件最初的八分区
划分（ADR-001，2026-08-12）——本文件在那之后长期没有同步，`CLAUDE.md` 的「NINE
capability partitions D1-D9」与这里的实现之间曾经对不上，2026-09-15 补齐。

## 全链路总览

```
                  D9 产品目录（基础设施，不带功能键，全链路只读引用，谁都不写它）
                          │
D1 战略  ──> D2 规划 ──> D3 市场执行 ──┐
                                      ├──> D5 商机侦探 ──> D6 商机管理 ──> D7 项目落地
                          D4 客户管理 ─┘                        │
                                                                └──> 赢丢复盘 ──┐
                                      D8 销售智能助手（横切八个能力分区）                 │
                                             ^                                  │
                                             └──────── 经验回流 ────────────────┘
```

D9 不在链路的主干上——它没有上一环也没有下一环，是被 D5（信号匹配）、D6（商机行项）、
D7（交付范围）平行引用的一张维度表，所以画在链路上方而不是链路里。D8 横切的仍然是
八个分区（`agent_playbook.scope_domain` 的 CHECK 约束只有八个取值，D9 不在其中——
详见 D9 小节的边界）。

## 域清单

| 域 | 名称 | 拥有的业务对象 | DB schema |
|----|------|--------------|-----------|
| D1 | 市场销售战略 | 战略规划、细分市场 | `yucer_gtm` |
| D2 | 销售规划 | 销售区域、目标/配额 | `yucer_gtm` |
| D3 | 市场执行 | 市场战役、战役执行项 | `yucer_gtm` |
| D4 | 客户管理 | 客户、联系人、关系图谱、**证据面**（跟进、承诺） | `yucer_core` + `yucer_field` |
| D5 | 商机侦探 | 商机信号、线索 | `yucer_pipeline` |
| D6 | 商机管理 | 商机、阶段事件、预测快照、赢丢复盘 | `yucer_pipeline` |
| D7 | 项目落地 | **合同**、交付项目、里程碑、回款计划 | `yucer_delivery` |
| D8 | 销售智能助手 | 会话、消息、建议动作、剧本 | `yucer_agent` |
| D9 | 产品目录 | 产品、解决方案、方案构成、价目条目 | `yucer_catalog` |

九个能力分区映射到六个 schema：D1/D2/D3 共享 `yucer_gtm`（同属「计划侧」，事务经常跨这
三个域），D5/D6 共享 `yucer_pipeline`（信号到商机是一条连续管道），D9 独占
`yucer_catalog`——它是全链路都读、只有它自己写的维度，混进任何一个业务域的 schema
都会让「谁拥有这张表」的答案变得可疑。域是**产品概念**，schema 是**存储边界**，两者
不必一一对应——最初八分区的理由见
`docs/30-design/decisions/ADR-002-five-schemas-for-eight-domains.md`（已被
ADR-017 追加修订，该文件顶部有修订记）。

## D1 市场销售战略

**职责**：定义一个周期内打什么市场、达成什么目标。产出是 `strategy_plan`（战略）
和 `market_segment`（细分市场）。**同一工作区同一周期允许多份战略**，各有编号、
目标、负责人和生命周期。目标与打法相同的多个客群优先纳入同一份战略，周期用于筛选。

**边界**：细分市场以独立功能入口维护，与战略规划、解决方案、产品目录同属战略武备域。
战略规划保留战略总览和执行跟踪（原“执行验证”）；后者跟踪按战略版本归因的商机储备、
累计赢单与赢率，不等同于战略假设已验证。细分市场不是某一份战略的子记录。旧战略市场页链接继续兼容。
战略卡片以规划域受控只读投影展示是否已纳入销售规划，按战略发布版本、当前有效／待生效／
草稿规划区分；权限不足或数据不可读不得报成未承接。至少一个目标已承接不代表全部承接。
卡片不在战略域修改销售规划；入口与展示约定见设计225和批次143。
细分市场描述可复用的客群条件、共性需求、采购场景、期望改善和切入门槛。
共性需求是独立可编辑的一句话摘要，建议 30–50 字、最多 60 字，在详情与编辑的「需求采购」
板块首行独占全宽，采用与其他条目一致的图标、标签和内容格式；总览卡片描述和清单单行摘要
继续复用该字段，智能填写同步提炼。客户痛点等长文保留分析和来源，不受摘要
长度影响。未填写摘要的存量市场仅在总览使用有界长文预览，详情显示未填写，
避免与客户痛点重复；不自动覆盖或改写原始分析。
本页市场名称建议 30 字以内、最多 50 字，只表达客群及核心特征，背景说明放入需求字段；
客户痛点和采购场景各 200 字，期望改善和进入门槛各 150 字。
六项可编辑业务文本统一显示实时字数及上限；超限时保留完整输入、逐项提示并阻止保存，
精简到范围内后恢复保存。历史长文不自动截断；编辑时提示按上限整理。智能填写与保存端
使用同一组限制，助手读取原有长文后归纳，不能截取开头代替业务结论。
战略从中选择目标市场；同一个细分市场可被不同战略采用，每份战略分别确定主攻或验证、
打法和主推方案。选入时保存市场名称和条件，目录定义修改不改写已选市场的口径。
自动匹配只产生当前库内候选，不改变客户分类、负责人或实际经营名单。跨市场客户去重。

细分市场有独立只读详情页，按「客群条件、需求采购、产品方案、关联战略、客户覆盖」组织，
与创建/编辑的信息分组对应。未填写的采购洞察不制造空白区块；产品方案和战略只展示有边界的
关联摘要，标题进入归属模块。主详情不使用抽屉，帮助和横向对比继续使用 DS 标准抽屉。
市场清单展示名称/编号、客群条件摘要、匹配客户数、产品方案数、采用战略数及状态，
需求和采购长文保留在详情。客户覆盖区分条件匹配、显式归类与资料不足，不将重叠数量相加，
也不把库内客户数解释为外部市场规模。旧查询式详情链接兼容跳转至 UUID 详情地址。

战略可引用同工作区方案目录，方案可以归在目标市场下，也可以作为战略通用方案。
方案内容仍由 D9 维护；新增关联只可选启用方案，停用保留既有引用，被引用的方案不可删除。
细分市场独立维护默认解决方案，战略选入目标市场时复制当前启用方案，形成该战略的
市场级方案选择；允许删除、补充或清空，保存后不再随市场默认方案变化。既有战略调整
继续走草稿与版本发布，不自动刷新已选市场的方案。新增目标市场仍按当时默认值继承，
相同方案在战略整体统计中去重。市场默认方案与战略通用方案相互独立。
人员投入和目标分配仍由 D2 承担。

战略制定结果以「基本信息、量化目标、目标市场、产品方案、高级设置」组织，创建与详情对应。
基本必填为战略类型、价值主张、战略定位、至少一项目标、目标市场、负责人；客户规模随目标市场
条件展示，不重复关联。名称、自动编号、真实执行周期、创建人和发布版本继续保留为元数据。
战略类型预置市场深耕、市场开拓、产品创新、多元布局、防御巩固、收缩聚焦、转型重塑；
价值主张预置成本优势、产品领先、客户亲密、体验便捷、生态整合。类型与价值主张均从配置读取。

战略目标统一原有经营预期，每项具有 UUID、指标名称、基线、目标值、单位、达成时间和对象标准。
收入、渠道建设、标杆案例继续投影为 D2 可承接的经营预期，保留原目标 UUID 与版本快照；
其他自定义指标不自动纳入收入汇总、区域拆解或无数据来源的进度。币种沿用工作区全局设置。
草稿允许未填完整，发布时检查必填。非法数值、无效日期、倒置里程时间不能保存；
新增或改变的达成日期不得早于当天，保留的历史日期不因自然时间推移而作废。

基本信息按名称/周期/负责人、战略类型/价值主张/实现路径两行排列，战略目标独占第三行。
实现路径从配置多选；量化目标使用一个下拉按钮新增，首行指标名称/基线/目标/达成时间，
次行描述要求。计量单位只展示，收入沿用工作区币种，其他指标沿用配置单位。
高级设置默认折叠，显示有效填写数 x/2；资源预算、阶段里程独立展开。折叠不清除数据，
详情只展示已填子项；两项均空则不展示整个高级区。历史风险数据保留，只读展示。
阶段首行名称/起止日期组合选择/负责人，次行交付成果与删除操作；负责人关联当前工作区成员。
具体人员分配与区域预算仍由 D2 维护。

后续资源到位反馈按「已登记到位量／本战略版本计划需求量」展示，如4/5、0/5。
需求未知保持未明确，需求为0显示无需投入；读取成功且没有到位登记时分子为0，不能把权限或读取失败当作0。
未投入、部分到位、全部到位分别使用info、warning、success，文字保持中性并辅以状态图标及来源提示。
实际到位是执行反馈，不改写已发布需求快照；实际资源事实仍由所属域持有，战略只读投影。
当前模型仅记录计划数量和说明，到位登记及统计尚未实现，实施跟踪批次144。

市场新旧属性在市场设置抽屉维护，关联卡片只读。产品方案新旧属性由目录维护，
战略不可改写；未配置保持未知，不以建档日期推断，发布快照保留当时属性。
Ansoff 一致性只做可关闭的提醒；不拦截保存或发布，不再提示偏好按成员保存。
战略智能填写复用 Atlas/Runos、多轮会话和现有助手框架，回填同一份未保存表单；
人员、市场、产品方案与配置必须来自当前工作区，保存与发布继续由用户复核后触发。


草稿中的目标市场、通用产品方案和市场级产品方案，统一使用 DS 标准中等宽度抽屉选择。
抽屉直接列出当前可选项，支持搜索、多选与已选计数；确认只更新本次草稿，取消不改变原关联。
产品和方案分组并使用不同图标；新增仅限启用条目，原有停用引用可保留或移除。
所有关联仍按工作区内 UUID 保存，编号仅用于识别和检索；抽屉不绕过既有权限和版本发布流程。

战略基本信息、目标市场与方案关联仅草稿可修改；批准后保持锁定，不退回原草稿覆盖历史
（ADR-039）。创建人由登录身份自动记录，与可选择的负责人分开。历史记录无创建人时保持未知。
周期是战略计划执行的真实日期窗口：年度按自然年、季度按自然季度，自定义必须提供起止日期，
支持跨年及单日，包含首尾日期。发布时间独立记录，不以发布时间推算执行周期。
到期提示复盘，不自动关闭战略或改写下游归属。已发布周期随版本冻结，调整走修订流程。
旧名称有可靠日历含义时可解析，无法解析时保留未知，不猜测；修订再次发布前需补齐有效日期。
查看页只读。

已发布战略通过「调整战略」建立共享修订草稿，当前版继续有效。保存修订草稿时必填修订说明，
字段显示必填标识和就地提示，发布仍复核该说明；发布生成 V1、V2… 并保留旧版与发布留痕。草稿保存不生成业务版本，也不改变历史执行归属。
`plan_no` 标识战略，`plan_id` 标识具体版本；下游不自动重指新版。发布内容冻结，实时匹配和
执行结果仍按当前事实读取。旧正式记录标记为迁移时 V1 快照，不补造历史发布人。

**交接**：D2 的目标、D3 的战役、D6 的商机都可以携带 `plan_id` 回指战略。这是全链路
可追溯的起点——没有它，「本季度多少商机来自这个战略」就无法回答。
从目标市场发起营销活动时，带入明确的战略和细分市场；同一期的其他战略不承接该活动的归因。

## D2 销售规划

**职责**：把战略拆成可执行的承诺。产出是 `territory`（销售区域）和 `sales_target`
（目标/配额）。

**边界**：只管目标的**设定**，不管目标的**达成度计算**（达成度由 D6 的预测快照对
比得出）。

**关键约束**：`sales_target` 的作用域元组 `(period, scope_type, territory_id,
owner_sub, metric)` 是行标识，一旦建立不可改；能改的只有金额和状态。改作用域 =
换了一个目标，应新建。

**地域与组织分开**（owner，2026-11-11）：销售区域以「配置管理 → 区域设置」的
地理划分为准，用于分解销售目标；组织架构维护公司部门和人员。部门与地理区域是
多对多关系：一个部门可负责多个区域，一个区域可由多个部门共同负责。没有部门或
只有两个人的工作区，也可按全国五个大区分别规划目标，不要求创建五个部门。
客户的「销售区域」从同一套区域设置选择。

区域销售规划将阶梯目标、时间分解、客户贡献和团队投入组织为完整版本；调整生成新版本，
历史达成绑定当时目标。模型与边界见 [35-sales-planning.md](35-sales-planning.md)，
该版本模型已实施；运行验收按工作计划记录，不把 D1 战略引用 `plan_id` 改作 D2 修订号。

2026-11-19 用户确认作战部署功能域按销售规划、重点客户、承诺达成、赢丢复盘归集。
功能导航不改变 D2/D4/D6 对象所有权；本期重点与长期客户级别分开。目标规格见
[36-deployment-workspace.md](36-deployment-workspace.md)，四板块导航与界面改造待实施。

## D3 市场执行

**职责**：把战略与细分市场变成具体动作。产出是 `campaign`（战役）和
`campaign_execution`（执行项）。

**边界**：管到「触达动作被安排、被执行」为止。触达的**结果**（线索、信号）归 D5。
不做邮件引擎、落地页、广告投放——见 `10-product-definition.md` 非目标。

**交接**：战役是归因的关键锚点。线索和商机携带 `campaign_id`，且该字段**创建后
不可改**——它是「这单从哪来」的事实记录。

## D4 客户管理

**职责**：客户主数据、关系图谱与证据面。产出是 `account`、`contact`、
`account_relation`，以及 `yucer_field` 的 `interaction`、`commitment`、
`contact_recency_policy`。

**边界**：管客户「是谁、什么结构、健康度如何、我们之间发生过什么」，不管「这个客户
身上有什么单」（那是 D6）。

**证据面归属**（2026-09-21 补）：`yucer_field` 此前不在任何域名下。归 D4 的理由是
它回答「我们和这家公司之间发生过什么」——主语是账户，不是商机也不是交付。
跟进原文是全链路一切判断的引用源（ADR-018）。

**关系图谱**：`account_relation` 是有向图边（汇报、平级、结盟、对立、引荐），
账户级、追加写。它是 D8 给出「下一步该找谁」的数据基础。

**采购角色不在这里**（ADR-024）：角色、立场、影响力按**单**存在
`yucer_pipeline.opportunity_contact` 上，归 D6。同一个人在三条商机里可以是三种角色。
账户级只能做**只读聚合**，不能写回（ADR-034）。
> 此前本节写「`contact.decision_role` 区分经济决策人/…」，那是 ADR-024 之前的形态，
> 2026-09-21 更正。

## D5 商机侦探

**职责**：不等销售录入，主动发现商机。产出是 `signal`（信号）和 `lead`（线索）。

**信号的本质是证据**：`signal` 的证据字段（来源、来源引用、类型、主题、载荷、
发现时间）**创建后不可改**，可改的只有「解析结果」（匹配到哪个客户、评分、生命
周期状态）。改证据 = 伪造证据。

**去重**：`(workspace_id, source, source_ref)` 唯一，同一来源的同一条外部记录只会
进来一次。

**交接**：线索合格后转化为商机，`lead.converted_opportunity_id` 回填，闭合归因环。

**操作闭环（C01）**：收件箱默认展示 `new/scored`，终态进入已处理，历史证据仍可检索。
人工发现也可登记为 `source=manual`，明确公司、事件、概要和发现时间；来源链接、预算及
截止日期按实际掌握情况填写，不冒充外部采集。打开页面不触发外部拉取；未配置来源时
明确显示未接入。公司匹配只提出建议，经人确认；转线索必须确认公司名称，不能使用
新闻标题代替。创建线索与推进信号状态、关闭状态与处理原因分别原子提交，并发操作
不重复生成线索或覆盖已经作出的判断。规则参考评分不代表证据已被独立验证。

## D6 商机管理

**职责**：商机从合格到赢丢的全过程，以及预测。产出是 `opportunity`、
`opportunity_stage_event`、`forecast_snapshot`、`win_loss_review`。

**阶段机与预测口径**见 `30-business-rules.md`。

**关键约束**：
- 阶段流转必须写 `opportunity_stage_event`（只追加），速度与转化率分析依赖它；
  **绝不从 `updated_at` 反推阶段历史**。
- `forecast_snapshot` 是不可变的时点快照，重新预测是**新增一条**，不是覆盖。
  历史预测准不准，是管理层最需要的数据，覆盖掉就永远算不出来。

**交接**：商机赢单后交给 D7 建立交付项目；赢丢复盘回流给 D8。

## D7 项目落地

**职责**：持有合同，并把它变成交付和回款。产出是 `contract`、`contract_line`、
`project`、`project_milestone`、`revenue_schedule`。（`project_task` 于 2026-08-28
删除，见 ADR-022。）

**边界**：覆盖「中标 -> 持有 -> 交付 -> 回款 -> 续约」，不做研发看板、工时、资源
排程，也不做合同**文本**管理（条款正文、模板库、电子签章、用印流程——见
`10-product-definition.md` 的非目标）。

**合同归属**（2026-09-21 补）：合同此前没有对象承载，但「合同」二字本来就在本域的
职责描述里。它存**元数据**——期限、金额、通知期、已购产品项、续约世系——是续约窗口
与已购态的唯一来源。不新开第十个分区的理由：现有九个里 D7 装得下（D6 管还在争取的、
D9 管卖什么、D4 是主语不是交易）。

**闭环意义**：链路终点不是「赢单」而是「钱到账」。`revenue_schedule` 的计划金额与
实际金额之差，是战略是否真正落地的最终度量。

## D8 销售智能助手

**职责**：横切八个能力分区的智能体。产出是 `agent_session`、`agent_message`、`agent_action`、
`agent_playbook`。

**人机边界（产品最重要的一条规则）**：智能体产出的是 `agent_action`——**可审阅的
建议动作**，默认生命周期是 `proposed -> accepted/rejected -> executed`，必须有人类
`decided_by_sub` 落章。自动执行（`copilot.autopilot`）只在企业档位且显式授权下开启，
且依然写全量留痕。

**建议本身不可篡改**：`agent_action` 的 `payload` / `rationale` / `confidence` 是模型
当时的判断记录，创建后不可改；可改的只有人类决策与执行结果。这样「智能体当时建议了
什么、人当时怎么决定的」永远可审计。

**接地**：`agent_playbook` 是可复用的销售剧本/话术，按 `scope_domain` 归属到八个能力分区之
一，是智能体建议的接地素材。

## D9 产品目录

**职责**：全链路共享的「我们卖什么」维度。产出是 `product`（产品）、`solution`
（解决方案）、`solution_item`（方案构成）、`price_book_entry`（价目条目）。

**边界**：只管「卖什么、标价与底价是多少」，不管「这一单订了什么」——那是 D6 的
`opportunity_line`，虽然 `opportunity_line` 按 ADR-014 §2 逐行读目录定价，行项本身
仍住在 `yucer_pipeline`、归 D6 所有：定一笔交易的价属于「维护这笔交易」的权限，目录
只是它读的维度，不因为被引用就拥有引用它的对象。

**不带功能键**（ADR-017，产品分区里唯一一个）：目录不是一项可售卖的能力，而是链路的
基础设施——不知道自己卖什么就没法卖任何东西。门控因此完全落在权限层，而不是「档位
够不够」：`catalog.read`（普遍授予——一个看不见公司卖什么的人也读不懂一条商机；
角色目录不冻结，具体授予哪些角色见 `50-role-permission-catalog.md` 而不是本文件，
避免又留一个会过期的数字）、`catalog.write`（维护产品与方案）、`catalog.price`
（定标价与底价，单独成权——能移动底价的人，等于能在不批准任何东西的情况下批准这个
产品里的每一笔折扣，`sales_rep` 刻意不给）。

**关键约束**：`price_book_entry` 按 `effective_at` 追加，不覆盖——新时点的新价格是
新行，被取代的一行仍可读，它解释了今天这个数字是怎么来的。`solution` 必须装着至少
一条 `solution_item` 才成立，空方案是一个名字，不是一个可提的方案。

产品与方案的「首次发布时间」独立记录：产品第一次进入系统在售状态（`active`）、
方案第一次启用（`active`）时，以数据库当前时刻记录。记录一次后，编辑、排序、
修改价格、停用或重新启用均不覆盖。迁移前没有可靠发布历史的存量保持「未记录」，
即使后续重新启用也不伪称第一次发布；不以创建、更新或价格生效日期推算。
时间与完整历史标记由持久化层维护，页面和智能体不能填写或覆盖；界面在编号后只显示日期。

**交接**：D6 的商机行项定价、D7 的交付范围、D5 的信号匹配（一条招标公示对应哪个产品）
都读它；它自己不产生归因、不携带客户信息，也不回指任何下游对象。
