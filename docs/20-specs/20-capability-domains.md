# 九个能力分区（D1-D9）

yucer 被切成九个能力分区。切分依据是**业务对象的所有权**：一个业务对象只能
由一个域拥有（可写），其他域只能引用（只读）。这条规则决定了域之间的交接契约，也
决定了 DB schema 的划分。

D9（产品目录）是 2026-08-26 由 ADR-017 追加的第九个分区，晚于本文件最初的八分区
划分（ADR-001，2026-08-12）——本文件在那之后长期没有同步，`CLAUDE.md` 的「NINE
capability partitions D1-D9」与这里的实现之间曾经对不上，2026-09-15 补齐。

## 全链路总览

```
                  D9 产品目录（基础设施，不带功能键，全链路只读引用，谁都不写它）
                          │
D1 战略  ──> D2 规划 ──> D3 市场执行 ──┐
                                      ├──> D5 商机侦探 ──> D6 商机管理 ──> D7 项目落地
                          D4 客户管理 ─┘                        │
                                                                └──> 赢丢复盘 ──┐
                                      D8 销售智能助手（横切八个能力分区）                 │
                                             ^                                  │
                                             └──────── 经验回流 ────────────────┘
```

D9 不在链路的主干上——它没有上一环也没有下一环，是被 D5（信号匹配）、D6（商机行项）、
D7（交付范围）平行引用的一张维度表，所以画在链路上方而不是链路里。D8 横切的仍然是
八个分区（`agent_playbook.scope_domain` 的 CHECK 约束只有八个取值，D9 不在其中——
详见 D9 小节的边界）。

## 域清单

| 域 | 名称 | 拥有的业务对象 | DB schema |
|----|------|--------------|-----------|
| D1 | 市场销售战略 | 战略规划、细分市场 | `yucer_gtm` |
| D2 | 销售规划 | 销售区域、目标/配额 | `yucer_gtm` |
| D3 | 市场执行 | 市场战役、战役执行项 | `yucer_gtm` |
| D4 | 客户管理 | 客户、联系人、关系图谱、**证据面**（跟进、承诺） | `yucer_core` + `yucer_field` |
| D5 | 商机侦探 | 商机信号、线索 | `yucer_pipeline` |
| D6 | 商机管理 | 商机、阶段事件、预测快照、赢丢复盘 | `yucer_pipeline` |
| D7 | 项目落地 | **合同**、交付项目、里程碑、回款计划 | `yucer_delivery` |
| D8 | 销售智能助手 | 会话、消息、建议动作、剧本 | `yucer_agent` |
| D9 | 产品目录 | 产品、解决方案、方案构成、价目条目 | `yucer_catalog` |

九个能力分区映射到六个 schema：D1/D2/D3 共享 `yucer_gtm`（同属「计划侧」，事务经常跨这
三个域），D5/D6 共享 `yucer_pipeline`（信号到商机是一条连续管道），D9 独占
`yucer_catalog`——它是全链路都读、只有它自己写的维度，混进任何一个业务域的 schema
都会让「谁拥有这张表」的答案变得可疑。域是**产品概念**，schema 是**存储边界**，两者
不必一一对应——最初八分区的理由见
`docs/30-design/decisions/ADR-002-five-schemas-for-eight-domains.md`（已被
ADR-017 追加修订，该文件顶部有修订记）。

## D1 市场销售战略

**职责**：定义一个周期内打什么市场、达成什么目标。产出是 `strategy_plan`（战略）
和 `market_segment`（细分市场）。

**边界**：只管「打哪里、为什么」，不管「谁去打、打多少」（那是 D2）。

**交接**：D2 的目标、D3 的战役、D6 的商机都可以携带 `plan_id` 回指战略。这是全链路
可追溯的起点——没有它，「本季度多少商机来自这个战略」就无法回答。

## D2 销售规划

**职责**：把战略拆成可执行的承诺。产出是 `territory`（销售区域）和 `sales_target`
（目标/配额）。

**边界**：只管目标的**设定**，不管目标的**达成度计算**（达成度由 D6 的预测快照对
比得出）。

**关键约束**：`sales_target` 的作用域元组 `(period, scope_type, territory_id,
owner_sub, metric)` 是行标识，一旦建立不可改；能改的只有金额和状态。改作用域 =
换了一个目标，应新建。

## D3 市场执行

**职责**：把战略与细分市场变成具体动作。产出是 `campaign`（战役）和
`campaign_execution`（执行项）。

**边界**：管到「触达动作被安排、被执行」为止。触达的**结果**（线索、信号）归 D5。
不做邮件引擎、落地页、广告投放——见 `10-product-definition.md` 非目标。

**交接**：战役是归因的关键锚点。线索和商机携带 `campaign_id`，且该字段**创建后
不可改**——它是「这单从哪来」的事实记录。

## D4 客户管理

**职责**：客户主数据、关系图谱与证据面。产出是 `account`、`contact`、
`account_relation`，以及 `yucer_field` 的 `interaction`、`commitment`、
`contact_recency_policy`。

**边界**：管客户「是谁、什么结构、健康度如何、我们之间发生过什么」，不管「这个客户
身上有什么单」（那是 D6）。

**证据面归属**（2026-09-21 补）：`yucer_field` 此前不在任何域名下。归 D4 的理由是
它回答「我们和这家公司之间发生过什么」——主语是账户，不是商机也不是交付。
跟进原文是全链路一切判断的引用源（ADR-018）。

**关系图谱**：`account_relation` 是有向图边（汇报、平级、结盟、对立、引荐），
账户级、追加写。它是 D8 给出「下一步该找谁」的数据基础。

**采购角色不在这里**（ADR-024）：角色、立场、影响力按**单**存在
`yucer_pipeline.opportunity_contact` 上，归 D6。同一个人在三条商机里可以是三种角色。
账户级只能做**只读聚合**，不能写回（ADR-034）。
> 此前本节写「`contact.decision_role` 区分经济决策人/…」，那是 ADR-024 之前的形态，
> 2026-09-21 更正。

## D5 商机侦探

**职责**：不等销售录入，主动发现商机。产出是 `signal`（信号）和 `lead`（线索）。

**信号的本质是证据**：`signal` 的证据字段（来源、来源引用、类型、主题、载荷、
发现时间）**创建后不可改**，可改的只有「解析结果」（匹配到哪个客户、评分、生命
周期状态）。改证据 = 伪造证据。

**去重**：`(workspace_id, source, source_ref)` 唯一，同一来源的同一条外部记录只会
进来一次。

**交接**：线索合格后转化为商机，`lead.converted_opportunity_id` 回填，闭合归因环。

## D6 商机管理

**职责**：商机从合格到赢丢的全过程，以及预测。产出是 `opportunity`、
`opportunity_stage_event`、`forecast_snapshot`、`win_loss_review`。

**阶段机与预测口径**见 `30-business-rules.md`。

**关键约束**：
- 阶段流转必须写 `opportunity_stage_event`（只追加），速度与转化率分析依赖它；
  **绝不从 `updated_at` 反推阶段历史**。
- `forecast_snapshot` 是不可变的时点快照，重新预测是**新增一条**，不是覆盖。
  历史预测准不准，是管理层最需要的数据，覆盖掉就永远算不出来。

**交接**：商机赢单后交给 D7 建立交付项目；赢丢复盘回流给 D8。

## D7 项目落地

**职责**：持有合同，并把它变成交付和回款。产出是 `contract`、`contract_line`、
`project`、`project_milestone`、`revenue_schedule`。（`project_task` 于 2026-08-28
删除，见 ADR-022。）

**边界**：覆盖「中标 -> 持有 -> 交付 -> 回款 -> 续约」，不做研发看板、工时、资源
排程，也不做合同**文本**管理（条款正文、模板库、电子签章、用印流程——见
`10-product-definition.md` 的非目标）。

**合同归属**（2026-09-21 补）：合同此前没有对象承载，但「合同」二字本来就在本域的
职责描述里。它存**元数据**——期限、金额、通知期、已购产品项、续约世系——是续约窗口
与已购态的唯一来源。不新开第十个分区的理由：现有九个里 D7 装得下（D6 管还在争取的、
D9 管卖什么、D4 是主语不是交易）。

**闭环意义**：链路终点不是「赢单」而是「钱到账」。`revenue_schedule` 的计划金额与
实际金额之差，是战略是否真正落地的最终度量。

## D8 销售智能助手

**职责**：横切八个能力分区的智能体。产出是 `agent_session`、`agent_message`、`agent_action`、
`agent_playbook`。

**人机边界（产品最重要的一条规则）**：智能体产出的是 `agent_action`——**可审阅的
建议动作**，默认生命周期是 `proposed -> accepted/rejected -> executed`，必须有人类
`decided_by_sub` 落章。自动执行（`copilot.autopilot`）只在企业档位且显式授权下开启，
且依然写全量留痕。

**建议本身不可篡改**：`agent_action` 的 `payload` / `rationale` / `confidence` 是模型
当时的判断记录，创建后不可改；可改的只有人类决策与执行结果。这样「智能体当时建议了
什么、人当时怎么决定的」永远可审计。

**接地**：`agent_playbook` 是可复用的销售剧本/话术，按 `scope_domain` 归属到八个能力分区之
一，是智能体建议的接地素材。

## D9 产品目录

**职责**：全链路共享的「我们卖什么」维度。产出是 `product`（产品）、`solution`
（解决方案）、`solution_item`（方案构成）、`price_book_entry`（价目条目）。

**边界**：只管「卖什么、标价与底价是多少」，不管「这一单订了什么」——那是 D6 的
`opportunity_line`，虽然 `opportunity_line` 按 ADR-014 §2 逐行读目录定价，行项本身
仍住在 `yucer_pipeline`、归 D6 所有：定一笔交易的价属于「维护这笔交易」的权限，目录
只是它读的维度，不因为被引用就拥有引用它的对象。

**不带功能键**（ADR-017，产品分区里唯一一个）：目录不是一项可售卖的能力，而是链路的
基础设施——不知道自己卖什么就没法卖任何东西。门控因此完全落在权限层，而不是「档位
够不够」：`catalog.read`（普遍授予——一个看不见公司卖什么的人也读不懂一条商机；
角色目录不冻结，具体授予哪些角色见 `50-role-permission-catalog.md` 而不是本文件，
避免又留一个会过期的数字）、`catalog.write`（维护产品与方案）、`catalog.price`
（定标价与底价，单独成权——能移动底价的人，等于能在不批准任何东西的情况下批准这个
产品里的每一笔折扣，`sales_rep` 刻意不给）。

**关键约束**：`price_book_entry` 按 `effective_at` 追加，不覆盖——新时点的新价格是
新行，被取代的一行仍可读，它解释了今天这个数字是怎么来的。`solution` 必须装着至少
一条 `solution_item` 才成立，空方案是一个名字，不是一个可提的方案。

**交接**：D6 的商机行项定价、D7 的交付范围、D5 的信号匹配（一条招标公示对应哪个产品）
都读它；它自己不产生归因、不携带客户信息，也不回指任何下游对象。
