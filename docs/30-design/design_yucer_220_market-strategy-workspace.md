# 市场战略工作区：市场选择、客群与进入策略

状态：2026-11-12 完成系统设计，并实现本地首轮交互供评审；未发布、未新增数据库结构。

用户要求：首先整合市场战略和细分市场，系统分析业务与体验，借鉴行业方法与卖点。
本文给出完整目标设计与实施验收。第 11 节记录本轮已实现范围；其余建议中的版本、关系和指标不代表已经实现。
产品边界以 [产品定义](../20-specs/10-product-definition.md)、
[能力分区](../20-specs/20-capability-domains.md) 为准；涉及新增业务规则的部分，
实施前同步产品规格并记录必要 ADR，不以本设计覆盖现有权威。

## 1. 定位与核心任务

模块继续叫「市场战略」，Launcher 保留一个入口。细分市场成为模块内部的「市场库」，
也是战略选择目标市场的基础。合并后帮助负责人回答五个连续问题：

1. 哪些市场值得投入，哪些暂时不做？
2. 在这些市场里，具体选择哪些客户，为什么适合？
3. 用什么解决方案、价值主张和进入方式打开市场？
4. 谁负责，怎样交给销售规划和营销活动落实？
5. 哪些假设已被客户、商机和成交事实验证，下一轮该怎样调整？

主要使用者是销售负责人、市场负责人和销售运营；一线销售读取与自己相关的市场打法，
从客户和商机进入，不要求每天维护战略表。小团队可先做一份战略、一个市场、一个打法。

## 2. 当前基础与真实缺口

| 当前实现 | 可保留的基础 | 重构要解决的问题 |
| --- | --- | --- |
| `strategy_plan` | 名称、周期、目标说明、负责人和五态生命周期 | 缺少市场取舍、打法、证据、检查节点与已批准内容的版本冻结 |
| `market_segment` | 稳定编码、行业/规模/区域条件、排序和状态 | 目前只有一个可选 `plan_id`，无法表达同一市场被不同战略采用、各自有不同打法 |
| 客群判断 | 条件匹配、在册与命中差异、客户详情 ICP 三维解释 | 手工主分类与动态匹配混在一起；缺失资料、排除项、历史条件与当前条件需要区分 |
| 战略检查 | 缺目标、无市场、无活动、周期已开始等规则检查 | 已有能力应汇合至一个检查抽屉，不再各页重复出现 |
| 战略诊断 | 市场/区域快照与趋势页面 | 统计口径存在问题，不能直接作为新工作区的可信成效数据 |

代码审查确认的前置问题：

- `domains/strategy/lib/lifecycle.ts:planSegment` 重建 criteria 时只保留 industries、regions，
  遗漏 sizes；前端填写、适配器直写测试通过，不代表经服务保存后规模条件仍存在。
- `segment-advice.ts` 的「无条件」判断也只看行业/区域，纯规模条件会被误报。
- `snapshot-job.ts:computeSegmentStats` 按 segmentCode 统计客户，但金额查询未按客户或
  市场限制，把工作区商机总额写入每个市场；币种固定 CNY，也未按币种过滤。
- 同文件 `computeTerritoryAttainment` 未使用 period 过滤成交；区域目标遍历也不是
  新版规划生效目标的读取口径。旧区域诊断不能替代已上线的承诺达成读模型。
- 现有市场规则可在 approved/active 战略下修改，`approved_at` 本身不能证明批准内容。

规模保存与纯规模检查已在首轮修复；快照口径与版本冻结仍作为后续实施阻断项登记在本轮工作计划。对旧快照不能通过改查询自动修复历史：
需要区分旧口径与新口径，旧点不进入新趋势；没有历史源数据时不能伪造重算。

## 3. 行业参考与具体取舍

以下页面于 2026-11-12 实际读取，仅作为方法参考，不引用厂商宣传数字证明聿策效果。

| 参考 | 采用的思路 | 在聿策的落点 |
| --- | --- | --- |
| [HubSpot ABM 指南](https://blog.hubspot.com/marketing/account-based-marketing-guide) | 理想客户画像、选择高价值账户、市场销售对齐、跟踪结果 | 明确客群与客户清单；市场负责人和销售负责人共享同一战略依据 |
| [Demandbase ABM](https://www.demandbase.com/products/account-based-marketing/) | 结合 fit、engagement、buying signals 确定优先级，再协调执行 | 客群适配、已有互动、明确信号分开展示；每项可看来源，不揉成神秘总分 |
| [Strategyzer Value Proposition Canvas](https://www.strategyzer.com/library/the-value-proposition-canvas) | 客户任务、痛点、期望收益与供给之间的匹配需要证据验证 | 每个主攻市场填写客户问题、方案、价值主张及验证方式，复用产品/方案目录 |

不照搬广告投放、第三方全网意向评分、营销自动化和企业情报数据库。系统没有的数据不以
「行业标杆」「市场总量」展示。MEDDPICC、采购决策链等逐单方法继续留在商机工作台，
战略页只保留进入某一类客户时的通用角色假设。

可销售的能力应能现场演示：

- 选择客群后立即看到库内匹配客户、资料缺项和排除原因。
- 两个市场并排比较已有客户、业务储备与方案适配依据，负责人能解释为什么先投一个。
- 同一个市场可用于两个战略，分别制定新客突破与存量扩展打法，不重复建立客户。
- 从市场打法进入销售规划或创建营销活动，保留战略、市场和版本上下文。
- 复盘时看当时选择和现在事实的差异，助手引用来源提出调整建议，由人确认。

## 4. 推荐业务模型

### 4.1 五个概念分开

| 对象 | 回答的问题 | 归属与关系 |
| --- | --- | --- |
| 市场定义 | 哪类客户构成一个可讨论的市场？ | D1 可复用的条件与说明，不是客户归属 |
| 战略 | 某个周期选择打哪里、为什么、以什么方式取胜？ | D1 稳定战略 ID、周期、负责人、批准/执行状态 |
| 战略中的市场选择 | 这份战略怎样对待某个市场？ | D1 战略修订中的引用、条件快照、投入档位、打法和验证依据 |
| 目标客户集合 | 这次准备实际经营哪些客户？ | 引用 D4 客户 ID；动态候选与人工纳入分开 |
| 销售规划与活动 | 谁承担多少目标，安排什么执行？ | D2/D3 原有对象；战略仅引用和交接，不在本页复制配额或活动维护 |

推荐新增「战略中的市场选择」关系，让战略与市场成为多对多。同一市场在不同战略里可
分别标记主攻、验证、暂缓；顺序和投入档位属于战略，不能修改市场库全局 priority 后
影响所有历史战略。市场库的默认排序仅供检索。

现有 `market_segment.plan_id` 保留为旧关系迁移来源；迁移为对应战略的市场选择，
不直接清空旧字段，不新建重复市场。`account.segment_code` 保持客户主分类的既有含义，
不因候选匹配、战略纳入或库内排序自动改写。市场编码保持不可变。

### 4.2 市场定义：可计算条件与业务假设

- 基础条件：行业、客户规模、地域范围；同维度多选为 OR，不同维度为 AND。
- 排除条件：明确不经营的类型或客户；显式排除优先于普通条件匹配。
- 业务说明：应用场景、客户问题、典型采购角色、进入门槛。文字没有结构化数据时不参与匹配。
- 方案引用：来自产品/解决方案目录；没有合适方案时标明待完善，不自动生成目录项。
- 证据：来源引用、摘要、日期、记录人；外部材料可作为人工依据，不能冒充已验证事实。

行业、规模从配置字典选择，地域使用配置管理的区域设置，不从组织部门推导。
地域条件应在模型中引用稳定 ID 并保存发布时范围快照；客户现有 region 名称仅通过明确
映射兼容，不能按相似名称推断。允许定义尚无客户的新市场，不能只用已有客户值限制选项。

条件评估输出「匹配／不匹配／资料不足／未定义」并给出逐维原因。全部条件为空时不代表
全部客户；必须显式选择全库范围并说明理由。现有 ICP 三维解释可复用，但 3/3 拟合不等于
购买意愿或成功概率，未限定维度不能被描述为三项已验证证据。

候选实时匹配；人工纳入、手工排除有记录和理由。条件变化只产生新增/移出候选提示，
不自动改变已批准客户集合，不自动把客户升为战略级，不重新分派负责人。

### 4.3 每个主攻市场的进入打法

| 分组 | 核心内容 | 填写约束 |
| --- | --- | --- |
| 投入选择 | 主攻/验证/暂缓、优先顺序、选择与放弃理由 | 主攻和验证必须解释；暂缓市场可只记录原因及复查日期 |
| 客户问题 | 任务或场景、关键痛点、业务触发条件 | 可从跟进/赢丢复盘引用；没有依据标为待验证 |
| 价值主张 | 主推方案、解决什么问题、可验证收益、差异化依据 | 不强制量化虚构收益；新方案需求可记录但不能伪装成在售方案 |
| 进入方式 | 直销/伙伴/活动/存量扩展等方式、首个切入角色 | 执行动作去活动或客户工作台维护 |
| 验证安排 | 负责人、下一检查日期、验证问题、通过/调整条件 | 验证市场必须有一个可执行的小范围验证 |
| 约束与风险 | 交付能力、资质、预算、竞争与渠道限制 | 逐条记录事实/假设/待核实，不把推测渲染成确定结论 |

优先级先采用「主攻/验证/暂缓 + 明确理由」，同时显示已有证据及缺口。资料充足后可增加
市场吸引力/我方竞争条件的辅助比较；首期不启用加权评分、自动排名或虚假的精确分数。
模板只带字段与提示，不带未经证实的行业结论。

## 5. 业务流程与版本

```mermaid
flowchart LR
  A[建立或复用市场定义] --> B[预览候选与资料缺项]
  B --> C[选择主攻与验证市场]
  C --> D[明确方案、打法和验证条件]
  D --> E[检查并批准战略版本]
  E --> F[衔接销售规划与营销活动]
  F --> G[客户经营与商机推进]
  G --> H[按原定条件验证与复盘]
  H --> I[形成调整草稿]
  I --> E
```

沿用 draft/approved/active/closed/archived，不凭合并新增一套审批流程。
「保存草稿」「批准战略」「启动执行」区分清楚，批准仍需 `strategy.approve`。
不存在的「已提交」状态不在界面伪造；若将来增加送审流程，另行定义。

推荐采用稳定根对象与完整修订：批准时冻结目标说明、市场选择、条件、客户集合、打法、
依据和验证指标。执行中日常只读；「调整战略」建立修订草稿，写明理由，经同样批准后生效。
现行版本在草稿期间继续工作。草稿有并发令牌，批准/启动/调整重试要幂等。
版本记录与差异收进抽屉，主页面只留版本、状态和核心业务信息。

市场库更新不会改写已批准战略的条件；采用新版规则需产生战略调整。
历史客户名单可以冻结 ID 和必要显示快照，但查询时仍按当前权限投影；被撤销权限的历史
名称、数量、金额也不能透过版本内容泄漏。无权限只显示不可读取，不显示隐藏数量。

实施可复用销售规划的版本设计经验，不复用其配额对象、状态实例或发布权限。
新增持久化对象、批准事务和冻结约束须由增量 DDL、列锁和 Prisma 一并交付。

## 6. 页面与交互设计

### 6.1 一级工作区

统一入口 `/strategy`，只保留一个「市场战略」主标题及原有浅色虚线。
三个内部功能是「战略总览／市场库／执行验证」，置于操作区；这是模块内真实功能切换。
功能切换保持当前战略、周期、搜索上下文，允许直接深链，不放五域之间的菜单。

| 位置 | 内容 |
| --- | --- |
| 页标题区 | 市场战略；右侧周期、主操作「新建战略」、三点菜单 |
| 操作区 | 内部功能切换、当前功能筛选、卡/列表切换；市场库主操作改为「新建市场」 |
| 战略总览主区 | 当前战略卡片，卡头为名称/状态/版本/负责人/菜单；内容为战略方向、主攻市场和衔接情况 |
| 市场库主区 | 默认紧凑列表，比较条件与当前匹配情况，进入定义详情或选择进入某份战略 |
| 执行验证主区 | 选择战略与有效观察周期，展示验证问题、证据变化和可核对结果 |
| 右侧 | 原有共享助手，使用当前战略/市场/版本/数据范围；不增加另一套会话 |
| 辅助信息 | 战略检查、版本历史、差异、证据详情均进入抽屉 |

战略卡是独立业务对象，可使用 DS ListCard；不把整个页面和每个数字分别套卡。
卡片默认只展示一行方向、主攻市场摘要和客户/活动/规划衔接信息，完整内容进入战略详情。
草稿、进行中、已结束有状态筛选；历史可以折叠，不常驻大量过期卡片。

市场库表建议列：序号、市场名称/一句场景、客群条件、库内客户、采用战略、状态、操作。
库内客户列区分「匹配 N／资料不足 M」，不称市场规模；长条件和策略正文收进 tooltip/抽屉。
编码是辅助信息。市场比较一次选 2-3 个，使用抽屉并排比较，不新建永久首页。

### 6.2 战略详情

新增 `/strategy/[id]`，标题为战略名称，不再重复打印「市场战略」。
顶部保留周期、状态、版本、负责人和合法操作。主体为三段开放式内容：

1. 战略方向：要解决的问题、重点投入和明确不做的范围；规划目标仅引用，不再维护一套。
2. 目标市场：主攻、验证、暂缓分组；每行能看到客群、理由、主推方案、负责人、下次检查日期。
   点击市场进入该战略下的打法；暂缓组默认收起，有依据可追溯。
3. 执行承接：关联销售规划和活动，缺失项用明确入口补齐；不把原模块整张表复制过来。

打法阅读用 DS Drawer；需要长内容编辑时进入编辑页，不在窄抽屉里塞完整复杂表单。
市场名称点击有 hover 字色变化，不使用下划线。行菜单提供查看客户、查看证据、调整选择、
查看历史等有实际结果的操作，无权限或状态不允许时不显示伪可用项。

### 6.3 新建和调整

采用一个分组表单：基本信息 → 选择市场 → 配置主攻/验证打法 → 检查。
可分段导航，不要求一次填完四步；草稿先保存最小信息，已填内容保持。
选择市场时显示实时匹配预览、资料不足与排除原因；有市场库维护权才提供新建定义。
修改共享市场定义是独立保存动作，不在保存战略时隐式修改全库。

批准最小条件：方向、周期、负责人、至少一个主攻或验证市场、该市场的客群条件/显式名单、
选择理由、打法与验证负责人齐备。没有市场样本可以批准验证战略，不强制已有商机或成交。
关键读取失败需先解决再批准；已明确为零的业务事实不阻止验证。

### 6.4 视觉纪律

- 沿用 DS ViewHeader、Tabs、ListCard/DataTable、Drawer、DetailList、Field 与 Tooltip。
- 页级操作 32px、局部操作 24px；操作行 12px，重点按钮 14px；三点按钮 32px，图标按 DS token。
- 序号和操作列各 64px、居中，序号列头不显示 `#`；保留表格前后留白。
- 主标题、市场组、检查/详情面板的标题图标不重复；图标使用 DS，避免给每条内容增加装饰图标。
- 表格不承载段落；支持卡/列表只在对象浏览有价值时提供，不强迫每个视图两套布局。
- 保持壳层现有外缘/侧栏留白和底部安全区；700/1024px 与助手展开时不产生整页横向溢出。
- 空态保留新建/复用入口；无数据、未设置、资料不足、无权限、读取失败各自表达。

## 7. 指标、归因与证据

### 7.1 可展示与不可混算的数值

| 指标 | 推荐定义 | 必须展示的限制 |
| --- | --- | --- |
| 库内匹配客户 | 当前权限范围内，满足市场条件的不同 account ID 数 | 仅是当前客户库，不是外部市场总量；多个市场合计取并集 |
| 已纳入客户 | 当前战略版本人工纳入、且可读取的不同客户数 | 与动态候选区分；发布后不因规则变化静默移除 |
| 已触达客户 | 纳入客户中，观察期有有效跟进证据的去重客户数 | 联系人存在不等于触达；须显示跟进定义和截止日期 |
| 客群内商机储备 | 属于所选客户集合、观察时点仍开放的商机金额 | 这是业务分布；不能称本战略创造，按币种分开 |
| 明确归因商机 | 商机显式 plan_id 或既定 campaign 链指向战略的商机 | 同一商机多条有效路径只计一次；冲突链单列待核对 |
| 成交与赢率 | 周期内实际关闭的合规商机；赢率为 won/(won+lost) | 放弃单单列；给出样本量，样本稀少不作稳定结论 |
| 验证结果 | 对照批准时的验证问题、阈值和明确证据 | 只能标为待验证/支持/不支持/证据不足，不从时间先后推因果 |

明确定义「业务分布」与「明确归因」两种口径，界面默认给出一种并说明，不能在同一个数字
里混用。共享客户、重叠市场、同一商机在总览均按 ID 去重；跨战略归因冲突不能随意选第一条。
创建后不可改的 campaign/source 等归因键保持原规则，当前匹配不能倒写历史来源。

区域、公司目标的达成由承诺达成提供入口与摘要，战略页不再自建区域实际/目标计算。
观察期内成交与当前开放储备有不同时间语义，不能把季度储备相加当作年度新增商机。
全生命周期统计只用于历史视图；期内指标用规范日期边界。旧自由文本 FY 周期不猜财年。

TAM/SAM/SOM 留作可选的有来源估算：只有负责人提供外部总体、范围、单位价值、日期和
估算方法后才显示区间，并标为估算；库内客户数乘平均客单价不能包装成 TAM。
资源和可达范围不足时不自动推导 SOM，首期不把市场规模估算作为必填项。

### 7.2 助手的职责

首批任务为解释匹配原因、比较市场、提出验证问题、整理有来源的打法草稿、复盘假设。
每条建议包含当前战略/版本/范围/时点、依据链接和未知项。规则检查与模型判断分开展示。
助手可建议调整主攻顺序，但不能未经授权修改市场规则、批准版本、客户级别或销售配额。
新接口沿用现有三档操作授权与建议裁决，不新建策略开关或商业能力键。
模型不可用时，列表、条件匹配、批准、检查和事实验证仍可操作，不输出假分析。

## 8. 权益、权限与跨模块交接

`strategy.plan` 与 `strategy.segment` 仍分别检查；单一入口不意味着自动解锁两者。
入口可由任一可访问内部功能承接：只有市场库权限时直接打开市场库；只有战略权限时不
下发完整市场定义。批准者若不能读取关键选定市场依据，应提示需要相应访问权，不能盲批。
客户、商机、目录、活动、规划各走自己的服务和数据范围，客户端 ID 不扩大授权。
旧快照只带 workspace/对象 ID 的访问模式需要补齐对象范围校验，不能从趋势绕过权限。

| 交接方向 | 行为与边界 |
| --- | --- |
| 战略 → 销售规划 | 查看或关联现有规划，提出市场投入依据；正式配额仍在规划编辑和发布 |
| 战略 → 营销活动 | 新建页预填战略/选定市场，服务端验证 active 状态与所选关系 |
| 市场 → 客户 | 打开带明确条件的客户清单，查看或人工选定；不另造客户创建面板 |
| 市场 → 商机智探 | 传递市场规则与关注方向；没有外部数据时不承诺全网市场覆盖 |
| 战略 → 解决方案 | 引用现有方案；维护跳到原页面，保留战略草稿 |
| 执行 → 战略 | 只读汇总明确引用，缺引用标为未建立关联，不自动归因 |

现有规划聚合没有策略修订引用，完整交接需要显式关系或 D1 持有的引用记录；不能把
sales_target.plan_id 或规划版本号挪作另一种 ID，不能声称首期已经完成自动同步。

## 9. 路由、存量与实施范围

- Launcher 移除独立 segment 行，保留内部注册与原权益升级目标，合并统计不重复计数。
- `/segment` → `/strategy?view=markets`，保留搜索、状态及有效市场定位参数。
- 原新建/编辑入口映射到新的市场编辑位置；未知编辑 ID 返回明确失效状态，不默默新建。
- 战略详情用稳定 ID；原 `/strategy/new?no=...` 解析旧编码后跳转，保留创建入口。
- 原 `/strategy-diag` 暂保留大屏入口；先修口径，再与工作区共用合规读模型，不能先把旧图搬进来。
- 回收旧模板、只服务旧页面的装配代码和重复文案；保留被客户 ICP、活动及其他业务引用的领域能力。
- 旧战略只迁移有依据的数据；缺打法或版本的记录标为历史简版，不补造理由、不宣称曾冻结。

推荐分两批交付，避免先上线一个只换菜单的空壳：

1. 基础与入口：修正规模保存/检查及统计口径，统一工作区、市场库、客户预览、检查抽屉、
   旧链接兼容和门禁；只展示现有可验证字段。该批不能宣称完整战略闭环已完成。
2. 业务闭环：市场复用关系、版本冻结、进入打法、验证安排、规划/活动交接与助手证据。
   随模型和必要数据库契约一起交付，达到本文目标后再作为整合完成验收。

## 10. 验收场景与演示

推荐内存演示：2027 年「华东制造业新客突破」与「制造业存量扩展」复用一个大型制造业市场，
分别采用新客方案与增购方案。包括主攻/验证/暂缓市场、规模缺失客户、已明确排除客户、
交叉匹配客户、无成交的新市场和一笔外币商机；演示数据明确标注，不写真实业务库。

核心验收：

1. 输入行业/规模/地域，经 Server Action、服务、内存/真实 DB 保存再读取，三个条件均保留。
2. 仅规模条件不误报无条件；未知资料与确定不匹配不同，重叠市场客户合计去重。
3. 两个市场各有不同金额，快照及实时数分别正确；无关商机、外币和越界日期不串入。
4. 同一市场可被两个战略复用，修改其中一份打法或顺序不改变另一份。
5. 战略批准 V1 后改变库内规则/客户资料，V1 依据仍可读；V2 调整显示差异，不覆盖旧归因。
6. 草稿并发编辑、重复批准、网络重试不覆盖他人输入、不产生多个生效版本。
7. 由市场进入活动与规划保留上下文，目标发布和活动执行仍由原模块及原权限负责。
8. 仅有市场库权益、仅有战略权益、客户范围受限、版本访问被撤销均不泄漏跨域明细。
9. 每个菜单有可验证结果；表单取消不落库，失败保留输入，关闭抽屉保留筛选和滚动位置。
10. 无数据可建市场和验证战略；无模型仍有匹配及规则检查，不显示模拟模型结论。
11. 桌面、助手展开、1024/700px 检查标题唯一、操作尺寸、长文本、表格留白和底部安全区。
12. 旧书签、客户 ICP、活动目标市场、商业升级入口、导航数量与调用链守卫均正常。

成功度量优先看首次建立可执行战略所需步骤、市场纳入到活动创建是否可达、复盘证据可追溯率，
以及规则保存/统计正确率。试点后再评估业务收益，不以没有对照的数据宣称提升赢率。
