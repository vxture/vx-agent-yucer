# ADR-025 - 里程碑是收款关口，不是工作包

- 状态：**已接受**（owner 裁定 2026-09-06）
- 日期：2026-09-06
- 落地：`incr/0032_milestone_as_commercial_gate.sql` 及其规则层、服务层、表单
- 相关：ADR-002（域的形状）、ADR-003（机器提议、人裁决）、
  ADR-014（金额与明细一致）、ADR-022（这个产品不做交付管理）

## 背景

owner 的裁定原话：

> 按照市场管理的视角，不是研发管理的视角，设定里程碑。后续的项目回款是关联这个里程碑的，
> 不是凭空来的。因此里程碑的设定，调整，变更，需要一套流程，里程碑的信息也需要重构。

`yucer_delivery.project_milestone` 从 baseline 起只有五个字段：
`name` / `sequence` / `due_at` / `completed_at` / `status`。

这是一个**工作包**的形状：一件事、打算什么时候做完、做完没有。它能回答"进度到哪了"，
回答不了任何一个商业问题。而 `revenue_schedule.milestone_id` 从 baseline 起就存在、
可空、**从来没有一行代码写过它**——于是每一笔回款的日期都是有人手打的。

三个缺陷，各自对应一条现在已经不成立的假设。

### 缺陷一：一个能随手改的日期，不是承诺

`due_at` 单独存在时**不可能晚**。改它就是把靶子挪走，所以一个拖了六周、分三次改期的项目，
在**每一个时刻**看都是准时的；延误只存在于还记得第一个日期的那个人脑子里。

### 缺陷二：内部完工 ≠ 客户认账

`status = 'done'` 是我们这边说的。发票能不能开、钱该不该到，取决于**客户签没签字**。
把这两件事压进一个状态，等于让"活干完了"自动读作"这笔钱可以收了"。

### 缺陷三：回款凭空排期

`milestone_id` 可空且无人写。回款计划的日期于是与交付计划**没有任何结构性联系**——
关口延后，钱的日期纹丝不动，两张表各自讲一个故事。

## 决定

里程碑是**合同上的收款/验收关口**。三件事同时落到数据库上。

### 一、`baseline_due_at`：承诺日，不可改

新增一列，记录**首次写下这个关口时承诺的日期**。它**不在 UPDATE 授权名单里**——
不是靠约定，是靠 `98_column_locks` 的列级 GRANT，服务角色改不动它，写错代码也改不动。

于是"晚了多久"变成**减法**，而不是记忆。

`milestoneSlippage()` 返回 `null` 而不是 `0` 表示"没有承诺过"：
"从没定过日期"和"正好卡在承诺日上"是相反的两个读数，都显示 0 会让一个没有计划的项目
看起来计划得很好。

### 二、验收三列：我们记录，不是客户操作

`accepted_at` / `accepted_by` / `acceptance_recorded_by_sub`。

**客户不使用这个系统，也不会被要求使用**：没有客户门户、没有邀请、没有签名采集。
`accepted_by` 是客户方签字人的**名字**，由我们自己的人写下来；
`acceptance_recorded_by_sub` 是我们这边录入的人。这和 `account.record` 是同一个形状——
记录发生了什么，不等于对方在操作什么。

两条 CHECK 兜底：三列同时有或同时无；`accepted_at` 只能出现在 `status = 'done'` 的关口上。
反方向是允许的——**已完成但未验收**正是等签字的常态，也正是这两件事必须是两列的原因。

### 三、绑定：每笔回款都要说清是哪个关口放的款

`revenue_schedule.milestone_id` 改为 `NOT NULL`。两项配套让它成为**保证**而不是愿望：

| 改动 | 拦住的事 |
|------|----------|
| 外键改为**复合** `(milestone_id, project_id)`，指向新的 `UNIQUE (id, project_id)` | 甲项目的回款挂到乙项目的关口上——单列外键两边都能通过，钱会被别人合同里的关口放出去 |
| `ON DELETE SET NULL` 改为 `RESTRICT` | 悄悄删掉一个还挂着钱的关口。SET NULL 配 NOT NULL 本身也是个会在最坏时刻爆的矛盾 |

### 四、变更流程：`milestone_change`，只增不改

一次改动一条记录，带 `reason`（`NOT NULL` 且 CHECK 非空白）、改动人、前值后值。
**没有 UPDATE 授权，也没有 DELETE 授权**——沿用本产品对
`account_relation` / `opportunity_stage_event` / `forecast_snapshot` / `agent_message`
的同一条护栏：更正是新增一行。

**只记计划，不记工作。** `field` 的 CHECK 只允许 `name` 和 `due_at`。
状态从 pending 走到 in_progress 再到 done 是关口在被推进，不是承诺在被改动；
每一步都要写理由，只会把这张表填满"开始了"。工作的历史已经在
status / completed_at / 验收三列里。

规则层对应地**只在计划真的动了时**才要求理由，并且**整笔编辑一起被拒**——
一个动了、历史却没写上的里程碑，比没动更糟：行和日志会互相否认。

## 后果

- 交付计划卡片现在多说三件事：偏离承诺多少天、客户签没签、改过几次和最后一次为什么。
- 里程碑表单变成了**编辑面**，因此必须整条载入。第一次实测就暴露了这个类别的缺陷：
  只载入了名称和日期，保存时把状态从"进行中"写回了"未开始"；补齐后又发现验收信息同样会被
  抹掉。**表单不载入的字段，就是表单会用默认值覆盖掉的字段。**
- demo fixture 里最后一笔"没有关口的回款"补上了它一直隐含在等的那个关口。
- 没有新增权限键。"记录客户验收"沿用 `delivery.write`；若日后认为签收该与改计划分权，
  那是一次独立的权限增量（权限本来就不冻结），不在本 ADR 内。
- 特性键仍冻结在 19 个，本次不涉及。

## 被否决的做法

- **不加基线，只留变更记录。** 能查出改过几次，回答不了"比最初承诺晚了多少"——
  而后者才是市场管理要的那个数。
- **让 `milestone_id` 保持可空、只在挂上时约束。** 改动最小，但"凭空排期"的口子原样保留，
  而这正是 owner 点名要堵的。
- **未验收就禁止开票。** 越界了。owner 采纳的是"未验收的关口，其回款不进入即将到账"——
  一个**读数**，不是一道硬闸；预付款在签约时开票是正常业务，硬闸会把它一起拦掉。
