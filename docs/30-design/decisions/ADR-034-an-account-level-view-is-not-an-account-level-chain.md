# ADR-034 - 账户级的是一个汇总视图，不是一条账户级的决策链

- 状态：**提议中，待 owner 裁定**（草拟 2026-09-21）
- 日期：2026-09-21
- 相关：ADR-013（客户经营是另一种作业方式，单位是一家客户）、
  ADR-024（决策链按商机存，账户级单一答案是缺陷）、ADR-018（证据面）

## 背景

客户详情页侧栏的"决策链"卡片，目前只能进入某一个**商机**自己的决策链
（`decisionChainsByOpportunity`，ADR-024）。owner 直接反馈：这里"缺少企业级决策链，
现在显示的是项目/商机决策链"——销售想在打开任何一个商机之前，先看一眼"这整个客户，
我们到底触达了多少人、经济决策人覆盖情况怎么样"，而不是必须先选一个商机才能看到任何
决策链信息。

**ADR-024 把这件事当缺陷删掉过一次**，理由完全成立且不需要重新论证：采购角色
(`buying_role`) 是"这个人在这一单里是什么"，不是这个人的全局属性——同一个人在 A 单
是经济决策人，在 B 单可能只是使用者，这是 Miller-Heiman 方法论本身的定义，不是这个
产品的偏好。种子数据也已经具体做出了这个反例（`acc_demo_2` 的两单，同一批人不同
角色）。**这条不重新讨论，本 ADR 完全接受。**

但 ADR-024 解决的是"数据存在哪"（`opportunity_contact`，按单），没有回答"客户详情页
要不要有一个跨商机的汇总视图"——这是两个不同层次的问题，前者是 schema，后者是页面。
ADR-013 已经承认账户本身是一个独立的经营单位（客户经营计划），所以"这个账户整体覆盖
得怎么样"是一个真实存在、值得回答的问题，只是**答案不能靠给一个人分配单一角色来给**，
那样就是把 ADR-024 删掉的缺陷原样建回来。

## 决策

### 1. 不新增账户级决策链，新增一个跨商机的只读汇总

**没有新表, 没有新列, 没有 schema 改动。** `opportunity_contact` 仍然是采购角色的唯一
来源（ADR-024 第 3 条不变）。新增一个服务函数（暂名 `accountChainCoverage`），输入这个
账户的全部开放商机，对每一个调 `decisionChainsByOpportunity` 已经在做的同一次分析
(`analyzeChain`)，然后按人聚合结果——**聚合的是"这个人出现在哪些单、每一单是什么角色"
这份清单，不是把多个角色合并成一个**。

```
{
  personId,
  name,
  // 每一单一条, 角色互相独立, 不合并、不取"最新"或"最高"的那一个
  roles: [{ opportunityId, opportunityName, buyingRole, reachable }],
}[]
```

同一个人在 A 单是 economic、在 B 单是 user，两条都原样列出——这正是 ADR-024 要求
保留的信息，汇总视图只是换一个入口把它们放在一起看，不是把两条压成一条。

### 2. 汇总卡片回答的是覆盖面的问题，不是"谁是决策人"

卡片本身只回答三类聚合问题，都是"数出来"而不是"判断出来"：

- 这个账户当前有几个开放商机、各自有没有决策链数据。
- 跨这些商机，一共触达了几个不同的人（去重, 用 `person.id`）。
- 有几个商机的经济决策人不可达（`coverage.economicBuyerUnreachable`，直接读
  `analyzeChain` 已经算好的字段，不重新判断）。

**不回答"这个客户的经济决策人是谁"**——那个问题在 ADR-024 里已经被证明没有单一答案，
汇总视图如果硬造一个，就是用页面把 ADR-024 删掉的东西偷偷放回来。

### 3. 父子账户仍然不共享（ADR-024 第 4 条不变）

这个汇总只在**这一个** `account_id` 的开放商机范围内聚合，不跨 `parent_id` 向上或向下
合并。子公司的覆盖面是子公司自己的问题。

### 4. UI 落点：卡片顶部新增一行汇总, 不是新增一张卡

具体形态留给实现时定，但方向是"决策链"卡片自己的标题下面加一行统计
（例如"3 个开放商机 · 已触达 7 人 · 2 单经济决策人未触达"），点开的仍然是某个商机自己
的决策链——汇总是导读，不是又一层要点开的详情。

## 这条 ADR 不决定什么

**不改变 `buying_role` 的存储位置或语义。** ADR-024 第 3 条原样有效。

**不新增"账户级角色"这个概念。** 一个人对这个账户没有全局角色，只有对每一单各自的角色
——本 ADR 的汇总函数只读不写，也不产生任何暗示"这个人=经济决策人"的账户级字段。

**不解决" 没有开放商机的账户看什么"。** 那种账户没有采购委员会（ADR-024 已经说过），
汇总视图对它就是空状态，不是本 ADR 要发明的新事实。

## 代价，如实写

- **一个新的服务函数**，复用 `decisionChainsByOpportunity` 已经在算的
  `analyzeChain`/`chainForOpportunity`，不是重新实现一遍决策链分析——多花的是"按人合并
  展示清单"这一层，量不大。
- **一张新的小卡片/一行新的统计**，不是新的路由或新的权限维度：读权限仍然是
  `account.graph.view`，跟 `decisionChainsByOpportunity` 完全一样，不新增网关。
- **"去重算人数"需要按 `person.id`**，如果这个人在两单里对应的是同一个 `person.id`
  （ADR-024 保证了这一点），去重是免费的；如果某处还有旧的按 `contact.id` 字符串比较
  而不是按同一个人的 id，去重会静默算错，需要在实现时核对。

## 顺序

这条 ADR 被接受之后才能开始写代码——跟 ADR-024 自己"先确认这个问题还没有答案"是同一个
纪律：本文档就是那次确认，owner 裁定通过之前，不新增 `accountChainCoverage`，也不改
`OrgUnitPanel`/`ChainSummaryList` 之外的任何决策链相关文件。
