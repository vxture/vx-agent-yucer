# ADR-010 - 后台作业面：内部令牌路由 + 外部定时器

- 状态：已接受
- 日期：2026-08-16

## 背景

证据层引入了几件**必须按时间发生**的事,而本仓**没有任何周期性作业面**：

- 承诺到期扫描（`due_at` 过去而未关闭 → `missed`）
- 判断失效扫描（`valid_until` 过期 → `stale`）
- 提案过期（`agent_action` 长期未裁决）
- 结果回填（成交/丢单后自动写 `assessment_outcome`）

今天仓里唯一的作业形态是 `/api/usage/flush` —— 一条由**外部定时器**调用的、**内部令牌
门控**的路由。除此之外只有标签触发的部署和一条 CodeQL cron,`docker-compose.yml` 里
没有 worker 容器。

编号跳过 007-009：那三份属于知识与判断层（二期前裁定),本 ADR 是一期前置,先落号以免
后写的增量引用一个不存在的编号。ADR 编号**只追加、不重排**,跳号是允许的。

## 候选方案

1. **新增 worker 容器**。能力最强,但引入一个新的部署单元、一套新的健康检查、以及
   "worker 挂了但 app 还活着"这类新故障形态。
2. **应用内定时器**(`setInterval`)。零部署成本,但每个副本各跑一份,扩容即重复执行,
   且部署重启会静默丢掉一个周期。
3. **复用 `/api/usage/flush` 的形态**：内部令牌路由 + 外部定时器（本 ADR 采纳）。

## 决策

周期性作业**一律实现为内部令牌门控的路由**,由**平台侧/宿主机的定时器**调用。
不新增 worker 容器,不使用应用内定时器。

每类作业一条路由,门控方式与 `/api/usage/flush` 一致（`INTERNAL_JOB_TOKEN`）。

## 理由

这个形态在本仓**已经被证明可用**,而且它把"什么时候跑"放在应用之外 —— 这正确：
调度是运维关心的事,不是产品代码该持有的状态。副本数变化不影响语义,重启不丢周期,
可观测性沿用已有的路由日志。

代价是**每条作业都要显式建路由**,不能像 worker 那样注册一个函数就完事。这个摩擦是
可接受的：作业是有权限的写路径,应该显式而不是方便。

## 后果：没有成员主体的作业,怎么过两道门

这是本 ADR 真正需要裁定的部分,也是最容易被含糊过去的地方。

两道门（权益 → 权限）都假设有一个**成员**在发起动作。定时作业没有。绝不能因此
**放宽门控公式** —— 那会让"作业"成为绕过授权的通用后门。

规则：

1. 作业以一个**具名系统主体**运行（`sub` 形如 `svc:commitment-sweep`),它**不是**
   `local_authz.member`,也永远不会出现在成员列表里。
2. 它的权限是一个**枚举的、写死在代码里的集合**,不来自角色目录 —— 系统主体不持有
   角色,因为角色是发给人的。
3. **权益门照常求值**：作业代表某个工作区做事,该工作区没买这个能力,作业就不做。
   一个未订阅的工作区不应该因为"是后台跑的"而获得付费能力。
4. 作业**只能做扫描与状态推进**（承诺逾期、判断失效、提案过期),**不得**代表任何人
   做业务写入。业务写入仍然要经 `agent_action` 由人签章 —— ADR-003 不因作业而松动。
5. 每次运行**记账**：处理了多少行、跳过多少、失败多少,写进日志。一个静默失败的
   清扫作业,比没有清扫作业更糟 —— 它会让所有人以为逾期承诺已经被标记了。
