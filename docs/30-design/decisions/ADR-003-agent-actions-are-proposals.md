# ADR-003 - 智能体的写操作一律是「可审阅提案」

- 状态：已接受
- 日期：2026-08-12

## 背景

yucer 是「超级智能体」，D8 横切八域，天然具备直接改写业务数据的能力：推进商机阶段、
调整预测、改客户健康度、创建交付任务。问题是：**智能体应该直接写，还是先提案？**

销售数据是业绩数据。业绩数据被自动改写而没人知道是谁改的、为什么改，会直接摧毁
组织对这套系统的信任——一旦销售不信任商机数据，他们就会退回到自己的 Excel，产品
的全链路价值随之归零。

## 候选方案

1. **直接写 + 事后审计日志**。体验最顺，但「审计日志」在实践中没人看；且模型当时
   的判断依据通常不会被完整记录。
2. **全部人工确认**。最安全，但智能体退化成建议弹窗，规模化场景（成百上千条信号
   评分）不可用。
3. **提案 + 人类落章，自动执行作为最高档位的显式授权**（本 ADR 采纳）。

## 决策

智能体的一切写操作以 `agent_action` 的形式先提案，生命周期：

```
proposed ──> accepted ──> executed
    │           │             └─> failed
    │           └─> rejected
    └─> expired（超时未决）
```

四条硬约束：

1. `accepted` **必须**有人类 `decided_by_sub` 与 `decided_at`。没有人落章就不存在
   accepted。
2. 提案内容（`payload` / `rationale` / `confidence`）**创建后不可篡改**，由
   `98_column_locks.sql` 在数据库层强制（只授出 `status` / `decided_by_sub` /
   `decided_at` / `executed_at` / `updated_at` 的 UPDATE 权限）。
3. 自动执行只在**两道门同时通过**时开启：权益档位含 `copilot.autopilot`（enterprise）
   **且**成员持有 `copilot.autopilot` 权限（默认仅 `sales_leader`）。此时
   `proposed -> executed` 可跳过人工确认，但仍写完整记录，`decided_by_sub` 留空以
   明确标记「这是自动执行的」。
4. 提案超时置 `expired`，**不得静默消失**。

## 理由

- **可审计性是结构属性而非流程要求**：因为提案内容在 DB 层不可写，「智能体当时到底
  建议了什么」永远可回溯，而不是「现在看起来建议了什么」。方案 1 的事后日志做不到
  这一点——日志和数据是两套东西，会漂移。
- **规模化问题由分级授权解决，而不是由放弃留痕解决**：需要批量自动化的组织走
  enterprise 档位显式授权，其代价是明确的商业选择，而不是默认行为。
- **`decided_by_sub` 留空作为自动执行的标记**，比新增一个 `is_auto` 布尔更难被绕过：
  它和「谁批准的」是同一个字段，读数据的人不可能忽略它。

## 后果

- 正面：人机边界成为产品的可宣称属性；审计与合规问题在架构层就已回答；赢丢复盘等
  学习闭环拿到的是「建议 + 人类决策」成对数据，是训练与评估的高质量素材。
- 负面：所有域的写路径都要经过提案编排，实现成本高于直接写。批量场景（如一次给
  500 条信号评分）需要设计批量裁决交互，否则人工确认会成为瓶颈——这一点列为批次 3
  的显式设计任务。
- `agent_action` 表增长快，是 `yucer_agent` 独立 schema 的理由之一
  （见 [ADR-002](ADR-002-five-schemas-for-eight-domains.md)）。
