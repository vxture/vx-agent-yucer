# ADR-018 - 证据面不单独售卖，但记录不等于编辑

- 状态：accepted
- 日期：2026-08-26
- 相关：ADR-006（证据面独立 schema）、ADR-012（一期带杀死判据）、ADR-017（目录分区）

## 背景

ADR-006 建了证据面（`yucer_field`：interaction / interaction_participant /
commitment），并写明新增两个功能键 `account.interaction` / `account.commitment`。
**两个都没加。**

于是整个证据面从建成起就挂在 `account.upsert` 上——功能键 `account.manage`、
权限 `account.write`。这不是有人裁定的，是漏掉键的副作用。

2026-08-26 owner 裁定：**19 个功能键是完整的商业面**。所以这个缺口不能靠加键解决，
必须转成一次显式裁定。查的时候发现它其实是**两个**问题，一个应该维持，一个必须修。

## 决策一：权益 —— 维持现状，并把它变成裁定

**证据面不带自己的功能键，随免费的 `account.manage` 提供。**

理由不是省事，是杀死判据的有效性。ADR-012 用 `/admin/adoption` 的覆盖率读数决定
判断层建不建；如果采集被关在 pro 档后面，那张表测的就不再是**习惯有没有形成**，
而是**愿不愿意付钱**——两个完全不同的量，而后者回答不了「该不该建二期」。

第二条理由更基本：**采集是判断的前提**。没有记录就没有判断，而判断是这个产品本身。
把前提关在门后等于把产品关在门后。

成本敞口据实说明：免费档工作区可以无限量记录跟进。约束落在平台的用量通道
（C3，`local_usage`）而不是产品的档位——若那不够，那是一次平台侧的对话，
不是把采集收费的理由。

## 决策二：权限 —— 新增 `account.record`

**记录发生了什么，不等于编辑客户档案。**

`account.write` 只有三个角色持有，后果是：

| 角色 | 见客户吗 | 改动前能否记一笔 |
|------|---------|-----------------|
| 交付经理 | 天天见，且握着大部分交付侧承诺 | **不能** |
| 市场经理 | 战役带来的对话由他产生 | **不能** |
| 销售负责人 / 销售代表 / 售前 | 是 | 能 |

**交付经理坐在客户会议里却写不下这件事发生过**——而交付经理通常是最先发现客户
沉默的人。这两个洞正开在杀死判据要读的那份证据上，而 ADR-006 的全部前提是
「记录必须是完整的」。

新增 `account.record`，授予上表前五个角色。
**不给 `sales_ops`**（运营不见客户）**，不给 `viewer`**（只读按定义就是只读）。

三条采集动作改挂新权限：`account.interaction.record` /
`account.commitment.upsert` / `account.commitment.settle`，
功能键仍是 `account.manage`（决策一）。

## 后果

- 权限 23 → 24，授权 79 → 84（`incr/0011`）
- 功能键**不变，仍是 19**
- 新增 3 条 action；`field-service.ts` 三处写入门重新指向
- ADR-006 那两个功能键**正式作废**，本 ADR 取代它们那一段

## 这次留下的判据

ADR-017 记过「已裁定 ≠ 已执行」。这一条补它的另一半：
**一次没执行的裁定，会在别处长出一个没人裁定过的默认值。**

ADR-006 漏掉两个键，产生的不是「缺功能」——是两个**从没被讨论过的既成事实**：
证据面免费（碰巧是对的），以及交付经理不能记录（明确是错的）。
两者都不是任何人的决定，都是空缺自己填上的。

因此收尾检查要问的不只是「ADR 说要加的东西加了没有」，还要问
**「没加的那部分，现在实际落在什么行为上」**——空缺从不真的空着。
