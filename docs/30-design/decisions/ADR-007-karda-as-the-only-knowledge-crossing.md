# ADR-007 - 知识只经 karda；在契约发布前，本仓不写任何 karda 代码

- 状态：已接受（作用域限于「消费侧立场」，非接口裁定）
- 日期：2026-08-16

**这条 ADR 的直接后果是「什么都不发」。** 它不是一份接入设计，是一份把「先不接」
写下来的决定，以及把为什么不接、以及接的时候必须守住什么，一并固定下来。

## 背景

owner 于 2026-08-16 指示：知识库部分需要链接 karda，这是所有 agent 都要链接的平台，
用于实现跨 agent 知识共享。

这个方向本身没有疑问。有疑问的是**现在能做到哪一步**。

对照 ADR-004 就能看清差距。那条 ADR 之所以能同时落两个客户端，是因为 Atlas 与 Runos
**已经有已发布的契约**——它能写出 `Atlas v0.8.0`、`Runos v0.5.0`，能引用平台侧的
`Runos ADR-006 / ADR-009 / ADR-010`，能说清 `endpointCode` 路由语义、失败转移链归属、
四工具面的错误分层。karda 目前**没有任何一项对应物**：没有版本号，没有端点语义，没有
错误码表，没有读者集合模型，没有留存与撤回模型。

`CLAUDE.md` 的规矩是：标准缺口先在平台仓修，不得在产品仓自造。

## 一次已被丢弃的尝试（必须记下来，否则会有人再写一遍）

2026-08-15 本仓曾写过一版 karda 接入：`platform/karda/{types,redact,client}.ts`，
三个文件，含一个「主张可外发、证据不可外发」的边界模块。**它已被整体丢弃**，原因不是
风格，是一次独立对抗审查（四视角 + 独立质疑者，62 个 agent）确认的实测结果：

那个 137 行的边界文件，唯一职责是「做披露决定的唯一一处」，却被查出**至少四条各自
独立的客户名称越界路径**：

1. `knownNames`（最强的一道检查）通过 `KnowledgePlane` 端口**结构上不可达**——
   端口签名里根本没有那个参数，而所有调用点都被要求依赖端口；
2. `derivedFrom` 原样外发，从不校验；它唯一的校验器 `isLocalPointer` 既是死代码，
   又是按 `acc_` / `opp_` 前缀写的，而本仓 `00_baseline.sql` 里每个主键都是
   `gen_random_uuid()`——该检查在真实数据上**永远不会命中**；
3. facet 的**键**从不检查（只检查值），键里放个名字就绕过了；
4. 正则集是照着测试夹具调的，不是照着本产品真实的中文文案调的。

外加：该模块从未编译通过（`client.ts:137` 一处 `TS2554`，是全仓唯一的 tsc 错误，
**硬失败 `build` 这条必需检查**），无测试，无 ADR，无联络函，源文件含非 ASCII 字符。

这不是一份 bug 清单，是**同一个设计错误被报告了十一次**：在不知道受众、不知道留存
模型、不知道撤回模型、且没有任何一个真实调用方的情况下，去规定一条对外披露边界。

**教训要写进这里**：可以把「线格式的猜测」隔离在一个适配器里；**不可以**把「不属于
自己的词汇表」隔离起来。当年那版代码自造了 `KNOWLEDGE_KINDS`、`KNOWLEDGE_SCOPES`、
`KnowledgeClaim`、`KnowledgeItem`——一个本仓并不拥有的领域的词汇表——然后把一条
不可逆的披露边界挂在上面。猜错时，端口错、边界规则错、所有建在其上的调用点全错，
传输层隔离救不回来。

## 决策

### 1. 作用域：本 ADR 只裁定「消费侧立场」

**yucer 不自建第二个跨 agent 知识存储。** 不建本地跨产品知识表，不建本地向量检索，
不与兄弟产品点对点交换知识。跨 agent 知识的出入口只有 karda。

这一条完全是 yucer 自己的事，因此可以现在就定。

### 2. 契约不在这里裁定

**平台发布契约之前，本仓不写任何 karda 代码**：没有模块，没有端口，没有类型，没有
`KARDA_*` 环境变量，没有 `lib/status.ts` 条目，没有调用点。**「没有」就是当前状态
本身，不是待补的桩。**

配置键随读它的代码一起发（ADR-004 的既定后果）；没有代码，就没有键。

### 3. 哪些是 yucer 自己的决定，哪些是猜测——分开列

**是 yucer 自己的决定**（源自 ADR-006 与两道门，不依赖 karda 的任何契约）：

- **主张可以跨界，证据不可以。** `yucer_field.*` 永不可外发，一个字段都不行。那个
  schema 存在的理由就是它装着关于自然人的原话，而那些人从没跟我们签过任何东西。
- **进来的东西是「别的 agent 的主张」，不是事实。** 任何被 yucer 引用进判断的外部
  知识，必须能回答「据谁所说、何时、哪一版」。做不到就不能进判断路径——否则
  「智能体说的」会从侧门重新进来，而 ADR-003 与 ADR-006 正是为堵这个而存在。
- **双门不因跨 agent 而消失**：权益先、权限后，顺序不变。
- **入站文本必须过 ADR-004 的围栏。** 外部知识是从网络进入提示词上下文的第三方文本，
  与 Runos 的 Skill 同类。`renderSkillPrompt` 已经把这套纪律定死了（来源围栏 +
  摘要校验结论渲染在围栏**内**）。karda 内容不走这个形状就不进提示词。

**是对 karda 的猜测**（一律不写进代码，只写进联络函）：受众与读者集合模型、知识条目
的种类与作用域词汇、provenance 字段是否一等公民、是否有内容摘要、是否存在产品侧的
发布方向、留存与撤回语义、鉴权 audience 与 scope 字符串。

### 4. 撤销条件

karda 公布契约之后，**本 ADR 被取代（superseded），而不是朝有利于 yucer 的方向修订**。
两边语义有分歧时，一律以平台侧语义为准。

## 理由

外发是这个领域里**唯一没有撤销键**的动作。入站错了可以删表重来；一条含客户名称的
主张广播出去，就再也收不回来，而受损的是客户的人，不是我们的人。

在受众模型、留存模型、撤回模型三者都未发布的情况下设计外发边界，等于用猜测去约束
一个不可逆动作。上一节那四条越界路径就是这么来的——它们不是马虎，是**在信息不足时
仍然动手**的必然产物。

## 后果

- 本批次 karda 的全部交付物是：这条 ADR，和 `docs/80-liaison/` 里那封联络函。零行代码。
- 联络函第 12 问（karda 是否存在产品侧发布方向）是本方案里**最大的一个分叉**：若
  karda 只是只读分发，`redact.ts` 这类模块就不该以任何形式存在。
- 编号取 007 是刻意的：ADR-010 已把 007-009 预留给「知识与判断层」，karda **就是**
  知识层，占 007 是兑现那条预留，而不是与之相撞；008-009 留给判断那一半。
