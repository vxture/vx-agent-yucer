# ADR-015 - 一个智能体、多种能力：提案带能力键，不带智能体身份

- 状态：已接受
- 日期：2026-08-18

## 背景

一次架构讨论里出现了两种说法：

- **甲**：每个环节一个智能体（战略参谋、关系测绘、交易教练、交付风控……），
  各有专业、各有证据来源、各自提案
- **乙**：一个智能体，在不同场景使用不同的模型与技能

先前的设计材料按甲写过一版，并提议给 `agent_action` 加 `agent_key` 与 `domain`。
**这一版是更正。**

## 证据：这个仓库已经回答了这个问题

`app/agent/atlas/endpoints.ts` 的文件头写着：

> 产品命名**任务**；运营决定哪个模型服务每个任务。

现有抽象：

| 概念 | 值 | 谁拥有 |
|------|----|--------|
| `CopilotTask` | `chat` / `propose` / `score` / `summarize` | 产品 |
| `endpointCode` | `chat/reasoning`、`chat/fast`…… | **运营**，可改指向且不需发版 |
| `applicationId` | `session.id`，Atlas 的**计量分组轴** | 产品 |

也就是说：**不同场景使用不同模型这件事，已经在做了**——提案走推理模型（有人要签字，
值得更强），打分走快模型（批量跑，单价压倒质量）。Runos 侧同样以 `capability_id`
为单位。

**这两个 plane 的设计本身就是「一个 agent 实例 + N 个能力」。**

## 决策

### 1. 一个智能体，不是七个

不建立七个智能体身份。理由有三条，都不是审美问题：

1. **计量会碎。** `applicationId` 是 Atlas 的默认计量分组轴。七个身份就是七条账，
   一次任务的花费再也无法相加。
2. **知识会断。** ADR-007 引入 karda 的**全部目的**是跨 agent 共享知识。
   给每个环节独立记忆，等于跟那条决定对着干。
3. **人的类比在这里不成立。** 人分工是因为一个人装不下所有专业、也不能同时在两处。
   这两个约束对模型都不成立。

### 2. 缺的是能力键，不是身份

现有 `CopilotTask` 是**活的形状**，不是**专业领域**。后果是具体的：

> 交付风险预警和折扣审批，今天都是 `propose`——同一个模型、同一套工具，
> **事后无从区分**。

所以 `agent_action` 增加 **`capability`**：一个稳定的字符串键
（`deal.stall_risk` / `delivery.payment_risk` / `pricing.discount_approval` ……）。
它决定四件事：

- 提示词与专业口径
- 工具集
- 证据检索范围
- 经由 task 落到哪个 endpoint（**模型仍由运营决定**）

### 3. 能力**不**决定谁裁决

裁决人由 `subject_type` 加权限目录推导，与提案来源无关。

把裁决权挂在提案方上，等于让智能体决定谁能否决它自己——这与 ADR-003
「没有人落章就不存在 accepted」是同一条边界。

### 4. `capability` 与 payload 同级不可篡改

它进 `agent_action` 的**冻结集**（与 `payload` / `rationale` / `confidence` 并列），
只能在创建时写入。

理由与 ADR-003 相同：审计要回答「**当时**是哪块能力提的」。
一个事后可改的能力键，会让「这块能力准确率多少」这个问题永远没有可信答案——
而那正是引入这个字段的主要目的之一。

### 5. 它换来的四件事

1. 「待我裁决」能说清等的是**什么**，而不只是一个混在一起的数字
2. **按能力度量准确率**——哪块专业不靠谱，可测
3. **按能力静音**——「交付预警太吵」可以单独关掉，不牵连其余
4. 运营可以把**某一个能力**换到更好的模型，不动其他

## 后果

- 先前材料里的「七个智能体」表述作废。产品对外仍可以叫「参谋」，
  那是**一个**角色的名字，不是七个进程。
- `capability` 可空：历史提案没有这个键，回填是**假的准确率数据**，
  比留空更糟。空值在界面上显示为「未标注」，不显示为某个具体能力。

## 备选方案

**`agent_key` + `domain` 两个字段。** 先前的提议。`domain` 与 `subject_type`
高度重合（提案打在什么对象上基本决定了它属于哪个域），而 `agent_key` 会造出
七个不存在的身份。两个字段的信息量不如一个能力键，还多一份要维护的对应关系。

**只用 `action_type`（现状）。** 它描述**要做什么**（`advance_stage`、
`draft_outreach`），不描述**凭什么专业提出来的**。同一个 `advance_stage`
可能来自阶段停滞分析，也可能来自竞争态势判断，而这两块的准确率应该分开看。
