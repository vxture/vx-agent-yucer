# ADR-014 - 产品体系：行项是权威，商机总额是它的和

- 状态：已接受
- 日期：2026-08-17

## 背景

这个模型说不出**我们在卖什么**。

`00_baseline.sql` 里唯一带 "product" 的东西是平台自己的 `product_code`（yucer 这个产品，
来自 C2 通道）。客户要卖的产品、方案、价目，一个都没有。后果是：

- `opportunity.amount` 是一个**没有构成的数字**。它从哪来、由什么组成，系统不知道
- 合同没有标的，交付没有范围，"卖了没交"这类问题**结构上无法回答**
- 预测只能到金额，到不了产品。"这季度承诺 420 万"说不出其中多少是哪条产品线
- **白地图分析不可能**：说不出一家客户买了什么、没买什么
- 信号匹配只能靠公司名。一条招标公示对应我们哪个产品，判断不了

最后两条正是战略客户（ADR-013）和定向情报挖掘最需要的能力，
所以产品体系不是一个孤立的补充，它是那两件事的前提。

## 决策

### 1. 建一个域，不是给商机加几个字段

新增 schema `yucer_catalog`，五张表：

| 表 | 是什么 |
|----|--------|
| `product` | 单品或服务 |
| `solution` | 组合方案 |
| `solution_item` | 方案 × 产品（含默认数量） |
| `price_book_entry` | 每产品每币种的标价与**底价** |
| `opportunity_line` | 商机的产品行项 |

放进独立 schema 而不是塞进 `yucer_pipeline`：目录是**跨域被引用**的维度——
商机、合同、交付、信号匹配都要读它，而它谁都不写。
按 ADR-002 的口径，这正是一个域该有的形状。

### 2. 行项存在时，行项是权威

这是本 ADR 最要紧的一条，因为它决定了两个数字冲突时信谁。

- 商机**没有**行项时，`opportunity.amount` 就是总额（现存数据都是这样）
- 商机**有**行项时，`amount` 必须等于行项之和

**约束写在服务层，不在 DDL。** 它是跨行的（一个 header 对多个 line），
CHECK 表达不了，触发器会把业务规则藏进数据库。服务层在写行项时重算 header，
并且这是**唯一**允许写 `amount` 的路径——否则两个数字会各自漂移，
而"总额和明细对不上"是这类系统最常见也最难查的一类烂账。

一致性由测试钉住，不靠自觉。

### 3. 底价是价目的理由

`price_book_entry` 带 `list_price` 与 `floor_price`。行项的实际单价低于底价时，
`opportunity_line.needs_approval` 为真。

没有底价，价目表只是一张参考表，存不存在都一样；
有了底价，它才承担一个真实的业务判断——**这一单的折扣要不要人来批**。

这条同时给了智能体一个明确的提案场景：折扣超限时提案走审批，而不是自己放行。

### 4. 行项引用产品，方案是展开的模板

`opportunity_line` 只指向 `product`，**不指向 `solution`**。

方案是**报价时的展开模板**：选一个方案，展开成若干产品行项，此后各行独立。
如果行项能直接挂方案，那么"这单里到底有哪些产品"就有两种答案，
而白地图与产品级预测都要求只有一种。

`solution_id` 作为**来源标记**留在行项上（可空，只读），用来回答
"这些行是从哪个方案展开的"，但计算永远只看产品。

### 5. 目录是工作区级的，不是全局的

每个工作区维护自己的产品目录。这与平台侧的商品目录（C2 的 `product_code`）
**没有任何关系**，也不得混用——一个是"我们这套 SaaS 卖给谁"，
一个是"用这套 SaaS 的公司自己卖什么"。名字撞了，含义相反。

## 后果

- **`opportunity.amount` 的写路径收窄。** 有行项的商机不能再直接改总额，
  只能改行项。这会让现有的 `updateCommercialTerms` 需要区分两种情况。
- **白地图与产品级预测成为可能**，但都要等行项有数据。演示数据同批补上。
- **交付范围回指行项**留到 D7 那一轮，本 ADR 只建目录与商机侧。
  `contract_line` / `delivery_scope` **不在本次范围内**，写在这里是为了说明
  为什么 `opportunity_line` 的主键与冻结口径要按"将来会被引用"来设计。

## 备选方案

**给 `opportunity` 加 `product_codes TEXT[]`。** 最省事，能支持"卖了什么"的粗查询，
但金额无法按产品拆，折扣审批无处安放，白地图只能到"有没有"到不了"多少"。
用一个数组换掉一整个维度，省下的建表成本会在第一次要做产品级预测时全部还回去。

**行项直接引用方案。** 见第 4 条：会让"这单有哪些产品"出现两种答案。
