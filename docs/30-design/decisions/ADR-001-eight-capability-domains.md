# ADR-001 - 产品切成八个能力分区

- 状态：已接受
- 日期：2026-08-12

## 背景

yucer 覆盖「市场战略 -> 销售规划 -> 市场执行 -> 客户管理 -> 商机侦探 -> 商机管理 ->
项目落地 -> 智能助手」全链路。这条链路很长，如果不先定切分维度，代码和数据会按团队
习惯自然裂成「CRM 模块 + 报表模块 + AI 模块」，链路可追溯性会第一个丢失。

## 候选方案

1. **按用户角色切**（销售端/市场端/管理端/交付端）。贴近使用者心智，但同一个业务
   对象会被多个角色写，所有权不清。
2. **按技术分层切**（数据层/服务层/智能层）。工程上整齐，但业务边界完全消失，
   「战略是否落地」这类跨层问题无处安放。
3. **按业务对象所有权切**（本 ADR 采纳）。一个业务对象有且只有一个域可写，其他域
   只读引用。

## 决策

采纳方案 3，切成八个能力分区 D1-D8，定义见 `docs/20-specs/20-capability-domains.md`。
判定规则只有一条：**一个业务对象只能由一个域拥有（可写），其他域只能引用（只读）**。

## 理由

- **所有权清晰**，交接契约就自然清晰：D5 把线索交给 D6 时，`converted_opportunity_id`
  回填是一个明确的接缝，而不是两个模块互相写对方的表。
- **可追溯性成为结构属性而非约定**：因为 `plan_id` / `campaign_id` 是数据上的父子
  关系，「本季度多少商机来自这条战略」是一次 JOIN，不是一次人工统计。
- **域边界可以映射到 schema 边界**，从而可以用 DB 权限（列级写锁）在最底层兜底，
  而不是只靠代码评审。

## 后果

- 正面：归因不依赖人工填写；域可以独立演进；权限与能力矩阵都能按域前缀命名，
  三套命名（feature key / perm_code / schema）保持同构。
- 负面：跨域的写操作必须显式编排（例如商机赢单后建交付项目），不能一把梭。这是
  刻意的成本。
- 八个能力分区并不等于八个 schema，映射关系见 [ADR-002](ADR-002-five-schemas-for-eight-domains.md)。

## 2026-08-26 术语更名 - 「能力域」改称「能力分区」

**只改中文称谓，不改任何裁定。** 八个分区、切分依据（业务对象所有权）、以及由此
派生的权限命名空间、功能键前缀、schema 归属全部不变；英文 capability domain、
本文件名、`DOMAINS` / `Domain` 等标识符也不变——英文里这个词不歧义。

**为什么改。** 2026-08-20 起，界面导航按销售动作的先后另分了**五个功能域**
（战略武备域 / 兵力部署域 / 火力侦察域 / 阵地经营域 / 战果结算域，见 YC-401）。
于是「域」这个字同时指两套东西、还带两个不同的数字，而两者的读者、切分依据和用途
都不同。owner 在读产品现状文档时被绊了一次，裁定：**「域」留给工作场景方向那五个**，
这八个另起一名。

**为什么不是「能力面」。** 那是 Runos 的名字（ADR-004，平台词汇，本仓无权改）。
用它会把一次碰撞换成一次更糟的碰撞。「分区」说的正是这八个是什么——
一次按归属做的划分——且不与「域」「面」两个已占用的词冲突。

**这次更名教的一件事**：产品词汇表和数据模型一样需要唯一性约束。
新造一个分类概念时，先查那个字是不是已经在指别的东西——
本次两处碰撞（域、能力面）都是在动手改之前查出来的，第二处险些改进去。
