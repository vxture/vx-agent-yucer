# ADR-036 - 登录状态只属于 accounts；产品只查询，不定义

- 状态：accepted
- 日期：2026-09-29
- 相关：080-rp（RP 会话）、vxture-platform/vxture-platform#538（按 sid 查询登录状态）、
  #517 / #520（被本决策取代的两次修补）

## 背景

生产反馈：使用约 10 分钟后被要求重新登录，点登录又直接进入。原因在产品侧：
yucer 把几分钟有效的访问令牌当成"是否已登录"的门槛，131 处代码各自判断令牌快过期、
各自去续期。平台的刷新令牌只能用一次，重复使用会吊销整条令牌链，所以只要两个请求
同时续期，所有人就一起掉线。#517（进程内合并续期）和 #520（掉线后静默恢复）都是补丁，
没有回答"谁说了算"。

owner 裁定（2026-09-29）：

1. 同一个人同时使用多个产品，**登录状态只以 accounts 为准**。
2. 产品**不定义任何登录有效期**，不因自己的原因把人登出。
3. 一个产品只有一份登录状态，不是每个板块各查各的。
4. 产品**查询** accounts，不采用推送式登出通知。
5. 产品内的登出是**全局登出**（结束 accounts 的登录）。
6. accounts 的空闲 / 总时限（当时为 4h / 24h）**不是产品的设计依据**，accounts 可随时调整。
   产品只在用户真实操作时报告"在用"，由 accounts 按自己的规则续期。

## 决策

`auth/lib/login-state.ts` 是这件事唯一的实现：

- **一份状态。** Redis 记录（`RpSession`）保存"这是谁（claims 快照）+ 对应哪次 accounts
  登录（sid）+ 下次何时询问 accounts（nextCheckAt）"。所有板块只读它；每次渲染只解析一次
  （`resolveAppSession` 用 React `cache`）。页面判断身份不再触碰令牌。
- **一个询问者。** 到了该问的时候，由 Redis 锁（SET NX，跨进程、跨副本）保证只有一个请求
  去问，并在锁内重新读取记录；其余请求照常使用现有记录，不等待、不询问。
- **只在用户操作时询问。** 页面访问和用户操作会询问；链接预取、状态探针、后台请求只读，
  不会让一个开着的标签页永远不过期。
- **节奏来自 accounts。** 下次询问时间取自 accounts：过渡期用它签发的令牌到期时间，
  #538 落地后用查询接口返回的下次查询时间。代码里的常数只有锁的自解时间和重试节奏，
  都不会导致任何人被登出。
- **状态只在两种情况下结束：** accounts 回答"无效"，或用户主动登出。accounts 没有回答
  （网络、5xx）不等于"无效"，状态保留。
- **令牌只用于代用户调用平台（OBO）。** 按需获取（`accessTokenFor`），在同一把锁下续期；
  续不上只影响那一次调用。
- **登出是全局的。** 结束 accounts 的登录（`end_session`，带 `id_token_hint` 与
  `client_id`），这台电脑上的所有产品在下次询问时都会看到。

"询问 accounts"是一个端口（`LoginAuthority`），两个实现：

- `accountsStatusAuthority`：#538 的按 sid 查询接口，设置 `ACCOUNTS_SESSION_STATUS_URL`
  时启用。请求 / 响应形状是本产品的提议，平台定稿后只改这个适配器。
- `grantAuthority`（过渡）：今天 accounts 在服务端唯一能回答的问题是"续这张授权"。
  消除竞争后，它回答的 `invalid_grant` 才是 accounts 真正的"不"，而不是产品自己绊倒自己。

每一次"状态结束 / 问不到 / 拿不到令牌"都计数并附原因，显示在 `/api/status` 的 `auth` 里。

## 后果

- 过渡期 accounts 若在别处结束了登录，本产品要等到下次到期询问、且用户有操作时才发现
  （由 accounts 签发的令牌时长决定）。#538 落地后由查询接口的下次查询时间决定。
- `RP_SESSION_TTL` 只是 Redis / cookie 的存储清理上限，每次询问成功都会延长，
  不再是登录规则，也不会让一个 accounts 仍然认可的登录结束。
- 身份信息（工作区、角色、账号状态）来自最近一次询问时的快照，最多滞后一个询问周期。
- vx-agent-vxtpl 是同一套代码，需要同步改造。
