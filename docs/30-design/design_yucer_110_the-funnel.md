# design_yucer_110 - 销售漏斗：一条线贯穿到底，每一段都能中途终止

- 状态：**部分落地** —— B、C 两批已完成，A / D / E 待做
- 日期：2026-09-06
- 缘起：owner 2026-09-06 —— 「从线索 到 商机 到项目这是一条完整的销售管理漏斗」，
  「需要贯穿全场-到回款复盘，或者中途终止」
- 相关：ADR-016（定向挖掘与归因冻结）、ADR-003（机器提议、人裁决）、
  ADR-025（里程碑是收款关口）、`design_yucer_100`（能力分区）

## 0. 这份文档要解决什么

漏斗的**数据**已经全在了，五段一段不缺。缺的是三件事：

1. 每一段的**入口条件**散在各处，有的在规则层，有的只在 DDL，有的两边都没有；
2. **中途终止**每一段都能发生，但**没有一段记得下原因**；
3. **复盘只覆盖商机**，而且只覆盖赢和输——被放弃的商机连复盘行都写不进去。

下面先摆事实，再提设计。

## 1. 现状：漏斗五段，逐段核对

| 段 | 表 | 正常出口 | 中途终止 | 终止有原因吗 |
|----|----|----------|----------|--------------|
| 信号 | `yucer_pipeline.signal` | `promoted` → 线索 | `dismissed` / `duplicate` | **无** |
| 线索 | `yucer_pipeline.lead` | `converted` → 商机 | `disqualified` | **无** |
| 商机 | `yucer_pipeline.opportunity` | `won` → 项目 | `lost` / `abandoned` | 赢/输有（`win_loss_review`），**放弃没有** |
| 项目 | `yucer_delivery.project` | `delivered` / `closed` | `cancelled` | **无** |
| 回款 | `yucer_delivery.revenue_schedule` | `settled` | `written_off` | **无** |

链接是真列，不是概念：

```
signal.id ──> lead.signal_id
lead.converted_opportunity_id ──> opportunity.id
opportunity.id <── project.opportunity_id
project.id <── revenue_schedule.project_id ──> project_milestone.id   (ADR-025)
```

### 1.1 五个已确认的缺口

**缺口一：终止原因，五段都没有。** `lead.status = 'disqualified'` 只是一个字，
没有列能回答「为什么」。`project.status = 'cancelled'`、
`revenue_schedule.status = 'written_off'` 同理。一年之后没有人答得出这些是怎么没的，
而这正是漏斗最该回答的问题——**赢的原因都记了，输的原因大部分没记**。

**缺口二：复盘表拦住了放弃的商机。**

```sql
CONSTRAINT chk_win_loss_review_outcome CHECK (outcome IN ('won', 'lost'))
```

`opportunity.status` 允许 `abandoned`，复盘表的 CHECK 不允许。所以一个被放弃的商机
**在数据库层面就写不进复盘**。这不是没人去写，是写不了。

**缺口三：商机的入口条件不足。** `planNewOpportunity` 今天只要两样：名称、客户。
owner 的裁定是**负责人 + 客户 + 项目基本信息/需求**。其中：

- **负责人**：`opportunity.owner_sub` 在 DDL 里**可空**；规则层不检查；
  `createOpportunity` 用 `ownerSub ?? ctx.sub` 兜底。也就是说"必须有负责人"今天是
  **靠兜底实现的巧合**，不是规则——任何绕过这个 service 的路径都能写出无主商机。
- **需求 / 项目基本信息**：**整个 schema 里没有这个字段**。名称、金额、赢率、预计
  关单日期都有，"客户要什么"没有。

**缺口四：线索没有自己的家。** 线索列表今天挂在商机智探页上，而智探是信号的模块。
owner 已经指出这一点。

**缺口五：漏斗没有一处能一眼看全。** 每一段都有自己的页面，没有一个地方回答
"这一批需求从进来到现在，走到哪、漏在哪"。

## 2. 设计

### 2.1 一条原则：每一段有入口闸门，也有出口记录

```
信号 ──升级──> 线索 ──转化──> 商机 ──赢单──> 项目 ──收款──> 回款结清
  │             │             │             │             │
 忽略/判重     判负          输/放弃       取消          核销
  └─────────────┴─────────────┴─────────────┴─────────────┘
                    每一个出口都要有原因
```

**入口闸门**（进入下一段要满足什么）：

| 进入 | 条件 | 今天的状态 |
|------|------|------------|
| 线索 | 信号已评分 | 已有（`score_required`） |
| 商机 | 线索 `qualified` + 有客户 | 已有（`planConversion`） |
| — | 线索**有负责人**才能判定 `qualified` | **2026-09-06 新增，已落地** |
| 商机（自建） | **负责人 + 客户 + 需求** | 客户已有；**负责人和需求要补** |
| 项目 | 商机 `won` | 已有（`project.opportunity_id` 可空，自建项目也允许） |
| 回款 | 挂在里程碑上 | 已有（ADR-025，`milestone_id NOT NULL`） |

### 2.2 终止原因：一张表，还是五个列？

**建议：一张 `funnel_exit` 表，只增不改。**

```
funnel_exit
  id, workspace_id
  stage        signal | lead | opportunity | project | revenue
  subject_id   该段对象的 id
  outcome      dismissed | duplicate | disqualified | lost | abandoned
               | cancelled | written_off
  reason_code  受控词表（价格/需求不匹配/时机/竞争对手/客户放弃/无预算/重复/其他）
  note         自由文本，可空
  decided_by_sub  谁做的决定
  decided_at
```

**为什么是一张表而不是每段加两列。** 漏斗要回答的是**跨段**的问题——"今年的需求，
在哪一段漏得最多、什么原因"。五个列分散在五张表里，那个问题就要五路 UNION 才能问；
一张表按 `stage` 一次 GROUP BY 就出来。而且新增一段（比如未来的"报价"）不需要
再改一次五张表的形状。

**代价，说清楚：** 它是**多态外键**（`subject_id` 指向五张表之一），数据库层面无法
用外键约束住。这是这个仓库到目前为止**没有先例**的做法，需要 owner 明确同意——
换取的是跨段可查。替代方案是五张表各加 `exit_reason` / `exit_note` /
`exited_by_sub`，外键完整、但跨段查询靠 UNION。

**复盘表怎么办。** `win_loss_review` 保留：它记的是**赢输的深度复盘**（竞争对手、
教训），比一个原因码重得多，且只有商机值得。要做的是把它的 CHECK 从
`('won','lost')` 放宽到包含 `abandoned`——一个被放弃的商机同样有教训。

### 2.3 线索的家

**建议：线索独立成模块，放在「战场侦察域」，排在信号和分派之间。**

```
战场侦察域：营销活动 → 商机智探（信号） → 线索 → 线索分派
```

理由：

- **智探是信号的模块**，它的对象是 signal。线索是另一个对象，有自己的生命周期
  （新建/跟进/合格/转化/判负）和自己的闸门。一个页面管两个对象，就是 owner
  指出的那个问题。
- **线索分派不是线索的家**，它是一个**动作**页——只写 `owner_sub`。把生命周期
  塞进去，等于让"谁接"和"值不值得做"共用一张表格。
- 分派可以**保留为独立模块**，也可以收成线索模块里的一个操作。建议**保留独立**：
  分派是团队负责人的活，跟进是一线销售的活，两个人看两个页面。

线索模块承载：列表 + 生命周期动作（跟进/判定合格/判负/转商机）+ 判负原因。

### 2.4 智探要更聪明（owner 明确不砍动作）

现有四个动作保留：升级为线索 / 忽略 / 判重 / 重新评分。可以加的能力，**按投入
从小到大**，全部只提议不自动执行（ADR-003）：

1. **判重靠算，不靠人眼。** 今天 `duplicate` 是人点出来的。同一家公司 + 同一时间
   窗口 + 同一类型的信号，规则可以**提议**判重，人确认。
2. **升级为线索时预填**。信号已经知道公司、来源、评分；线索表单不该再问一遍。
3. **匹配已有客户**。`signal.account_id` 可空——匹配上了才有区域，才分得出去
   （这正是线索分派"无区域"卡点的上游）。规则按公司名提议匹配，人确认。
4. **同一家公司的信号聚合**。三条信号指向同一家公司，比三条孤立信号强得多，
   这是"值得先看"的真实依据，比单条评分更接近判断。
5. **忽略也要留原因**（并入 2.2 的 `funnel_exit`）——否则同一条信号下周又进来，
   没人知道上次为什么放掉。

### 2.5 贯穿全场的那一个视图

漏斗的价值在**跨段**，所以需要一个页面回答：

- 一批需求（按来源/战役/时间）从信号进来，各段现在分别有多少、金额多少；
- 每一段**漏掉**多少，原因分布是什么；
- 从信号到回款的**周期**有多长。

这依赖 2.2 的终止原因先落地——**没有原因，漏斗图只能显示"漏了"，不能显示"为什么漏"**，
而后者才是能改进的那一半。

## 3.1 B 批落地后的两个已知缺口

- **另外四段的界面没接。** `funnel_exit` 接受五段，但只有线索这一段有地方录入原因。
  信号的「忽略」、商机的「输/放弃」、项目的「取消」、回款的「核销」仍然只写状态。
- **多态外键的代价已经付了。** `subject_id` 没有外键，删除线索时由
  `deleteLead` 在同一事务里清掉它的退出记录；其余四段的对象本产品不做物理删除。
  再出现第二张这种形状的表之前，值得先问一次是否有别的解法。
