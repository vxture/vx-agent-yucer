`agent/` 与 `platform/s2s.ts` 是**新增的两条平台集成通道**，与 C1/C2/C3 同属刚性区：
产品域代码调用它们，但不改它们，更不绕过它们直连模型厂商或自建能力目录。理由与
契约细节见 ADR-004。

`auth/`、`entitlement/`、`provisioning/`、`usage/` 四块是平台集成契约面，属于**刚性
区**，不因产品域而改动。产品域代码一律新增在 `domains/` 之下，不侵入这四块。

### UI 层：组织设计系统是唯一来源

产品页面的视觉与交互元件**一律取自组织设计系统**，不自建组件、不复制其源码、
不为了"改一点样式"而 fork 出本地副本。

**装哪两个包，以及为什么 `design-ui` 必须钉死**（2026-08-26，升 9.0.4 时确立）：
应用装 `@vxture/design-system`（伞包，带主题 / 密度 / 字号的运行时接线），版本用
脱字号；但本仓的组件同时直接 import `@vxture/design-ui`（`DataTable`、`Section`
这一族在那里），所以 pnpm 的严格 node_modules 下它**必须也出现在
`package.json`**——未声明的依赖解析不到。

那一条的版本**写精确值，跟伞包 `dependencies` 里的钉法逐字一致**（当前
`"@vxture/design-ui": "6.0.4"`，无脱字号）。写成 `^6.0.0` 的后果实测过：伞包升到
9.0.4 钉了 design-ui 6.0.4，而本仓那条 `^6.0.0` 判定"已满足"、原地不动，于是一棵树
里出现**两份 design-ui**——两个 `Button`、两套 Popover / Tooltip / Fullscreen 的
React context。不报错，只是弹层偶尔不认自己的 provider。精确值让这种分叉变成一次
安装失败，而不是一个跑起来才发现的怪现象。

- 需要 DS 没有的元件时，**先向 DS 提需求**，而不是在本仓造一个。确实必须临时自建的，
  按偏差纪律登记 TD 条目（写明缺失的 DS 元件、临时实现位置、回收条件），不得静默偏离。
- 允许的本地封装只有一种：把 DS 元件与本产品的**域语义**绑定的薄封装（例如把
  DS 的表格封装成"商机管道表"，注入阶段机的列定义）。薄封装不得重写 DS 的视觉。
- 主题与设计令牌以 DS 为准；`@yucer/shared` 的 `brand.ts` 只承载产品标识
  （productCode / displayName / defaultLocale），**不承载颜色、间距、字体**。

这条约束现在就写死，是因为它极难回补：等批次 3 把八个能力分区页面写完再换 DS，等于重做 UI 层。

#### 表格三件标配（owner，2026-09-06）

产品内**每一张表**都带同样三件，顺序固定：

| 件 | DS 开关 | 说明 |
|----|---------|------|
| 1. 选择列 | `selectedKeys` + `onSelectionChange` | 无消费方时也在位；`leadingSpacer` 是它的占位形态（有列宽、无控件） |
| 2. 序号列 | `indexStart` | |
| 3. 操作列 | `rowActions` | 钉在最右，单个触发器 |

这是**装配件**不是功能：它的职责是让两张表的网格一致，读者在模块之间移动时不必
重新找东西。每一件**做什么**由各自页面决定。

**操作列即使没有操作项也保留列与三竖点占位。** 无权操作的读者过去拿到的是一张比
同事少一列的表——同一份数据两套网格；而且它正是 2026-09-05 评审那个缺陷的根源：
逐列宽度从右数，对这个读者整体错位一列。现在由
`components/table-fittings.tsx` 的 `RowActions` 渲染空且禁用的 DS 触发器：列保住
位置，三竖点说的是"这里没有你能做的事"，而不是消失并带走整个几何。

由此得到一条列宽规则：**`nth-child` 一律从左数**。选择列与序号列对所有读者无条件
存在，所以首个业务列恒为 `nth-child(3)`，左侧没有任何会消失的东西。

装配件加宽了表格，窄容器下文本列会被压扁（实测挤到 56-72px）。解法是给表
`min-w-*` 让 DS 的 `overflow-x-auto` 外层横向滚动，而不是压缩文字列——页面本身
不得横向滚动。

三件之外，同一批还定了三条表格呈现规则（owner，2026-09-06，先落在产品目录与
产品定价两个板块）：

1. **除标题列外，一律居中。** 标题列内容左对齐，其余列（含金额）居中。金额列因此
   从右对齐改为居中——这是明确的产品决定，覆盖"数字右对齐"的通用惯例。
2. **标题列的主标题加大加粗**（`text-body-lg font-semibold`，16px/600），副行编码
   保持 `text-body-sm`。只对**有主副两行**的标题列生效；产品状态配置的名称列是一个
   StatusBadge、没有副行，不适用。
3. **点击整行即切换选中**，不必点那个太小的复选框。由
   `table-fittings.tsx` 的 `rowClickSelection` 提供：一个装在外层容器上的监听器，
   按行在 `tbody` 中的位置映射回行，不动 DS 组件。三种点击不触发——行内的交互元件
   （操作触发器、链接、复选框本身）、结束一次文本选择的点击（从单元格里复制编码是
   一次拖拽）、以及表头与空态行。没有选择列的表（价目历史表用的是占位）不接这个
   行为：那里点一下会去勾一个根本没提供的框。

4. **资金列右对齐，右侧留白**（2026-09-06）。金额居中什么都对不齐——760,000 与
   1,400,000 的个位落在不同位置。右对齐让个位对齐，再用 `MoneyCell` 的 `pad`
   把整块数字从列的右缘推回来，于是"块看上去居中、字是右对齐"。`pad` 取
   (内容盒宽 - 最宽数字)/2，是**逐列**的值；只有一种宽度能被精确居中，取最宽的
   那个。留白写字面量不写 DS 令牌：实测本版 `pr-md`/`pr-lg`/`pr-xs` 全部解析为
   0px。

5. **列宽三条铁律**（2026-09-06，都是量出来的，不是推出来的）。
   - **选择列 / 序号列 / 操作列固定 64px**（`EDGE_COLUMNS` / `ACTION_COLUMN`）。
     DS 文档写 64、实际发 `w-control-3xl` = 56px（TD-022），此处以 owner 裁定的
     64 为准，从外部钉死。
   - **除标题列外全部钉死，标题列留 auto**。`table-fixed` 下若每一列都有宽度，
     富余会按比例分给**所有**列——1920px 实测把选择列和序号列从 56 撑到 100px，
     操作列撑到 228px。"固定宽"只在有一列能吸收富余时才成立。
   - **标题列既要上限也要下限**。auto 是双向的：容器宽时它独吞富余（1096px 下
     胀到 624px，中间空、右边挤），容器窄时它被压到 0（名称整个消失）。所以表加
     `max-w-*` 把富余变成外边距，标题列加 `min-w-*` 兜住下限。

#### 模块头部统计条（模版，owner 定版 2026-09-06）

模块页头部卡片折叠区内的那条统计,是一个**定版模版**。新模块照抄结构,不重新发明。
实现在共用件 `components/module-headline.tsx`,页面只提供数据。

**结构**（自上而下）：

```
[ 分段比例条 ]                     ← 无标题、无数字
统计数字  %                        ← 金额在前,占比紧跟其后
（色点）名称  小字                  ← 色点与它在条上那一段同色
```

**六条规则,以及为什么**：

1. **一个数组喂两个视图。** 色条与数字都由同一个 `stats` 渲染,所以顺序与颜色**不可能**
   漂移。给色条单独一个数组,就是两份要保持同步的清单——而两份清单不会一直同步。
   `share` 一个开关同时开出色条和百分比:条是"看见的比例",百分比是"说出来的比例",
   只给一半就是两个半成品。
2. **顺序按管理视角,不按生命周期。** 回款读作达成:已回款 → 逾期 → 已开票 → 计划中 →
   坏账。"计划中在最前"是分期**行进**的顺序,那是排期表的事,不是头部条要回答的问题。
3. **颜色是单色相明度,不是意图色拼盘。** 用 DS color-policy 的 `--level-N`,深浅编码
   确定性。意图色拼出来的条读起来像"几个并排的判断",而不是"同一笔钱切成几份"。
   只借色阶,`LevelMarker` 的渐变+外发光材质留在等级记号那里。
4. **异常用 tone,且优先于色阶。** 逾期这类不是"同一条路上更远的一步",而是"路断了",
   不该靠比较蓝色深浅去找。`tone` 存在时压过 `depth`;**同一个函数**解析色条段与色点的
   颜色,两处不可能对"哪条规则赢"给出不同答案。
5. **条 8px,与色点同高。** 条和点是同一种记号的两种形态,重量该一致。
6. **百分比用小字,不用徽标。** 一行五个徽标是五块装饰在跟它们注解的五个数字抢注意力;
   而且百分比**不是一种状态**,它是同一个量的另一种说法,所以用注脚的语气。

#### 哪些模块该有折叠（判据，owner 定版 2026-09-07）

上面那条统计条装在头部卡片的**折叠区**里。折叠不是每个模块都该有——它是用来
**补列表的盲区**的，不是把列表已有的东西再画一遍。三条同时成立才给：

1. 这个模块的集合能**自然分成 3–6 个有意义的桶**；
2. 桶**之间的比例**是有人会据此行动的读数；
3. 这个读数**下面的列表说不出来**。

第三条是判据的重心。前两条容易满足，第三条才把"有用"和"重复"分开。

**没有折叠的模块，头部照旧是卡片 + 图标 + 标题 + 标签 + 说明**——`ModuleHeadline`
不传 `stats` 即可（与传空数组不同：空数组仍会展开并显示 `emptyNote`，意思是"这里有个
分解，只是现在空的"；不传则是"这个模块没有分解"）。那一档不渲染 Collapsible，也不渲染
箭头——一个点开什么都没有的箭头，是在教用户这个控件没用。

**已裁定不给折叠的三个，以及理由**（2026-09-07）：

| 模块 | 为什么不给 |
|------|-----------|
| 漏斗全景 | 整页就是一个分解。在分解之上再套一层更粗的分解，是同一件事说两遍 |
| 线索管理 | 唯一自然的切法是按状态，而标题行的四个标签**就是切完的结果**。折叠只多给一根条 |
| 商机智探 | 按定向线切？队列本身已经按它分组、每组标题带着条数。按信号类型切确实是列表的盲区，但那是**运营侧观察**，不是判信号时要看的东西 |

**接入方式**：页面给每个 `HeadlineStat` 填 `depth`（0–5,0 是比 DS 色阶下限更淡的
`accent` 档）和可选的 `tone`,并给 `ModuleHeadline` 传 `share`。

**实测记下的令牌陷阱**（都属于"静默解析为空"这一族,同 TD-022 的邻居）：
`h-md` / `h-lg` 高度为 0px；`--danger-text` / `--danger-border` / `--warning-border`
背景色为透明,而 `--success-text` / `--warning-text` 正常——danger 走 DS 自己的
`destructive`。**颜色和尺寸一律从 DOM 读回来核对,不看类名。**

守卫：`(app)/lib/table-fittings.test.ts`。尚未改造的表按名字登记在
`NOT_YET_CONVERTED`（都属于侧栏重建还没走到的模块），改造该模块的批次删掉对应行；
唯一因替代而不出操作列的是产品目录的排序变体（上移/下移已在一个常规尾列里），
登记在 `ACTIONS_REPLACED`。

## 2. 域 -> schema 的映射

八个产品域映射到五个 DB schema。映射依据是**事务边界**：经常在同一个事务里被一起
写的对象放同一个 schema。

| Schema | 承载域 | 事务边界理由 |
|--------|--------|-------------|
| `yucer_core` | D4 | 客户主数据被所有域引用，是稳定的引用中心 |
| `yucer_gtm` | D1 D2 D3 | 制定战略时常同时落细分市场、区域、目标、战役 |
| `yucer_pipeline` | D5 D6 | 信号->线索->商机是一条连续管道，转化是单事务 |
| `yucer_delivery` | D7 | 赢单后才产生，生命周期与前面几段解耦 |
| `yucer_agent` | D8 | 横切八个能力分区，但自身数据独立，可独立扩容与清理 |

完整理由见 `decisions/ADR-002-five-schemas-for-eight-domains.md`。

## 3. 跨 schema 引用

跨 schema 的外键是**允许的**，且已在 DDL 中显式声明：

| 引用 | 删除行为 | 理由 |
|------|---------|------|
| `pipeline.opportunity.account_id -> core.account` | `RESTRICT` | 有单的客户不允许被删掉 |
| `delivery.project.account_id -> core.account` | `RESTRICT` | 同上 |
| `delivery.project.opportunity_id -> pipeline.opportunity` | `SET NULL` | 商机清理不应连带毁掉已在交付的项目 |
| `pipeline.signal.account_id -> core.account` | `SET NULL` | 信号是证据，客户没了证据仍有效 |
| `pipeline.lead.campaign_id -> gtm.campaign` | `SET NULL` | 战役归档不应删除线索 |
| `gtm.campaign.plan_id -> gtm.strategy_plan` | `SET NULL` | 战略归档不应删除战役 |

**规则**：向上引用（下游指上游）一律 `SET NULL` 或 `RESTRICT`，**从不 CASCADE**。
CASCADE 只用于真正的从属关系（联系人属于客户、里程碑属于项目、消息属于会话）。
理由：链路下游的数据是既成事实，不该被上游的整理动作抹掉。

## 4. 三类表的写入形态

DDL 与列级写锁把域内的表分成三类，实现时必须按类别处理：

| 类别 | 表 | 写入形态 |
|------|----|---------|
| **可变实体** | account / opportunity / project / campaign ... | INSERT + 白名单列 UPDATE |
| **只追加日志** | opportunity_stage_event / forecast_snapshot / agent_message / account_relation | 只 INSERT，纠错=新增 |
| **半不可变** | signal / lead / agent_action | 事实字段冻结，仅结论字段可写 |

「半不可变」是本产品最容易写错的一类。以 `agent_action` 为例：`payload` /
`rationale` / `confidence` 是模型当时的判断，冻结；`status` / `decided_by_sub` /
`decided_at` / `executed_at` 是人类决策与执行，可写。实现时若试图「顺手更新一下
rationale」，服务角色会直接 permission denied——这是设计意图，不是障碍。

## 5. 两道门在代码中的落点

```
请求 -> 会话解析(auth/)     -> 拿到 workspace_id + sub
     -> 权益门(entitlement/) -> canUseFeature(entitlement, "pipeline.forecast")
     -> 权限门(authz/)       -> memberHasPerm(sub, "pipeline.forecast")
     -> 域业务规则(domains/)  -> 纯函数校验（阶段机、归因、口径）
     -> 持久化(lib/db.ts)     -> DDL 列级写锁兜底
```

四层是**递进收紧**的，任何一层都不得跳过。最后一层的列级写锁是兜底而非主防线：
应用层写对了它不该触发，触发了说明上面某层漏了。

## 6. 留白与批次

本批次交付的是**结构**（数据面、商业面、文档面），不含域页面与域服务实现。
`(domains)/`、`authz/`、`domains/<d>/lib/` 三处是显式留白，落地计划见
`docs/70-workplan/00-index.md`。
